# Agent executor adapter SDK readiness

Research date: 2026-10-25. Repository snapshot: `3699e2bf4f153d25b13b18bb9975c09987708d2a`, branch `feat/agentic-durable-execution`. This is source and metadata research; it does not accept ADR 0057, choose the durable-versus-reconciliation model, or implement an adapter.

## Findings that affect the next packet

Published first-party harness packages and ACP SDK 2.x exist. Their existence does not establish Bun compatibility, permission conformance, durable retry safety, or physical cancellation. The planned adapters remain blocked on specific contract questions:

- The current Codex harness accepts only `allow-all`, while PUNI accepts only `read-only` and `allow-edits`. There is no supported direct mapping for those accepted policies in the inspected release.
- Claude Code's `allow-reads` requests approval for edits and shell execution. It is a baseline permission policy, not an immutable read-only guarantee. Omitting the mode defaults to `allow-all`.
- Current harness cleanup suppresses important failures. A resolved `destroy()` cannot establish physical quiescence, and an aborted stream can settle before remote work stops.
- SDK 2.x still defaults to ACP v1. It separates stable and unstable features. PUNI already uses the app builder API, so removing legacy classes alone does not require a local rewrite; its `plan_update` consumer does require a feature-surface decision.
- The claim that ACP v1 exposes no usage is too broad. Installed SDK 1.4.0 already has optional unstable usage. The installed Claude ACP implementation reports cumulative session counters, and the current harness Claude bridge manufactures zeroes when counts are absent. Neither is sufficient evidence for Dash's measured per-turn usage without additional provenance.

These findings concern [the proposed decision](../adr/0057-activities-run-on-the-ai-sdk-and-an-interpreter-coordinates.md), [planned adapter tasks](../../openspec/changes/twilight-agentic-workflows/tasks.md#3-the-cli-harness-adapter), and the adopted [executor contract](../../openspec/changes/twilight-agentic-workflows/executor-design.md#public-contract). No existing planning document was changed.

## Harness exported contract

Claude exports `createClaudeCode(settings?)` and `claudeCode`; Codex exports `createCodex(settings?)` and `codex`; ACP exports `createACP(settings)`. These are distinct adapter factories, not exports from the installed `ai` package. The returned session drives `doPromptTurn` and `doContinueTurn`; prompt control supplies tool results, optional approval/user-message submission and a `done` promise. History reads are an optional `doReadHistory` capability. [Versioned adapter interface](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness/src/v1/harness-v1.ts), [session interface](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness/src/v1/harness-v1-session.ts), [prompt control](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness/src/v1/harness-v1-prompt-control.ts)

## Permission mismatch is concrete

PUNI's `CliHarnessClass` admits `harness:'claude-code'|'codex'` and `permissionMode:'read-only'|'allow-edits'`; its JSDoc explicitly says these are desired policies, not bypass/backend flags. Local evidence: `apps/twilight-structure/twilight-burokrat/cli/src/contracts/workflow-binding.ts:13`.

The harness contract instead defines `allow-reads | allow-edits | allow-all`, for adapter-native tools only. Host-executed tools use the separate `toolApproval` configuration. The framework default is `allow-all`; absent custom tool approval status is treated as allowed. No accepted binding mode should silently become that default. [Permission type](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness/src/v1/harness-v1-permission-mode.ts), [framework permission resolution](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness/src/agent/internal/permission-mode.ts)

Claude maps `allow-all` to native `bypassPermissions`, `allow-edits` to `acceptEdits`, and `allow-reads` to `default`. It asks for approval on edit/shell tools under `allow-reads`, and shell tools under `allow-edits`; a positive host decision can then allow them. Therefore `read-only → allow-reads` alone does not prove that writes are prohibited. A packet must specify the host decision behavior and test prohibited writes through the actual production permission path before claiming the accepted policy is enforced. [Claude bridge, lines 165–255 and 343–376](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness-claude-code/src/bridge/index.ts#L165)

Codex declares `supportsBuiltinToolApprovals:false`; `doStart` throws `HarnessCapabilityUnsupportedError` if `permissionMode` is supplied and is not `allow-all`. The framework also rejects a non-allow-all baseline for an adapter without built-in approval support. There is no source-backed direct implementation of either accepted PUNI mode using this release's normal baseline permission path. A fake `HarnessV1` passing a policy mapping test would not resolve this incompatibility. [Codex adapter, lines 224–247](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness-codex/src/codex-harness.ts#L224), [framework guard, lines 263–287](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness/src/agent/harness-agent.ts#L263)

## Session identity, continuation and cancellation limits

The harness session ID is caller-supplied or framework-generated. Claude's native conversation ID is distinct: the bridge emits it as `harnessMetadata['claude-code'].sessionId` and the adapter retains it as `claudeSessionId` in lifecycle state for exact conversation resume. Do not equate a native conversation ID, framework session ID and durable attempt/creation key without a retained mapping. [Agent creation](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness/src/agent/harness-agent.ts#L317), [Claude resume payload](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness-claude-code/src/claude-code-harness.ts#L813), [native ID emission](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness-claude-code/src/bridge/index.ts#L818)

`detach()` returns persistable resume state and leaves runtime/sandbox running; `suspendTurn()` returns continuation state and also leaves them running. `stop()` returns state for later resume. `createSession({sessionId,resumeFrom})` validates adapter lifecycle state; `continueFrom` resumes an unfinished turn. These are real continuation APIs, but do not establish durable creation lookup, launch/turn deduplication, owner fencing or authoritative effect inspection for PUNI's `RecoveryCapabilities`. Local required capabilities are at `apps/twilight-structure/twilight-dash/cli/src/agents/execution-records.ts:102`; the common methods are at `activity-executor.ts:60`. [Harness session lifecycle, lines 473–610](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness/src/agent/harness-agent-session.ts#L473)

The Claude adapter's abort listener sends an `abort` bridge message and immediately settles its local turn with an abort error, swallowing a send failure. Therefore observing aborted/rejected stream consumption is not an acknowledgment of physical stop. [Claude adapter, lines 1443–1463](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness-claude-code/src/claude-code-harness.ts#L1443)

More decisively, `HarnessAgentSession.destroy()` suppresses rejection from `session.doDestroy()` and owned `sandbox.destroy()`. `stop()` suppresses an owned sandbox's stop rejection. Claude's lower adapter destroy path also uses a bounded process wait and suppresses kill failure. Resolved cleanup cannot serve as PUNI's authoritative physical-quiescence proof. Source inspection establishes this limitation; the failure branches were not executed here. [Wrapper cleanup, lines 541–585](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness/src/agent/harness-agent-session.ts#L541), [Claude destroy, lines 1699–1735](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness-claude-code/src/claude-code-harness.ts#L1699)

## Usage must retain provenance

Claude's bridge `mapUsage` sums native input/cache counters and maps output tokens, but substitutes zero for missing native fields; `defaultUsage()` supplies all zeroes. A terminal finish falls back to `defaultUsage()` when turn/step usage is unavailable. Thus a normalized zero cannot by itself distinguish reported zero from missing usage. Dash must not mark every numeric harness count as measured solely because the normalized SDK shape contains numbers. The exact provenance needed to recover trustworthy counts remains unverified. [Usage mapping, lines 906–936](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness-claude-code/src/bridge/create-emit-stream-event.ts#L906), [finish fallback, lines 818–822](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness-claude-code/src/bridge/index.ts#L818)

Installed ACP SDK 1.4.0's `PromptResponse` already contains optional **unstable** `usage`, with `inputTokens`, `outputTokens`, `totalTokens` and optional cache/thought counters. Its comments mix “this turn” with cumulative/session wording. Installed Claude ACP `sessionUsage` reads `session.accumulatedUsage`; `turnOutcome` returns those counters. This is concrete cumulative implementation evidence, not proof of per-attempt accounting. Local evidence: `node_modules/@agentclientprotocol/sdk/dist/schema/types.gen.d.ts:2970`, `:3011`; `node_modules/@agentclientprotocol/claude-agent-acp/dist/acp-agent.js:6517`, `:6531`.

ACP SDK 2.0.2 stable v1 `PromptResponse` has `stopReason` and `_meta`, without typed turn usage. Its `usage_update` describes current context usage (`used`, `size`) and optional cumulative cost, not input/output counts for a turn. The `/unstable` declaration restores optional `PromptResponse.usage` with input/output counters, still with mixed turn/cumulative documentation. A version upgrade does not imply that a peer reports it, that its semantics are per turn, or that it includes all subagent work. [Official 2.0.2 tarball](https://registry.npmjs.org/@agentclientprotocol/sdk/-/sdk-2.0.2.tgz): `dist/v1/schema/types.gen.d.ts:2246,2713`; `dist/v1/unstable/schema/types.gen.d.ts:2689,2730`. [Migration guide: shared type changes](https://github.com/agentclientprotocol/typescript-sdk/blob/f2f218d314ee8f42c37c466b55d2b917ddc0006c/MIGRATION_STABLE_UNSTABLE.md#check-shared-types-not-just-method-names)

An explicitly unknown ACP usage outcome can remain a conservative adapter policy. Its explanation should identify absent stable/peer-supported per-turn evidence, rather than assert that every ACP v1 implementation lacks usage. No arithmetic attribution or new usage policy is chosen here.

## ACP SDK 2.x and the existing consumer

Registry versions `2.0.0`, `2.0.1` and `2.0.2` are published. Default import remains stable ACP v1; draft v2 requires `/experimental/v2` and remains experimental. `/unstable` is a complete v1 surface, not a supplement that changes other modules' imports. Selecting it does not advertise capabilities or establish peer support. [2.0.2 metadata](https://registry.npmjs.org/@agentclientprotocol/sdk/2.0.2), [official migration guide](https://github.com/agentclientprotocol/typescript-sdk/blob/f2f218d314ee8f42c37c466b55d2b917ddc0006c/MIGRATION_STABLE_UNSTABLE.md)

The published 2.0.2 default declarations retain `agent()`, `client()`, `onRequest`, `onNotification`, `connect`, `connectWith`, `ClientContext.request/notify`, `AgentContext.request/notify`, and `ndJsonStream(output,input)`. Stable v1 streams carry individual JSON-RPC messages over Web byte streams; the draft v2 stream is batch-capable. Connections expose `signal`, `closed:Promise<void>`, and `close(error?):void`. They do not expose child-process exit through `closed`. [2.0.2 tarball](https://registry.npmjs.org/@agentclientprotocol/sdk/-/sdk-2.0.2.tgz): `dist/v1/stable/acp.d.ts:15,28,95,150,183,575,660,669`.

Legacy `ClientSideConnection`/`AgentSideConnection` and implementation interfaces are removed in 2.x. PUNI's prototype already calls `client()` and `agent()`, so that removal is not itself an observed consumer migration. A concrete split issue exists in `tools/harness-example/src/log.ts:30`: `plan_update` belongs to 2.0.2's unstable v1 union, absent from its stable union. Upgrade work must choose a consistent feature surface across the client, fake peer and log types; simply changing a pin is not enough. [Migration guide](https://github.com/agentclientprotocol/typescript-sdk/blob/f2f218d314ee8f42c37c466b55d2b917ddc0006c/MIGRATION_STABLE_UNSTABLE.md), [2.0.2 tarball](https://registry.npmjs.org/@agentclientprotocol/sdk/-/sdk-2.0.2.tgz): `dist/v1/unstable/schema/types.gen.d.ts:2866`.

ACP `session/new` returns the agent-assigned session ID. `session/load` is capability-gated and replays history as `session/update` before completing; current protocol also distinguishes resume-without-replay. This supports a recall surface for agents advertising load, not arbitrary lookup/deduplication by PUNI creation key. [Official session setup](https://agentclientprotocol.com/protocol/v1/session-setup)

The SDK exposes `session/request_permission` and selected-option/cancelled outcomes. Permission option kinds include `allow_once`, `allow_always`, `reject_once`, `reject_always`; the client chooses according to policy. A cancelled prompt requires cancelled responses to pending permission requests. The protocol permits agents to request permission; this alone is not proof that all effects are governed by a client callback. [Official tool-call permission contract](https://agentclientprotocol.com/protocol/v1/tool-calls#requesting-permission)

`session/cancel` is a session notification; normal prompt stop reasons include `end_turn`, `max_tokens`, `max_turn_requests`, `refusal`, `cancelled`. SDK request `cancellationSignal` instead sends `$/cancel_request` and does not locally reject the pending promise before a peer response. Generic request cancellation is optional at the protocol boundary. Neither closing a connection nor sending a notification establishes process-tree quiescence. [Prompt lifecycle](https://agentclientprotocol.com/protocol/v1/prompt-turn), [generic cancellation](https://agentclientprotocol.com/protocol/v1/cancellation), [2.0.2 tarball](https://registry.npmjs.org/@agentclientprotocol/sdk/-/sdk-2.0.2.tgz): `dist/core/jsonrpc.d.ts:84`, `dist/v1/schema/types.gen.d.ts:2267,3904`.

Root-agent consumer inspection, source-checked here, found the prototype auto-selects the first allow-kind permission option, discards prompt response usage, throws on every non-`end_turn` stop, and requires load capability for the whole helper. Its `close():void` closes transport then calls `child.kill()` without awaiting exit. The fake peer's cancel notification is a no-op. These remain prototype behavior, not ActivityExecutor conformance or physical cancellation proof. Local evidence: `tools/harness-example/src/acp.ts:47,87,109,136,154`; `tools/harness-example/src/fake-acp-agent.ts:128`.

## Deferred harness ACP claim needs a fresh boundary check

The current `@ai-sdk/harness-acp` exports `createACP` and `permissionModeMapping`; its permission controller translates pending ACP requests into host tool approval events and selects explicit allow/reject-once options. Thus “no permission seam exists” is outdated as a blanket package claim. This does not establish equivalence with PUNI's required policy. [ACP permission controller](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness-acp/src/v1/bridge/permission-controller.ts), [settings](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness-acp/src/v1/acp-v1-settings.ts)

Cold restoration uses advertised resume, otherwise load, and refuses to manufacture a new unrelated session. During restoration it suppresses historical updates and discards captured history. Inspection found no `doReadHistory` implementation in the Claude, Codex or ACP harness session implementations. The generic optional history API therefore does not establish Board recall for these adapters. Keep the planned direct ACP recall path pending an explicit, tested exposed replay contract. [ACP restoration source](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness-acp/src/v1/bridge/session-lifecycle.ts), [ACP session implementation](https://github.com/vercel/ai/blob/612be2311464804d1e4897afacbf8f3fc2f6d9e3/packages/harness-acp/src/v1/acp-v1-harness.ts)

## Integration placement remains unresolved

Task 4.1's literal move into Dash cannot retain prototype consumers by forwarding their imports into the Dash CLI under the current boundary policy. `tools/harness-example/project.json:6` tags the prototype `scope:infra` without a product tag; `apps/twilight-structure/twilight-dash/cli/project.json:6` tags Dash `scope:app` and `product:twilight-dash`. `eslint.config.js:13` constructs generated product rules and `eslint.config.js:71` installs them in the dependency constraints. `tools/tool-devsync/workspace-projects.mjs:257` generates a `scope:infra` rule admitting only `scope:infra` or `product:shared` dependencies (rule at line 281; adjacent historical proof begins at line 277). The tools-to-Dash import would cross that constraint. This is a source-level integration constraint; no lint or boundary test was executed in this research. Placement and prototype retirement therefore need an accepted plan before a mechanical move. This finding does not choose a new shared library, duplicate the client, retire the prototype, or weaken the fence.

## Required next safe action and evidence limits

Prepare a bounded adapter contract packet before dependency mutation: identify an exact coherent SDK graph, retain its source identities, choose the ACP stable/unstable surface explicitly, and spell out the permission mappings and unsupported cases. Include actual production-path negatives for prohibited edits, refused approval, missing allow/reject options, absent usage, cumulative usage, abort transport failure and cleanup failure. Tests against a fake harness alone cannot prove a real adapter supports the selected policy. This is required evidence preparation, not a choice of execution architecture.

The next authorized proof can be source/type planning and inert transport/SDK-contract fixtures in a separately authorized implementation packet. Bun/sandbox compatibility, actual harness session creation, real CLI/native conversation resume, real peer replay completeness, full usage attribution, physical process-tree stop and durable recovery remain unverified. No session factory, child process, SDK request, credential read, provider call, token spend, activation, migration, test, build or remote gate ran during this research. The only repository write is this note; protected runtime/storage paths, pins, existing docs, Git index and HEAD were untouched.

A network read first failed in the sandbox with `ENOTFOUND`; scoped read-only registry/GitHub retrieval succeeded after escalation. Source download/unpack is not package installation. Exploratory registry requests for `@ai-sdk/sandbox` and `@ai-sdk/sandbox-local` returned HTTP 404; this is not a finding that all local sandbox implementations are unavailable. Shell `bun` reported `1.4.4`; the parent identified its separately pinned `1.4.2` binary. No Bun compatibility claim relies on either version. No full gate is claimed: this research-only note does not prove implementation correctness.
