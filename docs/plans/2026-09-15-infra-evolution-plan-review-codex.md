## Critical

1. **Critical — §2.1, §4, §7: the PVC backup design cannot work.** Hetzner Cloud Volumes do not provide snapshots, and server backups explicitly exclude attached Volumes. Therefore hcloud CSI cannot supply the `VolumeSnapshot`s assumed by Velero, and the claimed independent restore paths do not exist. [Hetzner documents both limitations](https://docs.hetzner.com/cloud/volumes/overview/); Velero’s CSI data mover also requires a snapshot-capable driver. [Velero prerequisites](https://velero.io/docs/main/csi-snapshot-data-movement/). **Fix:** use the existing verified SQLite `VACUUM INTO` pipeline, ECK SLM for Elastic, a Prometheus TSDB snapshot or remote-write target, and Velero filesystem/Kopia backup only where crash consistency is acceptable.

2. **Critical — §9.4: the SQLite cutover and rollback can fork production data.** “Copy the SQLite file” is unsafe with WAL active; a Litestream restore is only a point-in-time copy; DNS propagation can send writes to old and new backends; after the new DB accepts a write, pointing DNS back loses that write. Litestream is also not the currently implemented backup path—the encrypted pull-based pipeline is live ([backups.md](/home/df/wd/personal/claire/notes/backups.md:455)). **Fix:** fence all writes, drain WS, stop the old backend, take and verify a final consistent snapshot, restore ownership plus WAL state, run `integrity_check` and `foreign_key_check`, start exactly one new writer, smoke through an override, then switch traffic. Rollback is safe only before writes reopen; afterward require a reverse data transfer or fix forward.

3. **Critical — §9 and existing deploy contract: Kubernetes deployment semantics omit the WBS single-writer and migration guarantees.** A default Deployment rollout can overlap old and new `be-01`; Flux may reconcile tiers independently; nothing replaces the current migration-status capture, additive migration, health gate, WS drain, rollback, and smoke sequence. **Fix:** codify `be-01` as one replica with `Recreate` or an equivalent fenced rollout and `ReadWriteOncePod`; run migrations once under an explicit lock; order be/gw/fe promotion; preserve abort rollback and post-deploy smoke as release gates.

4. **Critical — §2, §3, §9.5: the role model is unschedulable in stage 1.** One label key cannot be both `role=core` and `role=obs`; applying the obs taint to the shared node also blocks core workloads. Moving novel/studio source-run pods to core contradicts the forge role and “no hostPath outside forge.” **Fix:** use independent capability labels such as `puni.io/core=true` and `puni.io/obs=true`; add the obs taint only after obs is dedicated; give platform DaemonSets tolerations for every taint; keep every source-run dev workload on forge.

5. **Critical — §3→§4: the planned in-place rescale is impossible.** Stage 1 creates CPX42 with a 320 GB root disk, then stage 2 proposes CCX23 with 160 GB. Hetzner refuses rescaling to a plan with a smaller disk regardless of usage. [Hetzner rescale rules](https://docs.hetzner.com/cloud/servers/faq/). **Fix:** use CCX23 from stage 1, choose a stage-1 type whose retained disk fits CCX23, or describe stage 2 as a new-server control-plane migration with measured downtime—not “one reboot.”

## High

6. **High — §3 memory budget: the advertised 4.3 GB headroom is not credible.** The table allocates the full 16 GB without OS/kubelet reserve, ECK and Prometheus operators, page cache, or the novel/studio/MLflow workloads later moved onto core. Requests alone do not cap usage; ECK sizes heap from the memory limit or, without one, node memory. [ECK resource behavior](https://www.elastic.co/docs/deploy-manage/deploy/cloud-on-k8s/manage-compute-resources). **Fix:** remove dev and MLflow from core, set measured request/limit pairs, reserve at least 2–3 GiB for node services and eviction headroom, use PriorityClasses, and load-test before selecting CPX42.

7. **High — §2.2, §7: resource policy does not provide the claimed memory isolation.** A LimitRange generally defaults or constrains resources; it does not prove manifests declared intentional requests. “No BestEffort” still leaves Burstable pods evictable, while `bootstrap.memory_lock` does not prevent node OOM. [Kubernetes QoS behavior](https://kubernetes.io/docs/concepts/workloads/pods/pod-qos/). **Fix:** admission-policy enforcement for explicit resources, Guaranteed QoS for critical stateful pods where appropriate, kube/system reservations, eviction thresholds, and negative admission tests.

8. **High — §3 forge migration: h2 is not ready to join safely.** It is already 85% full with active swap, while k3s adds a second image store and kubelet normally refuses enabled swap unless explicitly configured. [Kubernetes swap requirements](https://kubernetes.io/docs/concepts/cluster-administration/swap-memory-management/). Host-run gates and Dagger are invisible to the scheduler. **Fix:** reclaim or attach storage before installing k3s, decide and test swap policy, reserve host resources, and put gates/builds in bounded systemd cgroups.

9. **High — §2.1, §6, §7: backup failure domains and recovery secrets are missing.** `hel1` Object Storage is off-node, not off-region: a bucket’s data stays in one location and cross-location replication is manual. [Hetzner Object Storage FAQ](https://docs.hetzner.com/storage/object-storage/faq/general/). The Flux age key exists only in the cluster, and a k3s restore also requires the server token. [k3s restore requirement](https://docs.k3s.io/datastore/backup-restore). **Fix:** retain the h1 generations, replicate immutable encrypted copies to another region/provider, escrow the rclone key and age key, back up the k3s token, enable `--secrets-encryption`, and drill a zero-existing-cluster restore.

10. **High — §7–§8: “zero-loss” logging is false.** A 1 GB queue plus bounded retries loses logs when the outage exceeds capacity; full queues or I/O errors drop telemetry, and a hostPath disappears with the node. [OTel queue failure semantics](https://github.com/open-telemetry/opentelemetry-collector/blob/main/exporter/exporterhelper/README.md). Kubelet retains only 60 MiB per container here. **Fix:** state a maximum survivable outage derived from measured peak rate, alert on enqueue failures and queue runway, use unbounded-time retry within a bounded disk budget, and archive raw logs independently before rotation if losslessness matters.

11. **High — §7 upgrades: the order and availability claim are wrong.** There is no “staging node”; staging runs on core. k3s requires server nodes before agents, opposite the proposed forge-before-core test, and upgrading the sole core necessarily interrupts ingress and stateful applications. [k3s upgrade order](https://docs.k3s.io/upgrades/automated). Uncoordinated Sunday unattended reboots may hit several nodes together. **Fix:** test the exact pinned version on a disposable cluster, snapshot first, upgrade server then agents, serialize OS reboots, and explicitly budget stage-1/2 maintenance downtime.

12. **High — §5: stage-3 HA lacks a working control-plane endpoint.** Three servers need a fixed registration/API address; the listed LB covers only Traefik. Placement groups, control-plane taints, ingress spread, PDBs and failure-domain topology are absent. [k3s HA load-balancer requirement](https://docs.k3s.io/datastore/cluster-loadbalancer). **Fix:** specify the 6443 VIP/LB, `tls-san`, join sequence, placement groups, quorum recovery, and separate ingress/app/control-plane placement.

13. **High — §5: CloudNativePG cannot provide the claimed resilience on two app nodes.** Three PostgreSQL pods across two nodes place two replicas in one failure domain; losing that node can remove two copies. Replication alone is not backup, and asynchronous failover can lose acknowledged data. [CloudNativePG failover trade-offs](https://cloudnative-pg.io/docs/1.27/failover/). **Fix:** use at least three storage-capable failure domains, define synchronous/quorum policy, WAL archive plus base backups and PITR, and write a separate SQLite→Postgres reconciliation/cutover/rollback plan.

14. **High — §5: “survive a node loss” omits Prometheus, Alertmanager, Grafana and registry HA.** Prometheus local storage is explicitly non-replicated and non-clustered. [Prometheus storage limitations](https://prometheus.io/docs/prometheus/latest/storage/). **Fix:** two Prometheus replicas plus Thanos/remote-write, an Alertmanager quorum, externalized Grafana state, and a tested registry failover or documented deploy outage.

15. **High — §2.2, §4: Flux does not create the stated promotion pipeline.** Image automation edits and pushes Git manifests; it neither deploys source-run dev worktrees nor creates per-branch Kustomizations. [Flux image automation](https://fluxcd.io/flux/guides/image-update/). Staging and prod both tracking `main` can reconcile simultaneously, so staging proves nothing before prod. **Fix:** keep source-run dev outside Flux image automation; promote immutable digests through distinct staging and prod commits with an e2e approval gate. Make Flux mandatory before prod or specify its later adoption procedure.

16. **High — §2.2–§2.3: namespace isolation is treated as a security boundary.** A user allowed to create hostPath pods on forge can escape to the host; RBAC cannot express a generic `dev-*` namespace wildcard; taints do not isolate network or credentials. Hetzner Cloud Firewalls do not filter private-network traffic. [Hetzner firewall limitation](https://docs.hetzner.com/cloud/firewalls/faq/). **Fix:** per-namespace RoleBindings, restricted Pod Security, admission allowlists for exact host paths, default-deny NetworkPolicies, host firewalling, non-default service accounts, audit logging, and no user-created privileged workloads.

17. **High — §3, §5, §8: storage sizing breaks at the plan’s own growth points.** At 1 GB/day, 90-day hot retention needs at least 90 GB before index overhead and headroom; the 60 GB stage-1 ES volume alerts at 45 GB. At 20 GB/day, 90 days is 1.8 TB before replicas, while stage 3 prices no Elastic volumes or Object Storage overage. Registry size is also 50 GB in §2.1 but 30 GB in stage 1. **Fix:** size from measured indexed bytes/day × retention × replica factor ÷ usable watermark, publish low/expected/high bills, and trigger expansion from forecasted days-to-full—not a fixed 20 GB/day.

18. **High — §11 cost arithmetic: “new spend,” “total,” and “baseline” use different bases.** Stage 1 counts the already-paid Object Storage bucket as new spend but does not subtract h3/h4; stage 3 omits storage, backup percentage, IPs, Object Storage overage, and the Twilight control-plane server plus its ADR-required two agents. **Fix:** provide gross estate cost, incremental cost, retirement credits, and minimum/expected/maximum cost for each stage in one currency.

19. **High — §2.1 registry: the migration adds risk without defining a consumable endpoint.** Node containerd and host-run Dagger need a node-resolvable TLS/auth endpoint and registry mirror configuration; an internal Service name is insufficiently specified. Weekly online `registry:2` GC can corrupt concurrent uploads. [Registry GC requires read-only or stopped mode](https://distribution.github.io/distribution/about/garbage-collection/). **Fix:** retain the working h2 registry during stage 1, then expose a private stable endpoint and run stop-the-world/read-only GC with tag retention and restore tests.

## Medium

20. **Medium — §7 Elastic controls: watermark behavior and the drill are wrong.** Low is 85%, high is 90%, and only flood stage—95% by default—sets indices read-only. [Elastic watermarks](https://www.elastic.co/docs/troubleshoot/elasticsearch/fix-watermark-errors). PVCs cannot shrink, contradicting §6. **Fix:** keep defaults unless measured otherwise; test by filling a disposable PVC or temporarily lowering thresholds, then prove automatic write-block recovery.

21. **Medium — §2.1, §8: ECK does not create SLM automatically, and tail sampling may add license cost.** ECK requires manual repository and SLM configuration; §8 promises one-year archives before stage 2 installs SLM. Tail-based sampling is absent from Elastic’s Basic tier. **Fix:** stage-gate the promise, configure and alert on completed snapshots from day one if logs matter, and use head sampling unless a paid Elastic tier is budgeted.

22. **Medium — §2.1, §7: Traefik ownership is contradictory.** Bundled Traefik is managed as a k3s packaged component and its version follows k3s; a HelmChartConfig customizes it but does not make upgrades independent. [k3s Traefik behavior](https://docs.k3s.io/networking/networking-services). `hostNetwork` also conflicts with leaving ServiceLB unspecified. **Fix:** either accept bundled/version-coupled Traefik with pinned k3s and HelmChartConfig, or disable bundled Traefik and own a pinned HelmRelease; explicitly disable/configure ServiceLB and define the stage-3 LB transition.

23. **Medium — §9.2: Cloudflare versus HTTP-01 is a false binary.** cert-manager supports DNS-01 through external webhooks and delegated `_acme-challenge` CNAMEs while authoritative DNS remains elsewhere. [cert-manager DNS-01 options](https://cert-manager.io/docs/configuration/acme/dns01/). **Fix:** prototype delegated Cloudflare/acme-dns challenges or a maintained provider webhook; migrate nameservers only for broader DNS reasons, with DNSSEC and rollback steps.

24. **Medium — §2.1, §2.3: hcloud CCM networking is under-specified.** k3s must disable its built-in cloud controller consistently; CCM/CSI versions need pinning and compatibility tests; Flannel needs explicit private interface/node IP/MTU settings. Current CCM versions before 1.30.1 are broken by a removed Hetzner API field. [Official CCM notice](https://github.com/hetznercloud/hcloud-cloud-controller-manager). **Fix:** pin tested versions and spell out `--disable-cloud-controller`, network ID, internal/external IP selection, Flannel interface, ports and host firewall rules.

25. **Medium — §7 monitoring: several named alerts do not exist merely by installing kube-prometheus-stack.** The chart excludes blackbox-exporter, Alertmanager delivery waits until stage 2, and tainted nodes require exporter/collector tolerations. **Fix:** install and configure blackbox probes, alert routing and dead-man monitoring in stage 1; add explicit rules and negative drills for every claimed failure signal.

## What the plan gets right

- It correctly identifies WBS SQLite as the blocker to horizontal backend replicas.
- Separating forge from production addresses the existing disk, memory and build blast radius.
- Embedded etcd from day one avoids a later datastore conversion.
- External uptime checks, retention limits, restore drills and keeping Victoria in parallel are sound instincts.
- Immutable images, pinned versions, IaC, private networking and staged adoption triggers are the right overall direction.
