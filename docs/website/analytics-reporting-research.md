# PUNI acquisition and funnel reporting research

Researched 2026-10-29 against official Google documentation and public source revision `083fb680139ad9cb2207e1ed6520f42b33d0a57c` (`public083`). This is a reporting proposal and evidence review, not configured account assets or a completed launch. The [existing account setup](analytics-setup.md) remains the operator setup reference; this note adds verified API boundaries, campaign candidates and the remaining proof plan. The [analytics requirements](../../openspec/changes/website-funnel-analytics/specs/funnel-analytics/spec.md) require consent, bounded metadata, confirmed persistence, acquisition continuity and reports by channel, starting choice and device. The [acquisition draft](acquisition-experiments.md) supplies the first audience hypothesis: help improving an AI-built app. It supplies no demand, pricing or ROI evidence and authorizes no publishing, outreach or spend.

## Account setup proposed for the existing events

First record numeric property ID, numeric web stream ID, measurement ID, host pair, access owner and settings date. Admin API streams expose the property/stream resource path and `webStreamData.measurementId`; a `G-...` measurement ID cannot substitute for the numeric property in reporting calls. Prefer separate dev/production properties as already proposed. If they share a property, apply the appropriate numeric Stream ID plus Hostname host-pair filter to every saved analysis and API query, while recognizing that property-wide settings and key events are still shared. Do not filter a production journey down to the site hostname alone: its lead occurs on the app. [Stream resource](https://developers.google.com/analytics/devguides/config/admin/v1/rest/v1beta/properties.dataStreams), [report property argument](https://developers.google.com/analytics/devguides/reporting/data/v1/rest/v1beta/properties/runReport).

Keep Enhanced measurement off initially, especially automatic search, form and outbound-link collection; the spec also requires the adapter's `send_page_view:false` and explicit safe page views. The dev off decision is already supplied and need not be requested again; record production's setting when authorized access exists. The source suppresses Signals/personalization and denies advertising consent, but that does not inspect account-level Ads links, user-provided-data collection or other settings. [Enhanced measurement controls and collected fields](https://support.google.com/analytics/answer/9216061?hl=en), [tag configuration](../../libs/website/adapters/analytics/src/browser.ts), [Google tag configuration](https://developers.google.com/tag-platform/gtagjs/configure).

Create the following **Event** scoped custom dimensions in Admin → Data display → Custom definitions → Custom dimensions → Create custom dimension. Use the display name and event parameter exactly as below; descriptions can use the bounded meaning column. Scope and parameter cannot be changed after saving. Editor or Administrator is required. Allow 24–48 hours after definition and collection for broader reporting. [Google instructions](https://support.google.com/analytics/answer/14239696?hl=en).

| Display name     | Event parameter   | Bounded meaning in public083                                                           |
| ---------------- | ----------------- | -------------------------------------------------------------------------------------- |
| PUNI page        | `page_id`         | Reviewed public page catalogue key                                                     |
| PUNI article     | `article_id`      | Only `a-clearer-first-step-for-software-requests` currently                            |
| Starting choice  | `starting_choice` | `launch`, `improve`, `similar`, `assistant`, `automate`, `unsure`, `typed`             |
| Entry point      | `entry_point`     | `hero`, `service`, `article`                                                           |
| Funnel version   | `funnel_version`  | `1`, `legacy`                                                                          |
| Scoping question | `question_id`     | Keys of the reviewed `scopingQuestions` catalogue                                      |
| Answer mode      | `answer_mode`     | `choice`, `text`, `mixed`, `unsure`; no answer contents                                |
| Turn bucket      | `turn_bucket`     | `1`, `2-3`, `4-6`, `7+`                                                                |
| Funnel route     | `route`           | `early`, `default`, `exhausted`, `manual` on review views; `manual` or `chat` on leads |
| Failure category | `category`        | `unavailable`, `limit`, `network`, `validation`, `conflict`                            |

These values and event membership come from the [event contract](../../libs/website/domain/contracts/src/analytics.ts) and [choice/question catalogue](../../libs/website/domain/contracts/src/scoping.ts). Ten definitions fit within the standard property's 50 event-scoped definitions, subject to existing account usage. No custom metrics or user-scoped definitions are needed. Use built-in campaign, device, hostname and page dimensions; never create receipt, client-ID or session-ID custom dimensions. Google's web reporting can interpret numeric-looking dimension strings as numbers, so verify how `1` displays without changing the contract. [Custom-definition limits and cardinality guidance](https://support.google.com/analytics/answer/14240153?hl=en).

Mark **existing code-generated `generate_lead`** as the initial key event. Under Admin → Data display → Events, star the existing event if collected. If absent, use Create event, name `generate_lead`, enable Mark as key event, choose **Create with code**, counting **Once per event**, and no default monetary value. Do not create a page-view/form-derived duplicate. Marking applies forward, not retroactively; standard reporting may take up to 24 hours. Google lists Marketer as sufficient generally and for the new-event path, but the same help page's existing-event star note says Editor. Use an Editor for this combined setup and verify the actual UI rather than promising a Marketer-only workflow. [Marking instructions](https://support.google.com/analytics/answer/13128484?hl=en), [Create with code](https://support.google.com/analytics/answer/12844695?hl=en).

The equivalent proposed Admin API body is `{"eventName":"generate_lead","countingMethod":"ONCE_PER_EVENT"}`, omitting optional `defaultValue`, at `POST https://analyticsadmin.googleapis.com/v1beta/properties/PROPERTY_ID/keyEvents`. List current key events first to avoid a duplicate configuration. The endpoint requires `https://www.googleapis.com/auth/analytics.edit`; this is account configuration, not event collection or receipt deduplication. [Create endpoint](https://developers.google.com/analytics/devguides/config/admin/v1/rest/v1beta/properties.keyEvents/create), [KeyEvent schema and methods](https://developers.google.com/analytics/devguides/config/admin/v1/rest/v1beta/properties.keyEvents).

## Three small analyses to configure

Use the last 28 days, or the available shorter history, the verified property timezone, and the environment filters above. Suggested standard API names are below; the names are case sensitive. Validate actual combinations before implementation. [GA4 Data API schema](https://developers.google.com/analytics/devguides/reporting/data/v1/api-schema).

| Purpose                            | Dimensions / metrics                                                                                                                                             |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Acquisition                        | `sessionDefaultChannelGroup`, `sessionSourceMedium`, `sessionCampaignName`, `landingPage`; `sessions`, `engagedSessions`, `engagementRate`                       |
| New-user acquisition, separate tab | `firstUserDefaultChannelGroup`, `firstUserSourceMedium`, `firstUserCampaignName`; `newUsers`                                                                     |
| Content / diagnostics              | `eventName`, `hostName`, `streamId`, `deviceCategory`, `pagePath`, `pageTitle`; `screenPageViews`, `eventCount`, `totalUsers`, `activeUsers`                     |
| Lead reporting                     | `keyEvents`, `sessionKeyEventRate:generate_lead`, `userKeyEventRate:generate_lead`; event attribution uses `defaultChannelGroup`, `sourceMedium`, `campaignName` |

Units matter: `eventCount` counts occurrences; Views includes repeat page views; `totalUsers` counts distinct measured users with events, while `activeUsers` is the active-user metric; sessions count visits begun. Lead-specific rates count sessions/users with a lead, not events divided by sessions. Generic `sessionKeyEventRate` includes every configured key event. Registered custom dimensions use `customEvent:PARAMETER`, for example `customEvent:starting_choice`; property metadata must confirm availability. These are schema facts, not proof that this property has populated them. [API schema](https://developers.google.com/analytics/devguides/reporting/data/v1/api-schema), [property metadata](https://developers.google.com/analytics/devguides/reporting/data/v1/rest/v1beta/properties/getMetadata).

**PUNI acquisition.** Start from Traffic acquisition and save a new detail report. Default dimension Session default channel group; allow Session source / medium, Session campaign and Landing page; show Sessions, Engaged sessions, Engagement rate, Key events selected specifically to `generate_lead`, and the corresponding session key-event rate where available. Use Device category comparisons. Keep the first-user tab separate: it answers initial discovery, while session dimensions answer visit acquisition. Unprefixed source/medium/campaign assign key-event credit under property attribution settings; they are not interchangeable with session acquisition. [Traffic-source scopes](https://support.google.com/analytics/answer/11080067?hl=en), [saving detail report changes](https://support.google.com/analytics/answer/10445879?hl=en).

For an API version, query acquisition denominators without `eventName=generate_lead`; query lead `keyEvents` with that event filter separately, using identical period/environment/acquisition grouping. Filtering the whole denominator report to lead events would hide non-converting sessions. Alternatively request the metadata-confirmed lead-specific rate directly. Report counts and missing rows honestly; do not turn missing configuration or an unavailable query into zero leads. [Report filter contract](https://developers.google.com/analytics/devguides/reporting/data/v1/rest/v1beta/properties/runReport), [metadata discovery](https://developers.google.com/analytics/devguides/reporting/data/v1/rest/v1beta/properties/getMetadata).

**PUNI request journeys.** In Explore → Funnel exploration, create these tabs with **indirectly followed** steps. Begin with Device category as breakdown, then duplicate with Session default channel group and Starting choice as separate breakdowns. Open entry admits later consent; it does not make intermediate steps optional. Funnel counts describe measured users/sequences, not stored request totals. [Funnel setup and sequencing](https://support.google.com/analytics/answer/9327974?hl=en).

| Tab                            | Steps and conditions                                                                                                                        | Scope of interpretation                                                              |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Site entry and handoff, closed | Site `page_view` → site `funnel_start` → app `page_view` with `page_id=build` OR `page_id=manual`                                           | Landing → accepted intake → measured app continuation, from any registered site page |
| Start to confirmation, closed  | `funnel_start` → `email_request_view` → `generate_lead`                                                                                     | Short overall path; no mandatory question, answer or brief                           |
| Contact confirmation, open     | `email_request_view` → `generate_lead`                                                                                                      | Broad contact-to-confirmation sequence, including late entry                         |
| Chat contact, open             | `email_request_view` with `route` in `early/default/exhausted` → `generate_lead` with `route=chat`                                          | Chat review variants without demanding a question or brief                           |
| Manual, open                   | `email_request_view` with `route=manual` → `generate_lead` with `route=manual`                                                              | Manual path                                                                          |
| Question-led chat, closed      | `conversation_start` → `scoping_question_view` → `scoping_answer` → `brief_view` → `email_request_view` → `generate_lead` with `route=chat` | Diagnostic subset only; shortcuts and direct contact are valid outside it            |

For **Site entry and handoff**, set step 1 to Event name exactly `page_view` **AND** Hostname exactly `dev.puni.dev`; step 2 to Event name exactly `funnel_start` **AND** the same site hostname; step 3 to Event name exactly `page_view` **AND** Hostname exactly `dev.app.puni.dev` **AND** (PUNI page exactly `build` **OR** PUNI page exactly `manual`). For production substitute its host pair only after authorized activation. The registered site-page resolver admits home, service and published-content entry without a Home-only condition; the app identities resolve to canonical `/` and `/manual`. Keep both hosts in the exploration-wide environment filter: apply the site/app distinction within each step. GA supports event/dimension conditions combined with AND/OR; the API equivalent combines `funnelEventFilter` and `funnelFieldFilter` through `andGroup`/`orGroup`, with the bounded `page_id` condition as an event parameter filter. [Catalogue/resolver](../../libs/website/adapters/analytics/src/configuration.ts), [supported funnel filters](https://developers.google.com/analytics/devguides/reporting/data/v1/funnels), [filter schema](https://developers.google.com/analytics/devguides/reporting/data/v1/rest/v1alpha/properties/runFunnelReport).

The local [native handoff proof](../../openspec/changes/website-funnel-analytics/verify.md#private-site-and-native-handoff--2026-10-26) observes `funnel_start` after accepted intake, so label that milestone **saved intake**, not a raw CTA click. The first gap includes non-starters and unsuccessful intake attempts; the next diagnoses absence of a measured app continuation after that start. A closed Start to confirmation tab then measures the shorter observed sequence through the email invitation and confirmed lead. Duplicate these two tabs as open funnels for late consent/direct app entry, show entry position, and keep their denominators separate from the closed site-entry cohort. Starting choice is absent on landing `page_view`, so use channel/device for the landing gap and inspect choice on the start/continuation views without filtering landing views away. These are sequenced measured-user diagnostics, not receipt joins or conversion rates inferred by dividing bare event totals; account ingestion and continuity still require the later proof below. [Event membership](../../libs/website/domain/contracts/src/analytics.ts).

The step names/route values are the [current contract](../../libs/website/domain/contracts/src/analytics.ts). For a choice-specific diagnostic, add `starting_choice=improve` to its `conversation_start` step and label the tab accordingly. Do not apply that as an event-wide filter: `scoping_answer` has no starting choice, and leads recovered without draft context may lack it. Keep unknown choice visible. Funnel breakdown uses the first applicable value; multiple requests or changing choices by one user cannot be joined precisely with the current anonymous bounded events. An open funnel also counts users entering at the lead step, so show entry position rather than calling every lead a conversion from a measured email view. [Breakdown/entry semantics](https://support.google.com/analytics/answer/9327974?hl=en), [recovery caller](../../apps/website/fe-01/src/main.tsx).

Save the exploration first. An Editor/Administrator may additionally Save as a report in the Library and add it to navigation. The report copies filters, steps, open/closed type and breakdown; later edits do not synchronize automatically with the source exploration. Record the source/version. [Saved funnel report behavior](https://support.google.com/analytics/answer/13012015?hl=en).

**PUNI offers and content.** Use a free-form exploration: an intent tab with Starting choice rows, Event name columns, Event count and Total users, limited to `funnel_start`, `conversation_start`, `email_request_view`, `generate_lead`; retain missing choice. A content tab uses Hostname + PUNI page/PUNI article, event names `page_view/services_view/article_view`, Event count/Total users and Device category. Inspect failures separately by category and question progression by question ID/answer mode. These recipes use only the [existing bounded events](../../libs/website/domain/contracts/src/analytics.ts); the public contract's `about_view` type does not establish a live About page, and it has no `/about` catalogue entry. Owner-written About/new articles need their own reviewed publication/catalogue work before reports promise coverage.

## Proposed campaign links, not registrations or launches

Use one hypothesis campaign name, `ai-app-review`, with distinct distribution sources. These three candidates satisfy the source parser. The first two are for owner-published, venue-appropriate organic posts; the paid candidate is conditional on owner approval, a defined market/budget and verified measurement. None is registered or approved to spend.

| Proposed source / medium / campaign     | Full example landing URL                                                             | Expected manual-tag channel |
| --------------------------------------- | ------------------------------------------------------------------------------------ | --------------------------- |
| `linkedin` / `social` / `ai-app-review` | <https://puni.dev/?utm_source=linkedin&utm_medium=social&utm_campaign=ai-app-review> | Organic Social              |
| `reddit` / `social` / `ai-app-review`   | <https://puni.dev/?utm_source=reddit&utm_medium=social&utm_campaign=ai-app-review>   | Organic Social              |
| `google` / `cpc` / `ai-app-review`      | <https://puni.dev/?utm_source=google&utm_medium=cpc&utm_campaign=ai-app-review>      | Paid Search, conditional    |

Google's manual rules map medium `social` to Organic Social and a recognized search source plus `cpc` to Paid Search. `organic` would imply Organic Search, so do not use it for social posts; custom media such as `founder-post` can become Unassigned. Channel rules can evolve; verify the processed result. [Default channel definitions](https://support.google.com/analytics/answer/9756891?hl=en). All three exact triples, and any variants, need reviewed source registration before promotion; lowercase/hyphens are required by PUNI even though Google's channel rules themselves are case insensitive. The [campaign parser/resolver](../../libs/website/adapters/analytics/src/configuration.ts) rejects uppercase, dots/underscores in registrations and incomplete/repeated/mismatched triples.

Link internally from a PUNI article to `/` or the appropriate service with no UTMs. Internal campaign tags can alter event attribution and misrepresent acquisition; GA4 does not necessarily start a new session when campaign values change. Use the existing `entry_point=article` milestone to distinguish article-led entry. Do not add visitor identifiers, keywords, email or free text to campaign values. [Campaign processing](https://support.google.com/analytics/answer/11242841?hl=en), [PII guidance](https://support.google.com/analytics/answer/6366371?hl=en), [event contract](../../libs/website/domain/contracts/src/analytics.ts).

A manual `google/cpc` tuple is not verified Google Ads account linking, auto-tagging, cost import, conversion bidding or click-ID continuity. The adapter emits canonical URLs and neutralizes unapproved campaign fields; the retained fixture covers a bounded manual tuple, not Ads integration. Do not assume a normal raw-URL/`gclid` workflow survives this privacy boundary or claim spend/ROAS from these events. A paid test needs its own approved account/transport proof and external spend ledger. [Adapter configuration](../../libs/website/adapters/analytics/src/browser.ts), [campaign/Ads processing](https://support.google.com/analytics/answer/11242841?hl=en).

## Verification that remains necessary

The current [verification record](../../openspec/changes/website-funnel-analytics/verify.md#private-site-and-native-handoff--2026-10-26) documents a capture-fixture incident: page/Playwright/CDP observers missed an immediate-navigation event that the owned TLS collector received. Observer absence therefore does not prove event loss. Conversely, one intercepted request or local enqueue is not a complete wire audit or proof Google ingested it. Preserve the existing navigation behavior unless independent evidence identifies a product defect.

For the next authorized dev proof, use an isolated browser and one reviewed registered tuple on `dev.puni.dev`, accept analytics before starting, submit through the real intake POST/303/app path, then complete a synthetic request. Check the expected dev measurement destination, matching client/session IDs across both hosts, and exactly one bounded confirmed-lead event in the controlled case; keep those Google identifiers only in restricted verification evidence, never in custom parameters. Repeat denial, delayed acceptance, withdrawal/reacceptance, blocking, rejection, duplicate action and lost-response recovery. Existing tests demonstrate the intended local boundaries; they do not certify a newly deployed/account-connected run. [Controller tests](../../libs/website/adapters/analytics/src/analytics.test.ts), [domain-cookie/browser tests](../../libs/website/adapters/analytics/src/browser.test.ts), [app interception runner](../../apps/website/fe-01/browser/analytics.mjs).

Audit decoded request URL/body/headers with distinct synthetic description, answer, reference, email, claim/CSRF, receipt, query/hash and referrer-path sentinels. Only canonical public location/title, origin-only HTTP(S) referrer, registered triple and bounded event fields may enter measurement. Do not place secrets or tokens in test URLs to Google. Use the contained local official-runtime/owned TLS receiver proof for destructive sentinel/fault cases, with receiver controls and independent containment, then a separate authorized clean live-account run. Google explicitly warns about PII in URLs, titles, user input and campaign fields. [Source boundary](../../libs/website/domain/contracts/src/analytics.ts), [historical transport proof](../../openspec/changes/website-funnel-analytics/verify.md#private-site-and-native-handoff--2026-10-26), [Google PII guidance](https://support.google.com/analytics/answer/6366371?hl=en).

DebugView/Realtime have limited attribution; verify the registered campaign, host continuity and absence of self-referral in processed Acquisition reports, then the custom definitions/saved analyses after processing. ## Coverage limits and later commercial outcomes

The current basic-consent design loads no Google tag before acceptance and drops denied/loading interactions. Ad blockers, loader/storage failures, delayed acceptance and withdrawal create an incomplete measured cohort. Withdrawal clears environment analytics cookies and local lead markers; reacceptance can begin a fresh Google identity, so continuity and unique-user counts across it cannot be promised. The page-owned observer prevents late-consent replay of old actions; it does not provide a cross-browser, lifetime lead deduplication ledger. Functional requests stay independent of analytics. [Basic consent mode](https://developers.google.com/tag-platform/security/guides/consent?consentmode=basic), [controller](../../libs/website/adapters/analytics/src/analytics.ts), [cookie cleanup](../../libs/website/adapters/analytics/src/browser.ts), [milestones](../../apps/website/fe-01/src/analytics-flow.tsx).
