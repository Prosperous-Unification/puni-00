# OpenRouter research for a software-services scoping funnel

Checked 2026-09-27. Sources are OpenRouter's current official documentation or its official documentation repository. This is design research, not a tested integration.

This note preserves the source-linked provider findings gathered for this change. The current product contract is in `openspec/changes/puni-website-funnel/`: anonymous manual proposal submission launches before prospect sign-in and chat; operators still sign in to review requests. The approved retention period for description, chat and one contact email is 12 months unless the prospect becomes a client; anonymous claims expire after 24 hours. Provider-as-processor wording remains a chat launch gate. OpenRouter pricing and endpoint compatibility must be checked again before enabling paid calls. None of the USD allowances below authorizes live spend.

## Recommended flow (application design)

1. Accept an anonymous prompt into a short-lived, server-side draft with length and rate limits. Permit a browser-claim-scoped manual brief and proposal submission without prospect sign-in; **do not call the model before sign-in** (superseded for Build by the [anonymous conversation](../../openspec/changes/build-ai-chat-harness/design.md), which admits paid calls on the browser claim under its allowance). If the visitor chooses AI, attach the draft to the authenticated account and ask the user to send it. Treat login return and draft ownership as application duties.
2. Run the scoping chat through an authenticated backend endpoint. Keep the OpenRouter inference key only on the server. The [Chat Completions API](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request) uses a bearer key; OpenRouter's [key-creation API](https://openrouter.ai/docs/api/api-reference/api-keys/create-keys) says plaintext is returned only at creation. Use a dedicated key and rotate it if exposed.
3. Persist user turns and a versioned brief owned by that account; request an explicit review/submit action before human contact. This persistence, authorization, retention policy, contact workflow, and consent are application requirements, not OpenRouter features.

## Provider features and limits

- OpenRouter [API keys](https://openrouter.ai/docs/api/api-reference/api-keys/create-keys) support an optional USD `limit` and daily/weekly/monthly resets. [Guardrails](https://openrouter.ai/docs/guides/features/guardrails/overview) offer per-key/member budgets, model and provider allowlists, ZDR, input content filters, and sensitive-info rules; requests are rejected when a limit is reached. Their docs describe checks on each request, **not** a guarantee that overlapping in-flight requests or a single call cannot exceed an exact dollar threshold. [In-flight spending budget docs](https://github.com/OpenRouterTeam/docs/blob/main/api_reference/limits.mdx) describe a separate balance-based reservation mechanism that applies only to some prepaid accounts and excludes some cost types. Do not use it as this product's quota.
- [Provider routing](https://github.com/OpenRouterTeam/docs/blob/main/guides/routing/provider-selection.mdx) supports `only`, `order`, `allow_fallbacks`, `max_price`, `zdr`, and `data_collection: "deny"`. `max_price` filters endpoint **rates**, not total request cost. Set a backend model allowlist and OpenRouter guardrail allowlist; do not accept model/provider choices from browser input. Avoid automatic model fallback unless every fallback is vetted for price, quality, and privacy. `require_parameters: true` can restrict endpoints to ones supporting requested parameters.
- [Privacy controls](https://openrouter.ai/docs/guides/get-started/sovereign-ai) allow ZDR and denying provider data collection. OpenRouter says [ZDR applies to provider-side retention](https://openrouter.ai/blog/insights/zero-data-retention/), while requests still reach the provider and application logs/tools remain separate. Confirm the chosen model has an eligible endpoint. EU in-region routing is an enterprise feature, so do not assume residency from ZDR alone.
- [Chat Completions](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request) accepts `max_completion_tokens`; `max_tokens` is deprecated. Cap input size and history in the app too. The endpoint can return errors such as 402, 403, 429, and 5xx; map expected ones to usable UI states.
- OpenRouter's [tool-calling docs](https://openrouter.ai/docs/guides/features/tool-calling) say the model only proposes user-defined tool calls; the application executes them. For scoping, omit tools and OpenRouter server tools in the first release. If later added, use an explicit allowlist, schema validation, per-tool authorization, and bounded calls. OpenRouter [guardrails](https://openrouter.ai/docs/guides/features/guardrails/overview) scan incoming requests, while [sensitive-info checks](https://openrouter.ai/docs/guides/features/guardrails/sensitive-info/) do not scan model responses. Validate generated brief fields and output before persistence or display.

## Budget and usage algorithm (application requirement)

- Atomically reserve one active turn and its worst-case input/output token allowance **before** sending; enforce per-user and site-wide active-call counts, turn counts, prompt bytes/tokens, history length, completion cap, and a server timeout. Prevent duplicate submissions with a request ID. Release or reconcile the reservation when the call settles. Avoid retrying after an ambiguous error without reconciliation.
- OpenRouter [usage accounting](https://github.com/OpenRouterTeam/docs/blob/main/cookbook/administration/usage-accounting.mdx) says token and cost usage is automatic in the complete response or **last** SSE event; `usage: {include:true}` and `stream_options: {include_usage:true}` are deprecated no-ops. The [streaming guide](https://github.com/OpenRouterTeam/docs/blob/main/api_reference/streaming.mdx) says pre-stream errors are JSON, mid-stream errors are SSE events, comments can appear, and `X-Generation-Id` is in the response header. Parse both errors, keep the generation ID, and do not mark the turn complete merely because text arrived.
- On cancellation, disconnect, missing final usage, or mid-stream failure, mark usage **unsettled** and retain the reservation until reconciliation. Fetch [generation metadata](https://openrouter.ai/docs/api/api-reference/generations/get-generation) by ID for `total_cost`, tokens, and `cancelled`; retry reconciliation with a bound and surface unresolved accounting to operations. The docs do not establish when a cancelled generation becomes queryable or whether every failed pre-header request has a generation ID. Keep an operational hold/fail-closed admission policy for those cases until tested.

## Interactive prototype boundary (application design)

If the chat can generate a cute interactive prototype, initially ask for a constrained JSON scene/component tree from a server-owned schema, then render it through a fixed library of safe React components. Do not execute generated JS/HTML/CSS, fetch arbitrary URLs, or grant network/storage access. If free-form code is ever required, serve it from a separate origin in a sandboxed iframe with restrictive CSP, no same-origin permission, no cookies, and message validation. Human review precedes anything shared with a prospect. This is application isolation; OpenRouter has no documented sandbox for arbitrary generated UI code.

## Provisional defaults to validate (assumptions, not provider guarantees)

- One inexpensive, explicitly pinned text model plus one vetted provider endpoint; ZDR and data-collection denial if the chosen endpoint supports both. Recheck availability and current price at launch.
- 2,000 characters for anonymous draft, 4,000 for a later turn, 12 user turns per brief including the original text, 1 active model call per account, 4 site-wide calls, 2 active briefs per account, 1,024 completion tokens per chat turn, 30-second server timeout, and no automatic model/tool loops. The proposed local reservations are $0.50 per brief including preview, $1 per account per UTC day and $10 site-wide per UTC day, with a $100 monthly dedicated-key ceiling. These remain provisional until current prices and an operator-approved loss budget are confirmed.
- Persist only the turns and brief needed for follow-up, with clear consent, deletion/retention policy, and restricted staff access. Start with no response caching, prompt logging, broadcast, external tools, or generated-code execution.

## Hard uncertainties to settle by test or contract

1. Exact overspend behavior for simultaneous requests at the key/guardrail boundary and how a single request crossing the threshold is charged. Docs only say subsequent requests are rejected once a limit is reached.
2. Generation lookup latency and cost accounting after client/server abort and before response headers. Instrument and fault-test these paths before promising an exact per-user dollar cap.
3. Whether a chosen model/provider satisfies ZDR, data-collection denial, required parameters, latency, and price together at launch; model catalogs and endpoints change.
