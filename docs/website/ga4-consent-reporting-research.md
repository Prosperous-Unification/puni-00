# GA4 measurement, consent and lead emails

Research checked against primary Google documentation on **2026-10-30**. This is a recommendation, not activation or evidence from the PUNI Analytics accounts. No account, tag, runtime, production setting or private companion was changed.

## Decision for a new site

Keep GA4 as the owner's analytics destination. However, **complete measurement of every visitor's funnel in GA4, at low volume, while respecting a refusal of analytics identifiers is not a capability established by Google's documentation**. Always loading the Google tag can improve collection coverage; it does not guarantee report coverage. This conclusion follows from the eligibility and identity limitations below, rather than a blanket claim that Google must never receive anything before consent.

The supplied project context is that the current implementation blocks Google until analytics consent, dev uses `G-R0JM3R4SSV`, and production `G-69BBG6ZLB3` remains held. These facts were supplied for this research and were not independently rechecked here.

Recommended next design: advanced consent mode for supported cookieless collection, ordinary GA4 measurement after permission, explicit funnel events, and a durable server-confirmed lead event for the authorized measurement population. Keep the actual submitted email in the existing request inbox. Treat incomplete coverage honestly; do not promise that switching modes makes denied traffic appear in low-volume GA4 reports.

## Why the current consent gate exists

Google documents two implementations. **Basic** blocks Google tags before permission and sends nothing for visitors who refuse. **Advanced** loads tags on arrival, sets consent states before collection, sends cookieless measurements while storage consent is denied, and changes behavior after the visitor's choice. Consequently, the current complete block is an implementation choice, not the only supported GA4 configuration. Google distinguishes analytics storage from advertising storage, advertising user data and advertising personalization; those purposes should not be conflated. [Google: Consent mode overview](https://developers.google.com/tag-platform/security/concepts/consent-mode).

Denied analytics storage means no reading or writing first-party Analytics cookies. Cookieless events still communicate coarse information and can include ordinary HTTP/browser information. Explicitly supplied `user_id` and custom dimensions can still be sent: a denied flag does not automatically sanitize application payloads. [Google: Consent mode on websites and mobile apps](https://support.google.com/analytics/answer/9976101).

Changing this design requires an accurate notice and a decision about what the site is authorized to send. Google's Measurement Protocol policy requires proper notice and consent or an opportunity to opt out. This research does not establish a jurisdiction-specific legal exemption, and switching to server transport does not remove Google's policy. [Google: Measurement Protocol, SDK and User ID policy](https://developers.google.com/analytics/devguides/collection/protocol/ga4/policy).

## What low-volume GA4 reports can show

Google says declined events are not reported when insufficient consented traffic prevents modeling. Behavioral-modeling prerequisites include advanced consent mode on all pages, at least **1,000 denied events/day for seven days**, and **1,000 consented daily users on seven of the preceding 28 days**. Meeting these thresholds still does not guarantee eligibility.

Blended reporting identity exposes eligible modeling; changing identity does not change collection. Standard-report event counts are not themselves modeled, but enabling modeling makes denied events reportable. Therefore, “raw counts are not modeled” does not establish a low-traffic exception.

Google describes different treatment in path/funnel explorations and banners warning that most exploration templates exclude estimated users; sequence segments and User explorer do not support behavioral modeling. Use each report's quality indicator and supported technique, rather than assuming every funnel includes denied visitors. [Google: Behavioral modeling for consent mode](https://support.google.com/analytics/answer/11161109).

Realtime is a diagnostic view with limited attribution and best-effort delivery; it is not evidence that standard reports will include every collected event. Google's DebugView documentation explicitly excludes events when Analytics-cookie consent has not been given. For denied-state testing, inspect consent order and tag behavior with Tag Assistant; do not change the visitor's refusal merely to make a debug screen populate. [Google: Realtime report](https://support.google.com/analytics/answer/9271392), [Google: DebugView](https://support.google.com/analytics/answer/7201382), [Google: Consent debugging](https://developers.google.com/tag-platform/security/guides/consent-debugging).

## Documented cookieless options and their limits

GA4 documents a configurable `client_id`, normally stored in its first-party cookie. An override does not document a way to disable cookie storage. `cookie_domain: 'none'` still sets a cookie without a domain attribute; `cookie_expires: 0` creates a session cookie. Neither is “no cookies.” The GA4 configuration reference does not establish Universal Analytics' `storage: 'none'` as a GA4 configuration option. Do not propose that legacy switch as a supported solution. [Google: GA4 configuration](https://developers.google.com/analytics/devguides/collection/ga4/reference/config).

The documented consent-mode solution uses a random number generated on each page load among its coarse signals. It does not provide persistent browser continuity for a complete observed journey. Inventing a fresh client ID for each event would change what “users” means; using one ID for all visitors would merge unrelated people. Neither supplies an honest all-visitor funnel. [Google: Consent mode overview](https://developers.google.com/tag-platform/security/concepts/consent-mode). The preceding metric consequences are an inference from the documented browser-instance role of `client_id`, not a tested PUNI implementation.

Google's Measurement Protocol changelog recommends non-cookie **values** for client and session IDs while explaining that complete cookie strings are also accepted. The sending guide recommends retrieving the actual website tag's client ID. This is not documentation of a separate consent-free anonymous reporting mode. [Google: Measurement Protocol changelog](https://developers.google.com/analytics/devguides/collection/protocol/ga4/changelog), [Google: Sending events](https://developers.google.com/analytics/devguides/collection/protocol/ga4/sending-events).

## Server-confirmed conversions in GA4

Measurement Protocol can send server events directly to GA4 reports. Google positions it as a supplement to tagging; a fully server-only setup may have only partial reporting. It joins online activity through client identity. It therefore improves delivery of a real saved conversion but cannot reconstruct earlier denied visitor activity. [Google: Measurement Protocol overview](https://developers.google.com/analytics/devguides/collection/protocol/ga4).

For PUNI, a sensible proposed event is `generate_lead` after a request has actually been saved, using the real authorized browser identity. Choose one emitter for that conversion and persist delivery state so a browser success callback, retries and the server do not each count another lead. Do not send a button click as proof of a saved request or export an aggregate batch disguised as individual users. `generate_lead` is Google's recommended lead event; the save boundary and delivery bookkeeping are proposed application behavior, not a claim of generic GA4 deduplication. [Google: Recommended events](https://developers.google.com/analytics/devguides/collection/ga4/reference/events#generate_lead).

Protocol requirements include the web stream's measurement ID, private API secret and required `client_id`. Its documented consent object exposes `ad_user_data` and `ad_personalization`, with inheritance from corresponding online interactions when omitted; it does not expose `analytics_storage`. Enforce the permitted analytics population before sending. Requests allow up to 25 events, payloads below 130 kB and event backdating up to 72 hours. A `2xx` means receipt, not successful processing. [Google: Measurement Protocol reference](https://developers.google.com/analytics/devguides/collection/protocol/ga4/reference?client_type=gtag).

For session attribution, provide the real `session_id`, send within 24 hours of session start and place the event timestamp within that session. Engagement time must reflect actual elapsed engagement; do not invent engagement to populate Realtime. [Google: Measurement Protocol use cases](https://developers.google.com/analytics/devguides/collection/protocol/ga4/use-cases).

The API secret must be created in the relevant stream and kept on the server. This needs a property owner/editor with settings access and a new server secret; it does not require a service account or browser-exposed credential. The sending guide documents creation and explicitly warns against exposing the secret. Property Editors control property settings. [Google: Sending events](https://developers.google.com/analytics/devguides/collection/protocol/ga4/sending-events), [Google: Access roles](https://support.google.com/analytics/answer/9305587).

Standard Google Analytics is offered free of charge. A direct protocol integration can use the existing backend; its engineering, outbound delivery and monitoring costs remain application costs, unestimated here. A separate server-side Tag Manager deployment is unnecessary for this proposed save event. Google's Cloud Run guide estimates approximately **USD 45/month per instance** for its specified configuration and recommends at least two instances; that optional infrastructure is not a free consent workaround. [Google: Analytics](https://marketingplatform.google.com/about/analytics/), [Google: Server-side tagging Cloud Run setup](https://developers.google.com/tag-platform/tag-manager/server-side/cloud-run-setup-guide?provisioning=manual).

## Email addresses: three different requests

1. **“I need the prospect's email so I can reply.”** Ask for it and retain the submitted address with the request in the existing inbox. GA4's restriction on sending email to Analytics does not prohibit collecting a contact address in the site's own intake. The supplied project context says the final submission already does this; this research did not audit that implementation. No new CRM or alternative analytics dashboard is proposed.
2. **“Can GA4 tell me the Gmail address of someone who merely visited?”** No supported feature reviewed here provides that contact identity. Google signals exposes aggregate reporting, never individual Google-user information; User explorer uses a supplied User-ID or browser/device ID. A visitor being signed into Google does not give the site their Google-account email. [Google: Google signals](https://support.google.com/analytics/answer/9445345), [Google: User explorer](https://support.google.com/analytics/answer/9283607).
3. **“Can I use an email I already collected to improve GA4 conversion measurement?”** There is a dedicated user-provided-data feature, described below. It is not an email-contact report.

Raw email must not appear in ordinary event parameters, custom dimensions, URLs, titles, campaign parameters or User-ID. Filter free text and contact fields at the analytics boundary. Hashing an email and assigning it to an arbitrary custom dimension is not the documented exception. [Google: Avoiding personally identifiable information](https://support.google.com/analytics/answer/6366371).

User-provided data collection is currently **open beta**. Its setup page requires a linked Google Ads account and Editor-or-higher access, excludes Health-category properties and makes feature-policy acknowledgement permanent, although processing can subsequently be disabled. It accepts consented first-party identifiers through its supported fields; with Measurement Protocol, hash before transmission using SHA256. Improvements may take up to a month. Actual account eligibility and Ads linkage were not checked. [Google: User-provided data collection](https://support.google.com/analytics/answer/14077171).

The special policy permits identifying fields only through this feature, requires SHA256 and consent for collection, passing, use and relevant session association. Consent for this purpose is independent of the cookie-storage choices. Hashing enables matching; it is not a reason to call email anonymous or to assume an intake contact address grants advertising permission. [Google: User-provided-data policy](https://support.google.com/analytics/answer/12150158).

Enhanced conversions matches identifiers already supplied by the site with consented Google users and reports **aggregated conversions**. It does not reveal visitors' emails or return a contact list. Consequently, enabling it does not solve “I need emails to contact my leads”; the request inbox already serves that purpose. Recommendation: consider this feature later for a concrete attribution or Ads need, with the owner's explicit feature-policy decision, rather than silently activating it as a prerequisite for basic analytics. [Google: Enhanced conversions](https://support.google.com/analytics/answer/14252663).

## Acceptance evidence before any rollout

The next implementation should prove events for landing, meaningful engagement, starting the questionnaire/conversation, reaching contact, attempted submission and confirmed saved lead, with names and conversion boundaries agreed before coding. The owner should be able to inspect those events and the consented funnel in GA4 itself. This is proposed scope; event coverage was not audited here.

Validate denied/default/granted/withdrawn tag behavior, absence of contact text in payloads, failed-save exclusion, retry behavior and development/production separation. For Measurement Protocol, validate malformed payload negatives using Google's validation endpoint, then verify a real event in the development GA4 property. Validation-only requests never enter reports and do not validate the API secret, so neither validation nor an HTTP success proves visible reporting. [Google: Validate events](https://developers.google.com/analytics/devguides/collection/protocol/ga4/validating-events).

Real blockers are the low-volume reporting threshold, missing observed identity for denied journeys, any absent GA4 settings/secret access, and the owner's unresolved policy/notice decision for changed collection. None can be repaired by renaming analytics “necessary,” relabeling a refusal as granted, fabricating users or claiming anonymous hashing. No Google account inspection, network-payload experiment, live reporting validation, production activation or code/gate verification was performed during this research.
