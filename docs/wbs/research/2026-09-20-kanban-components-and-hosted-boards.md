### Shortlist

**dnd-kit (`@dnd-kit/core` + `@dnd-kit/sortable`) and `@hello-pangea/dnd`.**

- **dnd-kit** is the only headless engine with both a documented keyboard sensor and a
  copy-in board block already built against it (Kibo UI), already tracking React 19 in its own
  workspace — the cheapest path to "vendor a block, drive it from a contract," what F3 wants.
- **`@hello-pangea/dnd`** is the only candidate whose own docs state a concrete large-list
  number ("10,000 items @ 60fps") and claim keyboard, screen reader and touch support as one
  cohesive documented experience rather than three opt-in pieces. It wraps your markup instead
  of being fully headless, costing layout flexibility but buying a documented a11y story.

Pragmatic drag-and-drop is the fallback if bundle size matters most — smallest by a wide
margin, but its guidelines steer away from arrow-key dragging toward an action menu, meaning
more component work. react-aria is the fallback if built-in virtualization matters most, since
it is the only candidate with a documented `<Virtualizer>`, but the full component package
costs far more bundle weight than the others if drag-and-drop is the only reason to add it.

## Part 2 — how hosted trackers embed a board and authenticate it (K5)

This is comparison only, per the plan: the point is what "don't build the view" costs
elsewhere, not a candidate for the WBS's backend.

| Tracker                 | Embeddable board view                                                                                                                                                                                                                                                                                                                                                                                                              | Auth model for API / embedding                                                                                                                                                                            | What a host app would have to build                                                                                                                                    |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GitHub Projects (v2)    | None found; API docs for "using the API to manage projects" say nothing about an iframe, widget, or embed path.                                                                                                                                                                                                                                                                                                                    | GraphQL API only: a classic PAT or a GitHub App installation token, `read:project` for queries, `project` for mutations. `gh auth login --scopes "project"` is the CLI path.                              | The entire board UI from GraphQL data — read/write API access, not a view.                                                                                             |
| Gitea                   | No embeddable/public view documented. Project boards are a per-repository unit (`repo.projects`), issues and pull requests only, no standalone cards.                                                                                                                                                                                                                                                                              | REST API (`POST /repos/{owner}/{repo}/projects` etc.) accepts Basic auth, an access token, or an Authorization header token, per its own OpenAPI page.                                                    | The board UI from the REST API; no sharing/embed primitive to lean on.                                                                                                 |
| Forgejo                 | Same shape as Gitea: "A project is a kanban board to organize issues," with card-preview options. No embed, public link, or auth detail on the project docs page.                                                                                                                                                                                                                                                                  | Not stated there; inherits Gitea's token-based API auth, unverified for Forgejo's own reference.                                                                                                          | Same as Gitea: build the view against the API; no embed story documented.                                                                                              |
| Vikunja                 | Yes — link shares: "Link shares create a URL that gives access to a project without requiring a Vikunja account," with an optional password and Read / Read & Write / Admin tiers. No iframe statement found.                                                                                                                                                                                                                      | Link shares are anonymous-viewable, optionally password-gated; the general API uses its own token scheme (undetailed here). Whether a shared link preserves a specific view (e.g. kanban) is unconfirmed. | For read access to one project: point an iframe or fetch at the link-share URL. Write access or multi-project aggregation still needs the authenticated API.           |
| Plane (self-hosted)     | None found. API docs describe five view layouts (List, Board, Spreadsheet, Gantt, Calendar) but never mention embedding, a public link, or a widget.                                                                                                                                                                                                                                                                               | REST API: `X-API-Key` header from a personal access token, or OAuth `Authorization: Bearer`, scoped to granted permissions.                                                                               | The entire board UI from the API; no embed or public-link primitive documented.                                                                                        |
| Focalboard (standalone) | The standalone repo's own README states: **"This repository is currently not maintained."** Its function lives on in `mattermost/mattermost-plugin-boards`, requiring a Mattermost server, itself called "maintenance mode" in Mattermost's docs. That plugin does have public sharing: a board admin publishes a **read-only link**, disabled by default, enabled per-instance, regenerable to revoke. No iframe statement found. | The public link is anonymous-viewable once an admin enables and shares it; ordinary access uses Mattermost's session auth.                                                                                | Nothing for read-only display of one board once public sharing is enabled — but it needs a Mattermost server, not standalone Focalboard, which is itself unmaintained. |

The clearest cross-tool pattern: only Vikunja and the Mattermost Boards plugin document an
anonymous, revocable read-only link — the shape closest to "embed a board." Every git-forge
board and Plane require building the whole view against an authenticated API; none publishes
an embed primitive. This mirrors `docs/superpowers/plans/2026-09-20-wbs-backlog-md-kanban-research.md`'s
Backlog.md findings: no documented embedding story, an unauthenticated local-only server, a
hard-coded `/api` base path that breaks any reverse-proxy mount.

## What this leaves open

- **E3** (vendor one candidate board block into a scratch app, driven only by a props
  contract) has to show whether Kibo UI's kanban block — or a `@hello-pangea/dnd`-driven
  equivalent built by hand, since hello-pangea has no ready-made block — can actually be
  stripped of its internal state and Backlog.md coupling and driven purely from outside data,
  which is what F3 and K3 both assume is cheap. This note only confirms the sensors are wired
  in; it does not confirm the component renders correctly from an external contract.
- **E4** (keyboard-only drag between columns, with an observable assistive-technology
  announcement) has to show which of dnd-kit's documented `KeyboardSensor` or
  `@hello-pangea/dnd`'s documented keyboard support actually produces a working, announced
  move in a real browser — every claim in Part 1's keyboard and screen-reader columns is a
  documentation claim, not an observed behaviour.
- Neither part answers whether a card should be a work item or a slice, what a column is
  before per-step status exists, or how a drag becomes one broker-published planning command —
  those are the plan's open research questions 1–4 and are unaffected by which engine is
  chosen.
- Part 2 answers "what does a hosted board's auth cost," not whether the WBS should ever call
  out to one; the plan's option (d) already treats this as comparison only.
