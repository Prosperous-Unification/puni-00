# Runbook: `dagger-engine` losing DNS for `registry` after a restart

**Applies to:** h2puni, and any host set up the same way as of Task 5 of the 2026-08-02 compose
blue/green deploy.

> **Status (2026-08-02): no longer needed for publishing.** The registry's loopback host port was
> retired and builds now push to `registry.infra.bulletpoints.club`, a public name resolved by
> ordinary public DNS and reached over TLS through Caddy, so publishing no longer depends on
> `dagger-engine` resolving the container-DNS name `registry`. Verified after a full
> `systemctl restart docker`, which reverts the engine's `/etc/resolv.conf` to dagger's own
> resolver as described below: `getent hosts registry` failed (exit 2) while
> `getent hosts registry.infra.bulletpoints.club` returned `62.238.48.248`, and
> `nx run tool-dagger:publish-all` then built and pushed all three tiers with no remediation.
> Container-to-host-public-IP hairpin was confirmed separately
> (`curl https://registry.infra…/v2/` from a throwaway container returned the registry's own 401).
> The rest of this document applies to anything else that needs the engine to reach `wbs-net` by
> container name.

> **Managed release engine, 2026-08-27:** current publishes use the separately named
> `wbs-dagger-engine`, created and validated by `bin/publish-release.sh`. It pushes through the
> registry's public TLS name, is not attached to `wbs-net`, and is deliberately stopped after every
> outcome. The remediation below applies only to the historical `dagger-engine` container. Do not
> apply it to `wbs-dagger-engine` or start either historical engine for a release.

## Symptom

`bunx nx run tool-dagger:publish-all` (or any Dagger build that pushes to `registry:5000`) fails
to resolve `registry`, or, if a stale `/etc/hosts` workaround was in place, pushes to the wrong IP
after the `registry` container has been recreated.

## Root cause

`dagger-engine` runs its own CNI/dnsmasq setup for its build sandboxes, which rewrites
`/etc/resolv.conf` inside the container early in its startup (`nameserver 10.87.0.1`, dagger's own
resolver, not Docker's). This happens **before** Docker adds `nameserver 127.0.0.11` (its embedded
DNS) for a container on a user-defined network, and once anything other than Docker has modified a
container's `resolv.conf`, Docker stops touching that file for the life of the container (the
file's own banner: `Generated by Docker Engine. ... will not make further changes once it has been
modified.`).

So `docker network connect wbs-net dagger-engine` attaches the container to `wbs-net` (confirmed
via `docker inspect`; this part is durable and survives restarts), but the container never gets
Docker's embedded resolver, so it cannot look up `registry` or any other container on `wbs-net` by
name.

## What to run after every `dagger-engine` restart

Docker's embedded resolver (`127.0.0.11:53`) is listening and resolves `registry` for this
container once queried, verified directly:

```bash
docker exec dagger-engine sh -c '
  cp /etc/resolv.conf /tmp/resolv.conf.orig
  { echo "nameserver 127.0.0.11"; cat /tmp/resolv.conf.orig; } > /tmp/resolv.conf.new
  cat /tmp/resolv.conf.new > /etc/resolv.conf
'
docker exec dagger-engine getent hosts registry
# 172.18.0.3      registry   <- resolved via 127.0.0.11, not a static hosts entry
```

`sed -i` and other rename-based in-place edits fail with `Device or resource busy`:
`/etc/resolv.conf` is a bind mount. Overwrite it with a plain `cat > /etc/resolv.conf`, as above.

**This does not survive a `docker restart dagger-engine`.** Confirmed by testing: after a restart,
`/etc/resolv.conf` is back to just `nameserver 10.87.0.1` and `getent hosts registry` fails again.
The container's startup rewrites the file every time, unconditionally.

Prefer this DNS fix over hardcoding `registry`'s current IP into `/etc/hosts`: it keeps working if
the `registry` container is recreated with a new IP, where a static hosts entry would silently go
stale.

## Why this isn't fixed permanently here

A real fix needs `wbs-net` attached **before** `dagger-engine`'s startup runs its dnsmasq setup:
the container must be recreated with `--network wbs-net` in the initial `docker run`, not attached
later with `docker network connect`. That was out of scope for this fix round: it requires
stopping and recreating a `--privileged`, `--restart always` container that Task 1's spike stood
up, and this repo does not capture the exact `docker run` invocation used to create it. Whoever
owns `dagger-engine`'s lifecycle should either:

- capture its full creation command (ideally as a script) with `--network wbs-net` from the
  start, or
- add a small startup hook (e.g. a `docker update --restart` wrapper, or a oneshot systemd unit
  that runs the commands above on `docker events` for this container's `start`) so the
  remediation applies itself.
