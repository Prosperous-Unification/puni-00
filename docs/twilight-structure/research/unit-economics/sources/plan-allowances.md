# Plan allowances: measured tokens per subscription tier

Inspected 2026-09-08. Synthesis over the user-report sheets in [plan-allowances-reports.md](plan-allowances-reports.md), verified in [../verification/plan-allowances.md](../verification/plan-allowances.md). Web search was exhausted for the session, so Anthropic sources are Hacker News (via its Algolia API) and claude-code GitHub issues; Reddit and X were unreachable.

## Headline

There is no honest answer to the question as asked, because no source anywhere in this research pairs a subscription plan tier with a token count: the only real aggregated datasets (viberank, n=1.2K live and n=792 snapshot, 16.4T and 2.5T tokens) have no plan field at all, and every plan-labelled number is a single user's self-report. For Anthropic mixed-model use the plan-labelled month-scale points are $1,500/mo (Max 5x, cap NOT hit, 15x the fee), $3,200/mo (~$100 plan, only ~1/3 of the weekly limit used, 32x) and $3,000/mo (Max 5x, cap hit repeatedly, 30x); for Max 20x the only figures are dollar-denominated cap _bands_ derived from Anthropic's own rate-limit headers by one proxy tool, ~$1,300-1,900/week, which converts to ~$5,600-8,200/mo at list, a 28-41x ratio. The single rigorous token measurement at a cap (GH #84607, Max 20x) found the weekly quota filled at 335.0M weighted tokens one week and ~125M the next on the same unchanged account — a 2.7x swing, with 17x-45x same-day variance — so "tokens the plan delivers" is not a stable quantity to publish. Cache reads are 94.8-95.1% of all tokens in three independent sources but are weighted roughly 10x cheaper inside Anthropic's meter (back-solved formula: cache_creation×1.25 + cache_read×0.1 + output×5, raw input excluded), so token totals and quota consumption diverge sharply. Per-model resolution barely exists: Opus has only a message-count proxy and a historical hour range, Sonnet only one account's ~$150/week sub-budget on Max 20x, and Fable only session-level numbers plus a vendor statement that it may consume up to 50% of the weekly limit. The most load-bearing structural finding is that the "20x" multiplier is scoped by Anthropic to the 5-hour session window only; nine-plus independent reporters in GitHub issue 79773 back-solve the effective Max-20x-to-Max-5x weekly ratio at roughly 1.7-2.3x, not 4x. Every OpenAI cell is empty for a process reason rather than a factual one: that research task returned zero facts because its web-search budget was exhausted before it ran, so no Codex per-window or per-week credit or token figure exists here at any plan tier. Two upstream numbers were corrected during verification and one was refuted outright (a supposed HN comment reporting 40-50% of a 5-hour window on a trivial task does not exist and is excluded).

## Reading the tables

- **[CAP]** = the reporter states the plan limit was reached in that window; the number estimates a ceiling.
- **[LEVEL]** = the reporter states the limit was _not_ reached; the number is a lower bound on what the plan delivers.
- **[UNKNOWN]** = the source does not say. Do not read these as caps.
- Every dollar figure is the **source's own list-price computation** (ccusage / viberank / Claude Code `/usage` / claude-meter). I applied no price table of my own — see the method note.
- "Derived" cells name the arithmetic. Weekly→monthly is ×4.3333 (52/12).
- **No source in this research pairs a plan tier with a token count.** Plan-labelled rows are n=1 self-reports; the only multi-user datasets have no plan field and appear in table A5.

## Method

HOW API COST WAS COMPUTED: it was not computed by me. Anthropic list prices per token were not verified in this session, so multiplying token counts by remembered rates would have been invention. Every dollar figure in these tables is the source's own list-price computation, and the engine is named per row: (a) npx ccusage, which prices a user's local ~/.claude transcript against its own bundled list-price table, including cache-creation and cache-read tokens at their separate cache rates (sigseg1v, itsyonas, garblegarble, joshstrange, conradkay, nthypes); (b) viberank, which re-prices submitted ccusage exports at list (all four token categories, 94.8-95.1% of them cache reads); (c) Claude Code's own /usage panel, which Anthropic's docs state computes at list price by default unless an admin sets a modelPricing override (GH #75518); (d) claude-meter, which re-weights observed traffic at API list price to express the rate-limit headers as a dollar band (Max 20x 5h and 7d budgets). CACHE ASSUMPTION PER ROW: every dollar figure above includes cache reads, priced at cache-read list rates, and cache reads are ~95% of the tokens in every row where the mix is itemized. The plan-side meter does NOT weight them the same way: the one back-solved formula (GH #84607, n=1) is weighted = cache_creation x 1.25 + cache_read x 0.1 + output x 5, with raw input excluded entirely, and claude-meter independently concludes the meter is price-weighted rather than token-weighted with cache reads "much more cheaply" weighted. So a row's list-price dollars and its quota consumption are different quantities and must not be equated. THE ONE DERIVATION I DID FROM TOKENS TO DOLLARS: none forward. Backward only, on the single row that gives both: garblegarble's 5M input + 1.5M output + 121M cache-create + 1.7B cache-read = 1,827.5M tokens against the source's own ~$1,500 ccusage estimate implies a blended $0.82 per million tokens ($1,500 / 1,827.5M) — computed from the source's own two numbers, requiring no external price table, and low only because 93% of the mix is cache reads. TIME CONVERSIONS: weekly to monthly uses x 52/12 = 4.3333 and is labelled "derived, x4.33" in every cell that uses it ($1,300/wk -> $5,633/mo; $1,900/wk -> $8,233/mo; $1,949/wk -> $8,446/mo; $150/wk -> $650/mo). Daily to monthly is shown as a range across two stated assumptions, x21 tracked days and x30 calendar days, because no source supplies a days-per-month figure (viberank's median day $29 -> $609-$870/mo; the source's own average is ~37 tracked days per developer TOTAL, so this is illustrative, not a monthly measurement). Per-request to per-developer-per-day for the Faros pilot is $1,572.52 / 28 participants / 5 days = $11.23, which assumes all 28 were active on all 5 days and is almost certainly a floor. RATIO COLUMN: ratio = (API-equivalent dollars per month at list) / (plan sticker price per month), with overage excluded from the denominator. Overage is a separate charge: Anthropic's support article scopes usage credits to Pro, Max 5x and Max 20x and states overage is billed at "standard API rates", so the two dollar overage observations here ($15 on a Fable session, $49 on Pro) sit outside the ratio. CREDITS TO TOKENS: not performed, because no OpenAI data was gathered at all and Anthropic publishes no credit unit. HOURS TO TOKENS: not performed. The only hour-denominated caps found (240-480h Sonnet 4 and 24-40h Opus 4 per week on the $200 plan, quoted 2025-11-13 from Anthropic's then-published range) have no tokens-per-hour anywhere in any source; converting them would be fabrication, so they are reported in hours and left unconverted. CAP VS LEVEL: every token or dollar cell is tagged [CAP] when the reporter states the limit was reached in that window, [LEVEL] when they state it was not, and [UNKNOWN] when they do not say. A [LEVEL] figure is a lower bound on what the plan delivers; only a [CAP] figure estimates the ceiling, and even then GH #84607 shows the ceiling moves 2.7x week to week on one account.

## Data quality

Weak-to-moderate, and weakest exactly where the question is sharpest. There is no dataset anywhere in this research that resolves BOTH a subscription plan tier AND a token count. The only genuinely aggregated multi-user datasets (viberank, n=1.2K live / n=792 snapshot; Faros AI pilot, n=28) carry no plan field at all, so they cannot populate a Pro/Max-5x/Max-20x row. Every figure that does carry a plan tier is n=1 self-report from Hacker News or a GitHub issue, mostly dollar-denominated rather than token-denominated, and mostly not stated as measured at the cap. Anthropic itself publishes no token or dollar conversion for the 5x/20x multipliers (re-confirmed twice against claude.com/pricing) and its only published per-developer numbers are for API-billed Team/Enterprise, not flat-rate plans — and a third-party paraphrase of that same figure disagrees by more than 2x ($6/day vs $13/day). Two internal contradictions are unresolved in the source material: the same claude-meter account's 5h budget band is reported as $120–$280 in its author's HN comment and $35–$401 (median $164) in its own README, and the one rigorous weighted-token cap measurement (GH #84607) found 2.7x week-to-week variance and 17x–45x intra-day variance in quota cost per token on a single unchanged account, which means a token-count-at-cap is not a stable quantity even for one user. Cache reads dominate every token count (94.8–95.1% across three independent sources) but are weighted roughly 10x cheaper inside Anthropic's own meter, so token totals and plan-quota consumption are not proportional. OpenAI coverage is zero: the research task for it returned an empty fact list because its web-search budget was exhausted before it started — absence of coverage, not evidence of absence. One claim in the upstream research (an HN commenter "htuzel" reporting 40–50% of a 5-hour window on a trivial task) was refuted during verification as nonexistent and has been excluded.

Re-checked on claude.com/pricing and the Enterprise consumption guide; still absent.

- The alleged false-advertising lawsuit over Max limits (CNET, cited first-party from HN item 49509882) could not be fetched directly or via Wayback; its content is unverified and no number from it is used here.
- viberank's percentile figures are cumulative-to-date over varying tracked-day counts per developer, so they cannot be normalized to a month without an assumption the source does not supply.

### Method

Built exclusively from the supplied FACTS array and its VERIFICATION corrections (no new fetches). Where VERIFICATION marked a fact 'refuted' (the cloudzero.com Sol/Terra/Luna rate rows) or 'unverifiable', that number is excluded from arithmetic and flagged [UNKNOWN] rather than used. Where VERIFICATION corrected a sample attribution (MuffinFlavored→Aurornis; k9294→mark_l_watson) or a date, the corrected value is used. $0.04/credit is treated as verified (2 independent confirmations: khaledh, DominikPeters). GPT-5.5 rate ($5/$0.50/$30 per 1M in/cached/out) and GPT-5.3-codex rate ($1.75/$0.175/$14) are treated as verified (uibakery.io, matching the task prompt exactly). GPT-5.6 Sol/Astra/Terra per-token rates are treated as UNVERIFIED and excluded from $ arithmetic; the task prompt's asserted numbers for them are shown only as 'prompt-asserted, unconfirmed' for reference. 'Per month' figures are shown only where they are (a) an author's own stated monthly figure, or (b) a simple ×4.345 (=30.44/7) extrapolation of a weekly figure — the latter is explicitly labeled EXTRAPOLATED, not an independent measurement. Cap tags: [CAP] = source states 0%/exhausted/locked out; [LEVEL] = source describes ongoing/typical usage without stating exhaustion; [UNKNOWN] = cannot tell from the quote.

### Data quality

See the Data Quality table below (in tables_markdown). Summary: every usage-quantity data point is n=1 (a single HN comment, GitHub issue, or forum post), self-reported, with no independently auditable methodology; three fetch-based facts (viberank.app, GitHub star counts, community threads) were independently re-verified by live refetch and confirmed; two HN sample attributions were wrong and are corrected here; the cloudzero.com-sourced Sol/Terra/Luna rate-card numbers were refuted outright (that page never names those models) and are dropped from all arithmetic; the official learn.chatgpt.com/docs/pricing page gives message-count ranges, not tokens or credits, so it cannot populate the delivered-tokens column despite being the only primary-ish source that loaded.

### Gaps

- No primary OpenAI source stating an absolute weekly cap in tokens, credits, or messages was reachable this session (help.openai.com 403'd twice; the rate-card article 403'd; developers.openai.com redirected to a page with only 5-hour message ranges) — this is the single largest gap and the reason most 'per month' cells below are extrapolations or empty.
- GPT-5.6 Sol/Astra/Terra per-token credit rates are unresolved: cloudzero.com does not mention these model names at all (its 125/12.5/750 and 62.5/6.25/375 rows belong to GPT-5.5 and GPT-5.4 respectively, not Sol/Terra as the original dataset guessed), uibakery.io also never names Sol/Astra/Terra, and the only page that uses the Sol/Astra/Terra names (learn.chatgpt.com/docs/pricing) gives message ranges, not credit or token rates. No source resolves this. The task prompt's Sol/Astra/Terra rates ($4/$0.40/$20, $10/$1/$50, $2/$0.20/$12 per 1M) are therefore unconfirmed and were NOT used in any dollar computation below.
- Zero usage-to-cap measurements (tokens or credits) exist for GPT-5.5 or GPT-5.3-codex on any plan tier, despite their rates being the only verified ones — so the two rates that could support real arithmetic have no consumption data to multiply against.
- Zero usage measurements of any kind (tokens, credits, or even day-count anecdotes) were found for Business Standard/Premium; the only Business-specific fact is that its 5-hour message ranges mirror the Plus tier per the official pricing page, which is not a usage measurement.
- The best-quality raw-token data point in the whole dataset (GitHub #42357: 23,501,163 tokens = 98% of a 5-hour window, 96.8% cached, gpt-5.6-sol) is on a Team plan, outside the four required rows (Plus/Pro5x/Pro20x/Business), so it could only be used as a reference point, not a table row.
- The 'multiple independent HN commenters' token-volume anecdotes (radicality, ripped_britches, gbear605, stared, fomoz, ryan-a, reticulates) came from one aggregated search pass and were not individually re-verified in the VERIFICATION pass the way the other 29 facts were — treat their numbers as lower-confidence than the individually-checked facts.
- learn.chatgpt.com/docs/pricing's four dated milestones (2026-04-02/04-09/04-23/06-24) were NOT found verbatim on the live page during verification and are marked unverifiable — only the current Pro 5x/Pro 20x split and the 5-hour message ranges were confirmed on that page.
- No confirmed ratio between the 5-hour cap and the weekly cap exists from any OpenAI-primary source (one GitHub commenter's informal '5h is about half of weekly' was not confirmed by OpenAI).
- Reddit (r/codex, r/OpenAI) was effectively inaccessible this session, so a plausible large volume of user-reported cap data was never examined.
- The officeclaws.com half of the 'GPT-5.5 = 125/12.5/750' cross-check was not independently re-fetched during verification; only uibakery.io was re-confirmed.
