# Top-down business plan for a solo operator, built per client-month and per operator-month, with model cost derived from processed-token accounting (cost = U*p_in*1.25 + C*p_cache + O*p_out) at Twilight's shipped balanced routing. The single structural result: at every plausible routing and every plausible volume, model tokens are 0.5-4% of a client-month's revenue, hard-capped by Twilight's own strict per-run budgets to <=11%. The operating question is therefore price per accepted unit and number of clients, not tokens. The three premises (P1 subscription/API convergence, P2 cheap-model harness, P3 open weights ok and cheap) all bear on a line item that is a rounding error in this P&L; P2's real value is that bounded caps plus staging-proven acceptance evidence let Dany price per outcome at all, which is the lever worth 50x more than routing. Throughput is ceiling-bound twice: the shipped K3s pool binds at ~3 concurrent clients (a $100-200/month problem), human minutes bind at ~8-19 clients (the real ceiling), and demand binds before either in the conservative and base scenarios. Two shipped-default landmines are named: the balanced 1,500,000-token cap is breached 6.7x by a p50 medium feature if "tokens" includes cache reads, and 3x by a p90 medium feature even on the generous reading, while the $40 money cap is not breached at all; and Max-20x subsidy is a net loss at base volumes while carrying ToS and per-repo-credential exposure.

ToS/structural exposure, in order of severity:

1. **A34 makes it impossible anyway.** Twilight requires repo/provider-scoped ephemeral credential mounts and "never use a shared operator home". A Max seat is one person's OAuth token. Per-client credential scoping and a personal subscription are mutually exclusive by Twilight's own security floor.
2. Third-party harnesses have been off subscriptions since **2026-04-04**; Twilight drives ACP / `claude -p`, which is exactly the class Anthropic carved out.
3. Current legal page: OAuth is "intended exclusively for … ordinary use of Claude Code and other native Anthropic applications"; developers building products "including those using the Agent SDK, should use API key authentication"; "advertised usage limits … assume ordinary, individual usage".
4. The Agent SDK / `claude -p` / ACP → API-list-credit carve-out was **announced 2026-05-13, paused 2026-06-15** with advance notice promised. `--bare` (no OAuth, requires `ANTHROPIC_API_KEY`) "will become the default for `-p`". The subsidy is on a published deprecation path.
5. Enforcement precedent: 2026-01-09 harness-spoofing crackdown; "Anthropic reserves the right to take measures … without prior notice."

**Recommendation:** keep exactly **one** Max 20x for Dany's own interactive work and the OpenClaw secretary (that is "ordinary, individual usage" and ToS-clean), and put every worker attempt on API keys — which A34 requires regardless, and which at base volumes is _cheaper_ than a second seat.

**Which binds first:** in conservative and base, **demand**. ## Premise implications

P1 (labs will soon price coding subscriptions close to API usage prices) is already true at the margin and largely irrelevant to this P&L. Every overflow token on every Anthropic plan is billed at standard API rates; Enterprise is $20/seat + all tokens at API rates; third-party harnesses have been off subscriptions since 2026-04-04; OpenAI Codex credits convert to API list at exactly $0.04/credit; the Agent SDK / claude -p / ACP carve-out to API-list credits was announced 2026-05-13 and only paused 2026-06-15. Dany's factory is on the API-list side of that line already, by ToS and by A34's per-repo credential requirement. So P1 changes nothing about his cost structure: model spend is 0.6-1.3% of revenue at base and stretch, hard-capped by Twilight's own budgets at 7.1%. The convergence question is worth exactly the $89/month by which one Max 20x seat exceeds his entire API-list model demand.

P2 (until then, build a great custom harness that can use cheaper models) is half right and mis-aimed. The "cheaper models" half is worth 1% of revenue at most: model price x2 costs 1.06% of margin-after-operator-time, model price /2 gains 0.53%. The harness half is worth 50x more, but for a reason that has nothing to do with model price — the strict per-run caps ($40 balanced), the mandatory independent acceptance oracle, staging-proven acceptance and the run ledger are what let Dany sell an accepted outcome rather than hours, and price per unit is the lever worth +/-52% of margin. Build the harness for the acceptance evidence and the bounded blast radius, not for the routing flexibility. The routing flexibility should still exist, because it is nearly free to keep and it is the only hedge if measured tokens per unit turn out 10x my p50.

P3 (open-weight models will be ok for coding and much cheaper) is false in effective terms today at the tier where it was supposed to pay. At a 90% cache hit rate the bill is dominated by cache reads, and GLM-5.3's cache read ($0.26/MTok) is 30% MORE expensive than Sonnet 5's ($0.20/MTok) while GLM burns 1.22x the tokens (SWE-rebench 2.2x vs 1.8x). Routing implement to GLM-5.3 while keeping Opus review costs 1.01x pure-Anthropic balanced — a saving of nothing. MiniMax M3 (5.5x tokens, 2-5x attempts) and DeepSeek V4 Pro (1.6x tokens, ~5x attempts) are worse still on an effective basis, and the per-token discount is exactly what the merged-feature study measured being eaten by extra review cycles ($11-22 per merged feature for open-weight routers). The cheapest credible route is not open-weight at all: Anthropic's own economy ladder (Haiku implement, Sonnet review) is 0.54x balanced, all on one provider, one credential path, one rate card. Open weights become interesting only in two specific places: GLM-5.3-Flash at $0.03 cache read IF its attempts multiplier is measured low against Twilight's own verifier, and self-hosted inference, which is unpriced here because no self-hosting sheet was supplied.

The premise that actually governs the business is one Dany did not state: that clients will pay $1,250-1,500 per accepted unit for staging-proven acceptance. That is where +/-52% of the margin lives, and it is contested — 61% of dev shops expect AI to cut project budgets 10-25%, 27-33% of agencies have already been asked for an AI discount, and AI-native studios publish $1,500-2,500 per feature. A 30% price cut costs 28x what doubling every model price costs.

## Findings

- Model cost is a rounding error in this business. At base (4 clients, 12 accepted units/month) the entire API-list model bill is $110.56/month against $18,000 of revenue — 0.61%. Total COGS including all assumed infra is 4.3%. Twilight's own strict caps bound it mechanically at 7.1% of a $4,500 retainer ($120 of run budgets + $200 of sweep budgets per client-month).
- Routing implement to GLM-5.3 while keeping Opus for plan/review saves nothing: $9.37 vs $9.25 per medium feature = 1.01x. At a 90% cache hit rate the bill is cache reads, and GLM-5.3's cache read ($0.26/MTok) is 30% MORE expensive than Sonnet 5's ($0.20/MTok), before GLM's 1.22x token penalty. The open-weight lever is worth zero at the implement tier today.
- The cheapest credible routing is Anthropic's own economy ladder, not open weights: Haiku implement + Sonnet review = 0.54x the balanced blend, on one provider, one credential path, one rate card. That is a bigger saving than any open-weight substitution, with none of the adapter, licence-gate or attempts-multiplier risk.
- Lever ranking on margin-after-operator-time, base scenario: price per unit +/-30% = +/-51.6%; one extra client = +37.8%; human hours per unit +/-50% = +/-3.3%; one extra rework round = -1.28%; model price x2 = -1.06%; model price /2 = +0.53%. Doubling every model price costs less than adding one rework round, and one-fifth of what a 10% price cut costs.
- The balanced profile's 1,500,000-token cap binds before its $40 money cap, in both readings of 'tokens'. If cache reads count (adapter-defined, undecided), a p50 medium feature at 10M processed input is 6.7x over cap and every medium run pauses. If only uncached input + output count, p50 fits at 1.15M with 23% headroom but p90 (4.5M) is 3.0x over cap while costing $35.41 — still under $40. Deciding what 'tokens' means is the single highest-value measurement decision in the schema.
- The dev-sweep budget is 57x its own expected spend. A 200k-token nightly sweep at balanced sonnet routing, h=0.9, costs ~$0.14; the cap is $8. Across 25 branch-dev-nights the cap authorises $200/client-month against ~$3.50 of expected spend — larger than the entire delivery budget at base cadence. And verify-harness flags that a retried occurrence may draw a fresh account, so a bad night could be 3x that.
- A Max 20x seat is a net LOSS at base volumes. Break-even is 17.3 medium-feature-equivalents per $200 seat-month; the base scenario consumes 4 medium + 8 small across all four clients for $110.56 total. The subsidy is worth exactly the amount by which measured tokens exceed my p50 estimate — which is a reason to instrument (M1 ledgers) before buying, never to buy first.
- A34 makes the subsidy structurally impossible regardless of ToS. Twilight requires repo/provider-scoped ephemeral credential mounts and forbids a shared operator home; a Max seat is one person's OAuth token. The security floor and the subscription are mutually exclusive. Keep exactly one Max 20x for Dany's own interactive work and the OpenClaw secretary (ordinary individual usage, ToS-clean) and put every worker attempt on API keys — which is also cheaper at these volumes.
- Capacity binds before human minutes, but capacity is the cheap ceiling. The shipped 2-agent-node K3s pool supports ~6 concurrent attempts, i.e. ~3 concurrent clients at agentSlots 2 (1.5 in burst at perClientCeiling 4). The human-minute ceiling is 8-19 clients / 24-57 units per month. Each additional agent node is ~$50-100/month and ~2 h of manual join (A50); two more nodes reach ~6 clients, four more reach ~9-12. scalingAcceptance already authorises fanOut 8 / perClientCeiling 8 / agentSlotsCeiling 8. So: capacity binds first, human minutes bind second and are the real ceiling, and demand binds before either in the conservative and base scenarios.
- Serialized staging, 1 build slot and 1 browser slot per repo are burst constraints, not throughput constraints, at these volumes: ~6-13 medium features per client-DAY on serialized resources and 7-20 on agent slots, against 3-4.5 accepted units per client-MONTH. They only matter if candidates arrive in bursts, and only under the personal-delivery floor (factory-core terminates at handoff with cloud acceptance disabled).
- The conservative scenario is underwater on operator opportunity cost: 101.8 hours x $75 = $7,635 against $4,468 of gross margin, i.e. -$3,167. Two clients do not pay for the 60 h/month of factory-build time. The scenario is a build phase with revenue, not a business.
- Gross margin per DELIVERY hour is $990-$1,873 across all three scenarios while gross margin per TOTAL operator hour is $44-$351. The entire spread is sales and factory-build hours. That is the arithmetic case for spending marginal hours on selling rather than on delivering: one extra client at base is +$3,960 of margin for ~6.3 hours.
- The factory's own build is a human-hour investment, not a token investment: 280-560 hours ($21k-$42k of opportunity at $75/h) against 3.5-9.2M tokens ($3.24-$8.51 if those are processed tokens at $0.925/M blended, ~$32-85 if they mean billable non-cache tokens). At 40-60 build hours/month the base scenario is 5-14 months away. Note the tasks.md phase-table figure (280-560 h / 3.5-9.2M) disagrees with the line-item sum quoted in the brief (303-604 h / 2.4-6.4M) and with the dated plan-review snapshot (72-148 h / 1.19-3.46M for M1).
- Retainer pricing and per-outcome pricing only reconcile at a specific cadence. A $4,500 retainer with 6 accepted units/client-month implies $750/unit — below the bottom of the derived small band ($300-2,500) and far below the medium band ($1,500-8,000). At 3 units it implies $1,500/unit, which is consistent. Either publish the cadence in the retainer or price per outcome; a retainer with an unbounded unit cadence is the one structure where model cost could actually escape its 1% share.

The answer changes the balanced cap from 'fits a p50 medium feature with 23% headroom' to 'pauses every medium run at 6.7x over'. - What is the measured Twilight ceremony multiplier F? I assumed 1.25x on the derived per-PR distribution to account for discovery + spec critique + critic + judge + rework beyond a single review gate. If F is really 2.0-2.5x, every model cost above rises 60-100% (still under 3% of revenue) and the p90 medium feature breaches the $40 money cap as well as the token cap. - What is the measured human-minute cost per accepted unit? design.md requires it to be explicitly measured and never inferred, and no figure exists. My 0.4 / 1.5 / 5.0 h per small / medium / large drive the entire human-minute ceiling (8-19 clients) and the third-ranked sensitivity lever. If a medium feature really costs 4 h of Dany's attention, the ceiling drops to 4-8 clients and the stretch scenario is unreachable.
- What is the realised cache hit rate under Twilight's per-activity model switching? Every switch between activity classes (sonnet implement -> opus review -> haiku knowledge) forces a full uncached re-read, and API-key billing carries a 5-minute TTL by default while the grill deliberately left TTL unselected. If h drops from 0.90 to 0.70 the medium-feature cost rises from $11.56 to $17.19 (+49%) — still 1% of revenue, but it interacts with the token cap.
- What does the infra actually cost? No infra price sheet was supplied. Every dollar in section 7's fixed-cost table is my unsourced assumption, and infra is 85-90% of COGS in every scenario (base: $660 of $771). Browserbase per-session pricing in particular was explicitly not found. A real quote for K3s nodes, per-client environments and Browserbase would move total COGS more than any model-routing decision.
- Is self-hosted inference worth pricing? No self-hosting sheet exists. The arXiv 2604.17187 finding that 10-15B-active models run at ~1/7 the hardware cost of 32-40B-active, combined with GLM-5.3-Flash's MIT licence and $0.03 cache read, is the only route by which P3 could become true — and it is the one route this analysis cannot evaluate.
- What is GLM-5.3's attempts multiplier against Twilight's own verifier? SWE-rebench measured GLM-5.2 at ~1x attempts (needing an external verifier, which Twilight has: repo gate, browser gate, critic, judge, independent acceptance oracle). If GLM-5.3-Flash at $0.03/MTok cache read also holds ~1x attempts, the (b') aggressive route drops to ~0.25x balanced — the only configuration where routing is worth more than 1% of revenue. This is a cheap fixture to build once M1 ledgers exist.
- Will clients pay $1,250-1,500 per accepted unit, and will they hold that price? This is the lever worth +/-52% of margin and it is the only number in the model with no anchor from Dany's own market. Fraction publishes $99/story-point (medium feature 8-15 pts = $792-1,485); HouseofMVPs implies $1,500-2,500/feature; 61% of dev shops expect AI to cut budgets 10-25% and 27-33% of agencies have already been asked for an AI discount. A named design partner (the A63 gate) is the only way to resolve it.

Per-outcome transfers cadence risk to the client and matches the 27% enterprise preference for outcome pricing (Futurum); a retainer transfers it to Dany and is the one structure where an unbounded unit cadence could push model cost above 1%. The answer probably differs by client and should be a per-client decision, not a company one.
- What happens on 2026-09-13? The +50% Claude Code weekly-limit promo expires in five days and Anthropic's article says limits return to standard. If Dany is relying on any subscription capacity for interactive/secretary work, that is a 33% capacity cut on a known date. Unrelated to the factory's API-key path, but it hits the one seat I recommend keeping.

That trade is worth 52% of margin on one side and ~10% of throughput on the other, and no artifact in the repo evaluates it.
