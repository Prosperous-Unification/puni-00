# P2: "Until OpenAI/Anthropic price coding subscriptions close to API usage prices, I'll be able to develop a great custom harness that can use cheaper models." Three load-bearing parts: (a) a _window_ exists and the build lands inside it; (b) the harness's value _depends_ on that window (i.e. cheaper model tokens are the payoff); (c) "can use cheaper models" is a property the harness confers.

**Verdict:** premise is wrong as stated

## Strongest refutation

**All three parts fail, and (b) fails on arithmetic that does not depend on any forecast.**

**(a) There is no window to be inside.** Twilight's own design is API-metered by construction, so the subscription arbitrage P2 is racing is one Twilight cannot enter. `estimatedCost is tokens times the rate-card entry pinned at admission… billedCost is the provider's reported figure` (design.md:257-276); the word "subscription" appears nowhere in the Twilight docs; and A34 requires `repo/provider-scoped integration secrets resolved by the trusted launcher into an ephemeral read-only credential mount; never use a shared operator home` — which subscription OAuth structurally cannot be (a `claude setup-token` OAuth token is tied to one person's subscription; Anthropic's own GitHub Actions doc says use an API key for org-shared secrets). Worse, the secretary half is _already_ off subscriptions: OpenClaw is a third-party harness, and third-party harnesses have been billed per token on Pro/Max since 2026-04-04. And Anthropic's legal page already scopes plan limits to `ordinary, individual usage of Claude Code and the Agent SDK`, reserving enforcement `without prior notice` — a 24/7 K3s pool running one Job per admitted attempt across two agent nodes is not that. The convergence signal is not a future risk to schedule against; for this architecture it has already happened.

**(b) Model tokens are 0.3–5% of per-unit cost, so the harness's value cannot depend on token price.**

What in the design converts pass@5 into acceptance? Only four things, and three are too small:

1. **speculation** — the _only_ independent resampling — is `defaultEnabled: false`, `maxAttemptsPerDeliverable: 2` → **pass@2 max**, and enabling it mid-run is an envelope change needing a new human decision.
2. **rework.maxRounds** (3/2/1) is _correlated_ retry on the same closure, shared across the whole affected-dependency closure — pass@k arithmetic does not apply.
3. **escalation** is maxSteps 1 and the failed cheap attempt stays charged (grill Q20: "Does escalation erase the cost of the failed cheaper attempt? **No.**").
4. **acceptance.evaluate + coverage + gate + browser** is the one genuinely strong piece — floor-required, tool-executed, "missing assertions block as unavailable." But its assertions are authored by the _specification_ stage, i.e. by a model, and nothing conditions oracle strength on implementer model class: a cheaper spec writes a weaker oracle exactly where it matters.

So the shipped harness buys **pass@2 = 1−0.598² = 64.2%** on DeepSeek V4 Pro — **exactly Fable 5's pass@1 (64.5%) at 2×1.6 = 3.2× the tokens**, both charged. And it cannot even buy that: 4 attempts × 1.6× × 4.3M = **27.5M processed input for the implement class alone against a 1.5M whole-run cap** — the budget halts the run at ~5% of the way to pass@4.

The one end-to-end measurement says the same: open-weight implementers on Claude Code via router cost **$11–22 per merged feature** (M3 $14.77/3 cycles, Kimi-K2.7 $21.73/3 cycles, GLM-5.2 $14.95/176 min) vs **Opus 4.8 + Claude Code $9.98 / 1 cycle / 26 min**. Cheap models were measurably more expensive and 3–7× slower. MAI-Code-1-Flash's $2.81 total was **97% gate** ($2.76) — cheap implementer, expensive reviewer, which is exactly balanced's shape (Sonnet implement, Opus review/judge).

And the repo already concedes it. Grill **Q106**: "Should the scheduler always select the cheapest feasible model? **No.** …benchmarked model choice is a **profile input, not a per-dispatch auction**." Grill **Q105**: "Can reviewer capacity erase savings from cheaper worker models? **Yes if lower-quality outputs create more review or rework.**" Grill **Q6** (promise savings): **Reject**. Task 8's two runs "do not select a default profile." So Twilight's "cheaper models" capability is a class→model YAML map plus a one-step ladder — ~30 lines that any harness with a model config already has — and the design explicitly refuses to make it automatic. Every `provider:` key in all three profiles, both escalation targets and the discovery envelope is `anthropic`; there is no open-weight adapter, no non-Anthropic route, and Task 6 says "Probe Claude first, then Codex…; if both fail, **stop**."

Finally, the harness-vs-model literature cuts the wrong way: the 27.4 pp harness delta and the 19.1%→73.4% minimal-vs-full-adapter swing on the same GLM 5.1 are about the **inner coding loop** — and Claude Code/Codex _are_ the full adapter. Twilight's 9 model activities each delegate to an ACP session against a provider CLI. Twilight does not own the loop that produces the 27.4 pp; it owns admission, budget, evidence and acceptance. **Building it buys governance, not pass@1.**

## Steelman

The strongest version of P2 that the evidence actually supports:

1. **Harness genuinely is worth a model generation** — 27.4 pp of Pass@1 from harness choice vs 29.4 pp from model choice, and 19.1% → 73.4% from minimal vs full adapter on the _same_ GLM 5.1. If the delta were harness-shaped, building one would be the highest-leverage move available.
2. **Model prices are volatile enough that switchability is real optionality, priced in weeks not years.** Fable 5 was pulled from Pro subscriptions within two weeks of launch; DeepSeek raised V4 Pro prices 2-3× with three days' notice (announced 2026-08-13, effective 2026-08-16); Anthropic drafted the ACP/Agent-SDK carve-out and paused it inside 33 days; `--bare` will flip the `-p` default with no pricing announcement at all. A control plane where model choice is a class→model map plus a rate-card row makes a provider change a config edit instead of a rewrite. That is worth something, and it is the _only_ part of "can use cheaper models" that Twilight actually confers.
3. **Nobody publishes cost per accepted outcome, and Twilight's ledger is designed to measure exactly it** — per attempt, per model, per profile epoch, with failed attempts kept in the numerator and "no accepted outcome gives an unavailable ratio, not zero." The best public substitute is SWE-rebench: 111 synthetic tasks on a fixed ReAct scaffold. Twilight would produce the first such measurement on _real accepted features with a staging-proven oracle_. P3 cannot be settled without an instrument like it.
4. **The acceptance oracle is the genuinely load-bearing invention.** `acceptance.evaluate` + `acceptance.coverage` are floor-required, independent, tool-executed, charge the run before candidate acceptance completes, cannot be disabled, and block as _unavailable_ on missing assertions. That is the mechanism that turns any model's pass@k into an accepted outcome, and it is the piece a subscription and a coding CLI do not give you.
5. **The learning is front-loaded.** Tasks 1-4 (39-98 h, or 55-130 h with the 4.4-4.5 allowance) produce the first measured ledgers. Even if the rest never ships, that spend buys the numbers that decide P2 and P3 — and the plan's own text says exactly this: "Re-estimate M1 after Tasks 1-4 expose measured runtime and provisioning costs."
6. **Governance is the sellable product, and it is not commoditized.** Staging-proven acceptance, a CAS main publication, an explicit single-use release command, a 30-day escaped-defect window and a run ledger are what an SMB client is buying when they buy accountability rather than hours. That is orthogonal to token price and does not decay when subscriptions converge.

## Narrower statement

**What survives, with the "until convergence" clause deleted and the payoff re-pointed:**

"Twilight's model-token bill is 0.3-5% of the price of an accepted unit and it is already API-metered by design, so there is no subscription window to race and no material saving to capture from cheaper models. What is worth building — in 151-300 human hours for M1, 280-560 for the personal loop, landing 2026-11 to 2027-05 at 15-35 solo hours/week — is the per-attempt ledger and the independent acceptance oracle, because _cost per accepted outcome on real features is unmeasured by anyone_ and because model prices move on a 3-33 day notice cycle. The harness buys (i) the first honest measurement of what an accepted feature costs, (ii) a config-edit provider switch as insurance against price shocks, and (iii) staging-proven accountability, which is what the client is actually paying $1,500-8,000 for. It does **not** buy cheaper delivery: under the same scaffold every cheaper implement model (Haiku $3.74, DeepSeek V4 Pro $4.00, GLM-5.3 $4.21, MiniMax M3 $7.31) costs *more* than the Sonnet 5 the balanced profile already ships ($3.45), and the only end-to-end measurement has open-weight models at $11-22 per merged feature versus $9.98 for Opus 4.8 at 3-7× the speed."

**Three corrections the plan needs regardless of the verdict:**

## Model consequence

**Set the model's cost model so token price is a leaf, not a driver.**

1. **Per-accepted-unit cost stack (use these as the model's defaults, low / base / high):**
   - model tokens: **$1.5 / $10.8 / $120** (balanced factory-core p50 = $7.72; +$0.55 personal-delivery cloud-browser; ×1.0/1.3/2.0 failed-run loading). Empirical cross-check band $10/$35/$120.

2. **Price the model bill as noise against revenue.** Model $ / medium-feature price = **0.36% base**, band 0.02-8%. Any scenario branch whose payoff is "cheaper tokens" should be capped at ≤0.5 pp of gross margin and dropped from the decision.
