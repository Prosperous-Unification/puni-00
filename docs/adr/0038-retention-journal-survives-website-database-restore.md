# Retention journal survives website database restore

The website keeps an authoritative, remotely durable append-only record of client designations, classification holds and erasures, with a monotonic latest-head witness outside primary SQLite snapshots and the database host. A confirmed remote event and head precede any destructive database commit or success acknowledgment. A restored snapshot can predate those events, so startup replays the latest complete record before serving and refuses a missing, damaged or stale record. Recomputing solely from the restored database would revive erased content or lose a client exception; refusing every older backup would make otherwise valid recovery snapshots unusable. The separate record adds remote availability, crash-consistency and release-compatibility obligations that must be proved before activating retention decisions.
