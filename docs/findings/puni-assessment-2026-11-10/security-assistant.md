## Security findings

### SEC-01 — Organization isolation needs environment acceptance

**Acceptance/applicability/owner:** For new and existing WBS clients on shared/hybrid hosting, client A cannot read, mutate, replay or infer B; stale tabs cannot redirect A's writes into B. Application security owner and environment operator own acceptance; dedicated/client-owned deployments must prove their selected configuration too.

**Intent → implementation/evidence:** [Organization access tasks](../../../openspec/changes/organization-ownership-and-access/tasks.md) require activation and browser acceptance. [`SqliteOrganizationAccess`](../../../libs/wbs/adapters/store-sqlite/src/organization-access.ts) still deliberately permits deployment-wide legacy access before activation, then rechecks membership/current credential rules. Browser immutable expected-organization clients and stale-tab invalidation are implemented (tasks 8.1–8.7); 8.8 remains open. Fresh local project tests prove foreign/absent 404 parity, viewer refusal, next-request membership removal, corrupt-marker failure and audit rollback; they do not exercise every real browser/socket/MCP path.

**Reconciliation/gap/action:** Prior S1's implementation has advanced, but activation and production identity remain separate **activation/verification gaps**. [Activation runbook](../../runbook-organization-activation.md) now documents dev's historical epoch-0 cutover and required epoch precondition; its older task prose still contradicts that history. Fresh central evidence confirms dev activation and configured browser authority, but production lacks the activation table and the current MCP epoch remains unknown; this supersedes the prior snapshot without closing a two-client proof. Reconcile those live identities/epoch, then run an attended two-client matrix on the exact release, including selection, delayed responses, stale reads/writes, socket replay and revoked MCP. Closure: retained identities, denied requests, unchanged B persistence/events and measured revocation bound. No shared-client guarantee before that proof.

### SEC-02 — Sign-in is configurable; each provider remains an integration

**Acceptance/applicability/owner:** New-app and existing-stack integrations need exact issuer/audience/claims, verified linking, allowed sign-in methods and current authorization; client identity administrator owns IdP configuration, application owner owns policy across every hosting model.

**Intent → implementation/evidence:** [OIDC integration](../../auth-integration.md) and [ADR 0049](../../adr/0049-enterprise-sso-is-a-wbs-connection-record.md) separate identity from WBS membership. [Auth adapter](../../../libs/wbs/adapters/auth/src/oidc-client.ts) implements discovery, code+PKCE, issuer-mix-up checks and RS256 verification; native passwords coexist by configuration. [Auth mode](../../../libs/wbs/adapters/auth/src/auth-mode.ts) refuses production local mode; cookies are host-only, Secure and HttpOnly. Fresh adapter tests pass. Keycloak's credentialed browser/socket/MCP acceptance in the runbook is dated 2026-08-24; Auth0 credentialed acceptance and [social connection/operator tasks](../../../openspec/changes/social-sign-in/tasks.md) are not closed by present source inspection.

**Reconciliation/gap/action:** Prior S2 remains a **configuration/verification gap**, not absent OIDC implementation. Auth0 is an actual supported mapping; Okta is historical (expired trial); Google/GitHub/email require enabled provider connections; Apple is deferred. No new provider certification follows from PKCE support. Prove the chosen client's real login, account-linking denial, wrong audience/issuer/group prefix, disabled account, local-password policy and refresh outage on the delivered origin. Closure includes HTTP/browser/socket/MCP outcomes and named configuration owner without credential values.

### SEC-03 — Machine identity is narrower; host authority is a different boundary

**Acceptance/applicability/owner:** An agent may act only as its bound person/organization and delegated scopes, never gain organization administration or reuse another client's grant. WBS security owner controls machine credentials; infrastructure owner controls host/provider/Git authority for all journeys/models.

**Intent → implementation/evidence:** Since prior S3/S5, [machine surface](../../../openspec/changes/wbs-mcp-agent-surface/tasks.md) adds API-key/JWT-bearer grants through MCP, person-bound consent, agent pools, narrow audiences and read-only scope support. [Authentication contract](../../auth-integration.md#fleets-and-the-mcp-endpoint) and [middleware](../../../apps/wbs/be-01/src/middleware/authenticated.ts) refuse machine bearers on `/api`; [credential tests](../../../apps/wbs/be-01/src/controller/machine-credential.controller.db.test.ts) assert no admin bypass and person restrictions. Fresh fleet tests prove retired groups-less links cannot mint users. These controls govern WBS, not arbitrary shell credentials reachable by an assistant.

**Reconciliation/gap/action:** This is substantial **implementation progress**; [open M16](../../../openspec/changes/wbs-mcp-agent-surface/tasks.md) still allows account-bound agents to claim beneath another same-account agent's subtree. Run scope is opt-in; this is not adversarial worker isolation. Before a client pilot, enumerate effective WBS/host/Git/provider authority per role and route; issue separate client credentials, prove forbidden admin/cross-person/cross-org actions and a compromised-worker attempt to reach coordinator credentials. Closure requires denied effects and evidence of credential reachability, not just a role name.

### SEC-04 — Revocation works locally; full offboarding crosses systems

**Acceptance/applicability/owner:** Removal ends already-issued browser, socket, MCP and machine authority within the agreed bound, retaining unrelated clients and audit. Security lead plus client identity/infrastructure administrators own this for shared, dedicated, client-owned and hybrid environments.

**Intent → implementation/evidence:** [SCIM deprovisioning tests](../../../apps/wbs/be-01/src/controller/scim-deprovisioning.controller.db.test.ts) freshly pass immediate A denial with B retained, last-super-admin refusal, and audit failure rolling back membership deletion. The selected-cookie gateway-access case uses real mounted backend authentication; it is not a complete deployed socket exercise. [Gateway task 6.3](../../../openspec/changes/organization-ownership-and-access/tasks.md) describes 3 s renewal plus 1.5 s deadline (4.5 s bound), with notification fan-out absent. [Durable browser revocations](../../../libs/wbs/adapters/store-sqlite/src/browser-credential-revocations.ts) and per-use membership checks exist.

**Reconciliation/gap/action:** Prior S3's local evidence remains strong; deployed cross-system expiry and customer exit are **verification/runbook gaps**. WBS removal does not revoke cloud/SSH/Git, assistant connectors, billing or backup copies. Smallest action: one synthetic offboarding inventory/exercise covering those owners, active connections and retained backups. Closure: old credentials fail, unrelated tenant continues, export is usable, retained/deleted copies have an agreed policy and PUNI access can be removed without disabling client ownership.

### SEC-05 — MCP epoch, refresh and secret lifecycle are distinct controls

**Acceptance/applicability/owner:** MCP cannot revive old/unbound or revoked authority across restart, refresh or key rotation; secrets have named owners, bounded overlap and tested expiry. Application security and platform operators own all MCP-enabled journeys/models.

**Intent → implementation/evidence:** [Epoch CLI](../../../apps/wbs/mcp-01/src/credential-epoch.ts) now drains via exclusive store refusal, advances one-way and revokes epoch-0 families; activation refuses an unadvanced store. Fresh epoch tests pass. [Session store](../../../apps/wbs/mcp-01/src/session-store.ts) tests prove ciphertext/digests, replay revocation, tamper refusal and one refresh lease. [Production authority reader](../../../apps/wbs/mcp-01/src/organization-authority.ts) now exists and rechecks membership/consent, superseding [refresh tasks](../../../openspec/changes/mcp-refresh-policy/tasks.md) saying no production adapter; it explicitly supplies `lifecycle: null`, so it cannot satisfy session policies requiring trusted times. Policy revision/publication convergence remains open.

**Reconciliation/gap/action:** Prior S4/S5 now split into **implemented epoch/authority**, **unverified operational cutover/rotation**, and **remaining lifecycle/publication implementation**. [MCP rotation procedure](../../../apps/wbs/mcp-01/README.md#durable-sessions-and-key-rotation) is not proof it ran; [public tool-secrets](../../../tools/tool-secrets/src/README.md) remains placeholder automation. Private fleet main documents actual SOPS/escrow conventions; this does not turn the placeholder into a general rotation service. Inventory each credential consumer/owner/scope/expiry/backup treatment; prove non-client key overlap, old-key expiry, queued refresh revocation and restart on the selected release. Keep lifecycle-policy claims disabled until authoritative timestamps and publication fence are proved.

### SEC-06 — Workload policies do not yet qualify a client isolation product

**Acceptance/applicability/owner:** A compromised/noisy client cannot reach another client's network, storage, credentials or reserved capacity; agreed degradation holds. Platform security owner and client infrastructure owner choose boundaries, especially for shared/hybrid new-app and scaling work.

**Intent → implementation/evidence:** [Namespaces](../../../infra/platform/policy/namespaces.yaml) declare restricted application/worker namespaces, no automounted worker token and worker quota (8 requested CPU, 16 GiB requested memory; 40 pods). [Network policy](../../../infra/platform/policy/network-policy.yaml) declares default deny for WBS/workers/website environments and worker DNS/telemetry-only egress; privileged monitoring/backup and trusted host-path workloads are explicit exceptions. These are source declarations and historical proof comments, not fresh policy enforcement or per-client isolation tests. See [infrastructure assessment](infrastructure.md) for fleet maintenance/recovery boundaries.

**Reconciliation/gap/action:** Prior S6 still has **activation/verification gaps**. Product/environment namespaces, one shared worker quota and Compose process limits are not per-client CPU/storage/backup reservations. Prove exact deployed network/RBAC/storage/account boundaries and concurrent noisy-neighbor pressure. Closure: expected denies from actual workloads, surviving legitimate-client targets, bounded failure/recovery and owner-approved shared trust exceptions. Dedicated environments must also disclose shared root/cloud/backup/telemetry authority.

Application performance/security owner and edge operator own the endpoint mix, proxy trust, replicas, NAT population, alerting and acceptable degradation across application/scaling/shared-service journeys.

**Acceptance/applicability/owner:** Every client has credential/patch owners, access review, incident response, retained tamper-evident-enough audit for its agreed threat model and a supported exit. ## Reusable features

### REU-01 — Authentication is reusable WBS code, not demonstrated second-app adoption

**Acceptance/applicability/owner:** A second new or existing application integrates versioned sign-in/session/revocation contracts without inheriting WBS roles, measured configuration effort or bespoke authorization hidden as reuse. Shared-module owner and second-app owner own the proof in every delivery model.

**Intent → implementation/evidence:** The map advertises OIDC/Auth0/Okta. [`wbs-auth` project](../../../libs/wbs/adapters/auth/project.json) remains `product:wbs`; [claims](../../../libs/wbs/adapters/auth/src/oidc-identity.ts) import WBS contracts and map `<environment>:wbs:{read,write,editor}`. The [authentication module](../../../libs/wbs/application/core/src/module/authentication/README.md) declares WBS consumers. Scoped searches found no `@wbs/auth` import in public website/shared code or pinned private-main website apps/libs. Private website operations (`puni-pr-00/docs/website/README.md` at the pinned revision) explicitly retires prospect OIDC; it is not second-app auth acceptance.

**Reconciliation/gap/action:** Prior S7 remains a **reuse verification/contract gap**. Provider-neutral protocol code can be adapted; provider registration, principal/claims, local-password policy, roles, tenant boundary and logout/refresh/revocation are still app-specific. Smallest action: second-app fixture with independent authorization and a real chosen IdP, cross-account negatives, upgrade compatibility and measured active/wall time. Closure: versioned integration contract and repeatable install/upgrade evidence; no extraction is prescribed by this assessment.

### REU-02 — Shared foundations exist; service reuse requires separate qualification

**Acceptance/applicability/owner:** Distinguish importing a library, adapting deployment automation and relying on a running shared service; each has a version/owner/failure contract. Shared-module/platform owners and client delivery lead own this for all three journeys.

**Intent → implementation/evidence:** [Shared validation](../../../libs/shared/domain/validation/README.md) and [failures](../../../libs/shared/domain/failures/README.md) are framework-free product-shared foundations; [delivery observations](../../../libs/shared/domain/delivery/README.md) define a versioned read-only provider-neutral contract. [Website portability fixture](../../../libs/website/adapters/portability-fixture/index.ts) demonstrates a shared formatting dependency. The private companion pins public app/API/library snapshots and fleet manifests, showing concrete source reuse rather than another auth consumer.

**Reconciliation/gap/action:** Compared with prior S7, shared contracts remain credible **implemented ingredients**; their existence does not prove arbitrary-stack onboarding or a tenant-aware running auth/registry/telemetry service. Produce a per-client dependency bill (version, import/service/automation, adaptation, owner, upgrade and exit path). Closure: a second-app delivery receipt and compatibility/negative checks for the actual reused boundary; these shared libraries were not retested in this focused security pass.

## OpenClaw assistant findings and journey

### AST-01 — Existing operator assistant is not a qualified customer installation

**Acceptance/applicability/owner:** A new assistant starts from client-owned accounts, 3–5 useful tasks, pinned runtime/plugins and declared shared/dedicated components; tasks pass with named acceptance, install time and active operator minutes. Delivery lead and client task owner own acceptance; operator/client infrastructure owner provisions according to the chosen model.

**Intent → implementation/evidence:** [Assistant vocabulary](../../assistant/CONTEXT.md) defines secretary/worker/assignment; [prototype](../../assistant/work-view-prototype.md) is fictional in-memory UI that calls no agent. [Twilight assistant contract](../../../openspec/changes/twilight-control-plane/specs/twilight/assistant-interaction/spec.md) and [2026-09-07 boundary research](../../twilight-structure/research/assistant-runtime-boundary.md) are design evidence; the latter explicitly lists live proofs not run. [Human operations](../../../HUMAN_README.md#when-openclaw-itself-is-unreachable) covers an existing operator gateway's triage, not a reproducible customer installer. Fresh central evidence observes the CLI/service/channel metadata above; it does not establish a reproducible customer installation. See [live evidence](live-evidence.md).

**Reconciliation/gap/action:** Prior assistant product/installation gap remains **implementation/service-packaging and verification**; website sales-scoping chat is a separate application. Smallest action: one isolated attended assistant install for a selected supported environment, with pinned artifacts/configuration references, authenticated channel, connectors and allowed/refused tasks. Closure: another operator can reproduce it and client acceptance records task outcomes, elapsed/active/wait time and remaining manual steps. No customer onboarding-duration claim is established.

### AST-02 — Effective tool authority and approvals must be proved per route

**Acceptance/applicability/owner:** Sending messages, editing/deleting private information, spending and infrastructure changes require exact client-approved authority; malicious retrieved content and alternate harness routes cannot widen it. Security lead, client information owner and identity administrators own consent and enforcement in every model.

**Intent → implementation/evidence:** [Human runbook](../../../HUMAN_README.md#read-this-before-you-use-whatsapp-for-anything-real) historically describes `security=full, ask=off` and a separate-command approval habit that is not enforced. This is dated operational documentation, not fresh effective policy. Historical [runtime-boundary research](../../twilight-structure/research/assistant-runtime-boundary.md#configurability-quality-and-execution-authority) distinguishes host/harness policy routes; it cannot certify today's installed version/defaults. WBS MCP offers an actual narrow connector (SEC-03/05), but it cannot limit unrelated host/Git/cloud/email credentials. Absent policy fields alone establish neither permission nor safety.

**Reconciliation/gap/action:** **Effective-authority verification and customer policy implementation gaps** persist even if the current CLI version differs. Inventory connector accounts/scopes/expiry and all native/ACP/CLI/subagent tool routes; use client-owned grants. Prove allowed/denied action, missing/stale/mismatched approval, compromised channel, injected email/document and attempted bypass through another route. Closure: exact action/target-bound approval is enforced before irreversible effects, old grants fail after revoke, and an interruption cannot duplicate an external effect. Do not place unrelated adversarial clients behind one assumed trusted operator boundary.

### AST-03 — Assistant privacy, spend and responsiveness are unknown at service level
