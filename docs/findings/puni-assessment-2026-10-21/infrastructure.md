# Infrastructure, fleet, capacity and recovery assessment

Assessed 2026-10-21 against [the requested scope](../../../puni-assessment.md), at local source revision `4151532121633d978beb67ab52b3eb748285cd8e`. This is a read-only assessment apart from this report. No provisioning, deployment, remote access, recovery drill or configuration change was performed by this assessment worker. Fresh read-only observations supplied by the main assessor are identified explicitly and recorded in [live evidence](live-evidence.md); historical SSH observations below are not observations made today.

PUNI has substantial reusable infrastructure machinery with deliberate identity, recovery and failure boundaries. It does not yet have evidence for a repeatable, generally available client hosting service or for arbitrary application scaling. Its strongest proofs concern the existing WBS topology and disposable k3d/QEMU environments. The largest delivery gaps are operational activation, the lifecycle of standalone hosts, cloud-provider acceptance, stateful capacity constraints, and proof that every relevant store can be recovered under an agreed target.

The highest-priority fresh operational finding is that h1's hourly SQLite backup timer is active but its latest service invocation failed: 2026-10-21 17:17:00–17:18:27 UTC, `Result=exit-code`, `ExecMainStatus=1`, `ActiveState=failed`. This establishes a failed scheduled attempt, not that every database lacks a valid older backup. The backup owner should determine the failure cause and the newest independently usable generation before relying on the nominal hourly RPO. No retry, repair or restore was initiated by this assessment.

## Findings

### INF-01 — Cloud provisioning is implemented for Hetzner, but provider acceptance and state operations remain open

**Acceptance:** create or adopt the exact reviewed resource in the intended account; detect drift; change capacity safely; recover interrupted operations; retire without deleting retained storage or another client's resource. Measure elapsed time, operator effort and cost against the client request.

**Source:** [Terraform module](../../../infra/terraform/main.tf) creates networks/subnets, SSH recovery firewalls, optional public IPv4 identities, servers, private attachments and protected retained volumes. Logical node and operation labels carry identity. [Variables](../../../infra/terraform/variables.tf) require an explicit machine type, region, image, SSH keys and positive estimate within a budget cap. [Provider lock](../../../infra/terraform/versions.tf) contains only Hetzner. Server types are configurable inputs, not a verified catalogue of every Hetzner node kind. Dedicated/bare-metal Hetzner provisioning is not established.

[Terragrunt configuration](../../../infra/terraform/terragrunt.hcl) is a pinned, source-free execution unit, not a hierarchy of client/account environments. [The adapter](../../../tools/tool-fleet/src/terraform.ts), [Terragrunt boundary](../../../tools/tool-fleet/src/terragrunt.ts) and [runbook](../../../infra/terraform/README.md) bind saved plans, exact binaries/configuration, variables, backend evidence, state lineage/serial and ownership. Lost-create-response import is modeled. Protected volumes and primary IPs are deliberately excluded from ordinary server destruction.

**Reconciliation:** [F4 tasks](../../../openspec/changes/k3s-fleet/tasks.md) and [verification](../../../openspec/changes/k3s-fleet/verify.md) explicitly leave the remote HTTP backend and paid-provider drill open; local Terragrunt smoke is narrower. Fresh Terraform/apply tests passed, including ownership and retained-resource refusals. No live backend encryption/versioning/atomic-lock readback or successful paid-resource lifecycle is established here. No AWS provider/resource definition was found under `infra`, `tools`, `deploy` or `.github`; this is a repository search result, not proof that PUNI owns no AWS resources.

**Consequence:** dedicated PUNI and client-owned cloud offerings require operational setup and verification before they can quote repeatable onboarding. A self-reported cost estimate is not billing attribution or a spending enforcement service. Bootstrap of an entirely new account/cluster needs its own proof; established-cluster provision tests are insufficient.

**Smallest next action:** Platform infrastructure owner inventories cloud accounts, resource identities, state backends and unmanaged resources without exposing credentials. Separately authorize a disposable provider lifecycle after reviewing its cost and cleanup boundary. Completion evidence: backend guarantee readbacks, exact saved plan/state/receipt chain, successful enroll and no-op reapply, controlled interruption/recovery, retained-resource survival and accounted cleanup. AWS work should begin with account-scoped inventory before deciding whether implementation is missing.

### INF-02 — Cluster lifecycle is deeper than general fleet lifecycle

**Acceptance:** every host has an owner, role, supported baseline, patch/reboot procedure, replacement/retirement path and maintenance evidence, including hosts outside Kubernetes.

**Source:** [desired fleet](../../../infra/fleet/desired.yaml) contains h4claw and h3mon only. [Inventory](../../../infra/ansible/inventory/production-existing-hosts.yml) preserves OpenHands on h4 and Victoria/Grafana/MLflow on h3. [Enrollment record](../../infra/enroll-h4claw-h3mon.md) explicitly keeps h2 outside k3s because production, registry, builds and the heavy gate share it; h1 retains operator credentials and the backup puller. These standalone roles remain essential to client delivery even though the cluster inventory does not model them.

[Base role](../../../infra/ansible/roles/base/tasks/main.yml) installs prerequisites, keys, chrony, journald/sysctl settings and swap policy. [Upgrade playbook](../../../infra/ansible/playbooks/upgrade.yml) upgrades k3s serially with drain and health checks. It is not an OS security patch/reboot rollout. [Maintenance](../../../tools/tool-fleet/src/maintenance.ts) returns plans for certificates, tokens, SOPS keys, control-plane expansion, registry recovery and forge replacement. No end-to-end standalone-host or whole-estate OS patch, image replacement, credential revocation or retirement workflow was established by the inspected files.

**Historical:** [enrollment verification](../../../openspec/changes/enroll-existing-hosts/verify.md) records h4 bootstrap/idempotence; [later operational reconciliation](../../infra/enroll-h4claw-h3mon.md) records both nodes Ready, but not all intervening join/validation summaries or the prescribed reboot/data-comparison evidence. It explicitly records that enrollment ran without provider snapshots; a configuration archive is not a whole-host restore point.

**Consequence:** all journeys and ownership models depend on manual operations outside the currently modeled cluster nodes. An assistant on h1 and a customer app on h2 cannot inherit a complete fleet SLA from k3s tooling. Existing administrator privileges retained during adoption also need an explicit client offboarding/ownership decision.

**Smallest next action:** Fleet operations owner records one inventory spanning h1–h4, future workers and client nodes, with account/asset owner, OS baseline, maintenance authority, patch age, reboot requirements, configuration source, backup scope and retirement evidence. First completion evidence is an accurate read-only inventory and one reviewed lifecycle procedure per role; execution requires separate authorization.

### INF-05 — Adding nodes does not establish application scaling or high availability

**Acceptance:** a representative client journey achieves agreed latency, error rate and throughput at an attributable cost; a defined failure or maintenance event stays within its availability/recovery target.

**Source:** [WBS backend](../../../deploy/k8s/wbs/base/backend.yaml) is one `Recreate` replica with a 5 GiB [RWO SQLite claim](../../../deploy/k8s/wbs/base/storage.yaml) and a host-local solver directory. [MCP](../../../deploy/k8s/wbs/base/mcp.yaml) is another single `Recreate` process with a [1 GiB persistent session store](../../../deploy/k8s/wbs/base/mcp-storage.yaml). Gateway and frontend manifests also start at one replica. [Release execution](../../../tools/tool-deploy/src/k8s/execute.ts) restores tier replicas to one. No application HPA, scale-out acceptance baseline or general stateful replication contract was established from these deployment assets.

The [production Elasticsearch manifest](../../../infra/platform/observability/elastic/production/elasticsearch.yaml) specifies one node, a 2 GiB heap inside a 4 GiB request/limit and 100 GiB RWO storage. [Registry](../../../infra/platform/registry/base/registry.yaml) is one `Recreate` replica with 50 GiB RWO storage. The [desired cluster](../../../infra/fleet/desired.yaml) is single-server, with product and ingress on h4 and observability on h3. These are multiple logical services, not independent failover domains.

**Prior intent:** [evolution plan stages](../../plans/2026-09-15-infra-evolution-plan.md) propose HA control planes, separate pools and a future PostgreSQL change when more backend replicas are required. Those proposals do not migrate the current SQLite application. Adding execution agents increases worker placement options; it does not increase WBS database write capacity or create distributed gateway/session semantics.

**Consequence:** scaling engagements need a measured bottleneck diagnosis before a node purchase. Vertical capacity, stateless replication, solver CPU, SQLite contention, disk latency, gateway/session behavior and database migration are distinct interventions. Guaranteed HA, regional failover, automatic database scale-out and arbitrary AWS/legacy-stack integration are outside the currently evidenced offer.

**Smallest next action:** Application performance owner defines one realistic client workload, baseline p50/p95/p99, throughput/concurrency, errors, CPU/memory/I/O, database contention and monthly cost. Compare one proposed change under the same workload and recovery/compatibility checks. Record the smallest improvement that meets the target; do not substitute a Kubernetes node count for client benefit.

For **new application launch**, accept readiness only after repository/environment creation, actual deployment, DNS/TLS/auth, monitoring route, recovery acceptance and operator handover all complete for that application. For **scaling**, require before/after workload and cost evidence plus compatible recovery, rather than provisioned capacity alone. For **personal assistants**, use the standalone-host lifecycle and state/credential backup criteria; the k3s worker proof does not install or operate OpenClaw.

The required input set is already partly encoded in [site inputs](../../../infra/environments/site-inputs.schema.json); missing commercial inputs include accepted service targets, incident owner, maintenance/exit authority, supported workload exclusions and cost allocation. Onboarding duration and manual effort are **unknown** for each production model. The operator guide's historical 53-second `app` lab startup and the 3m9s backup lab are narrow technical timings, not client-delivery lead times. Record request acceptance, completed inputs, engineering/operator minutes, blocked waiting and handover timestamps on the next authorized delivery.
