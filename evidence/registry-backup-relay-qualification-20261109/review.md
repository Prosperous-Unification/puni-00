## Claims supported

1. **Same encrypted repository, with real cross-backend consumers.** Both direct S3 and REST use the same responder prefix; the relay maps pack fanout explicitly and forwards the actual encrypted bytes. The first snapshot is taken from the direct S3 backup's returned ID, then required in the REST listing and checked with REST `check --read-data`. The second snapshot is created through REST, required in the direct S3 listing, and checked through direct S3. The fixed responder scope plus successful decrypting/checking consumers make the hardcoded `sameRepository:true` summary non-vacuous.

2. **Restores target the intended snapshots and compare actual content.** The second REST-created snapshot, first retained direct-S3 snapshot after the fault, and faulted third snapshot are passed explicitly to real `restore` commands into distinct target directories. The orchestrator reads each restored `owned-payload` and compares it byte-for-byte with its original known stdin body. Recorded sizes are 65,570, 65,565 and 65,571 bytes, respectively. These are REST-route restores; direct S3 supplies listings and read-data checks. Do not paraphrase the evidence as a separately executed direct-S3 restore. No production source traversal or journal dump is exercised.

3. **One observed upstream dispatch after a committed/lost response.** The standalone `probe-lost` uses the official SDK and the same custom handler as the relay. Its responder trace contains one complete 32-byte PUT and one retained version before the socket is closed. The call fails with `socket hang up`, SDK attempts 1 and one connection-factory invocation. The acknowledged control uses identical bytes. The wrong-CA control fails before any HTTP request reaches the responder. All 135 recorded handler exchanges have one factory invocation. This is an observed finite case, not a universal absence-of-replay proof.

4. **Genuine lost downstream POST reply and real retry cleanup.** `experiment.ts:101` destroys the downstream socket only after the upstream PUT promise succeeds. The raw pinned Restic log names the selected Save, reports `EOF`, and reports success after one retry. The relay trace is POST/lost, DELETE/200, POST/200 for the same key; the independent receiver trace is PUT version 1, DELETE marker, PUT version 3. The two 298-byte payload versions have the same ciphertext SHA256. The selected retained payload liability is therefore 596 bytes in this fixture model. No delay threshold or expected sleep duration determines success.

5. **Protected baseline retention is not masked by the receiver guard.** The baseline comprises six real visible config/key/pack/index/snapshot objects. The explicit baseline-pack DELETE returns 403; the final upstream trace contains no DELETE for any baseline key. Thus the relay refused before dispatch, rather than relying on the responder's independent protected-key rejection. The code compares baseline visible ciphertext hashes after the fault, checks the repository, and restores the exact original first snapshot. The final audit records all six objects unchanged and visible.

6. **Completed finite cleanup is supported.** Every recorded command exits zero; the helper is stopped, awaited and required to exit zero. Final receiver failures are empty; receiver and relay closure are recorded; `repairedCleanup` is false. The final process audit reports no survivors among its named owned groups, orchestrators and exact arguments. The byte audit records no remaining private key or Unix socket. The orchestrator's unconditional group cleanup is not itself a universal descendant-lifetime proof, but the separate final host observation supports the finite absence claim made here. Failed/repaired attempts 1–3 are excluded from the passing verdict.

## Interpretation and retained limits

The receipt's `retainedBytes:202368` is sampled immediately after the injected fault. The final audit's 203,078 bytes include subsequent check/restore lock versions. Those are different observation points, not contradictory accounting. The final audit records 29 archived payload versions and 13 delete markers. This review inspected the audit receipt and the executable comparisons; it did not independently rerun the auditor or rehash every archived ciphertext file.

TLS, pinned CLI commands, official SDK calls, Unix routing, encrypted bytes and socket closure are real within the owned experiment. S3 signature checking is only a prefix model; version storage/delete markers and the protected baseline are controlled fixture semantics. The prototype keeps baseline/created sets in memory and has no durable funding or authority state. Its finite request/body/time bounds characterize the experiment, not production resource guarantees.

Nothing here qualifies production store/admission/effect integration, debit-before-dispatch, concurrent budget safety, restart/crash liabilities, complete real-provider census, multipart/copy, retention/prune, installed credential isolation/non-bypass, source writer exclusion/visibility, privilege/namespace/queued descriptors, or independent resource enforcement. The one-connection raw CLI profile also does not establish concurrency behavior. A successful retained restore after retry cleanup is not a post-prune restore proof.

The evidence is suitable for archiving as immutable executed prototype text plus finite receipts, and for informing the next design slice. It is not suitable for adopting the prototype as the production relay or opening physical admission.
