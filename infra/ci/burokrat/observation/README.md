# Uninstalled Tool Wiki observation service

These files are a one-time provisioning artifact for the observation-only PR tick. They are not installed or enabled by this repository change. The observer can read GitHub pull requests and update its protected SQLite state; it cannot review, publish, admit, merge, or update the WBS. A service template does not establish independent bootstrap authority or live host acceptance.

An administrator must create a dedicated non-sudo `toolwikiobs` account and group. Install the reviewed Bun binary and bundled `observation-service-cli.js` in a versioned, root-controlled runtime directory such as `/opt/tool-wiki-observation/v1`. Place canonical `service.json`, the independently approved `bootstrap.json`, and an optional GitHub read token in a root-owned, non-writable trust directory such as `/etc/tool-wiki-observation`. The three protected files must be owned by the service UID, be regular files with one link, and have mode `0600`: both the service preflight and the state controller require that ownership for the bootstrap. Install the empty Bun configuration in the reviewed trust directory. Within the systemd unit, `ProtectSystem=strict` and the explicit read-only paths prevent writes to these files; their `0600` ownership alone does **not** make them unwritable by the service account outside that mount namespace. The service's only writable path **inside the unit** is a private service-owned `0700` state directory such as `/var/lib/tool-wiki-observation`; never place it under a candidate checkout or a replaceable parent. Keep the state database and observation lock in that directory. Do not grant this account publisher, reviewer, merge, or WBS credentials.

The service configuration is canonical JSON with `schemaVersion:1`, `stateDirectory`, `bootstrapPath`, the exact bootstrap `pin`, the fixed GitHub `binding`, finite `policy` and `cleanupMs`, and `credentialPath` (`null` for anonymous public GETs). Use the same exact values and independent pins that the trusted observation controller is approved to use. If a token is installed, its file contains only ASCII token bytes, with no newline. The service never reads `GITHUB_TOKEN`, `.env`, preload modules, or a candidate file as authority. Bun runs with `env -i`, `--no-env-file`, and an explicit protected empty configuration.

Prepare a reviewed layout JSON using the fields in `ObservationUnitInput` in [render.ts](render.ts). The layout binds the non-root account, runtime and trust directories, exact Bun, launcher, Bun configuration, service configuration and bootstrap SHA-256 digests, all protected file paths, and timeouts. The layout's tick and cleanup budgets must equal the values in the pinned service configuration; `startTimeoutSec` must exceed their sum and `stopTimeoutSec` must cover cleanup. Generate a bundle into a **new** directory:

```sh
bun infra/ci/burokrat/observation/render-cli.ts /protected/admin/layout.json /protected/admin/new-observation-bundle
systemd-analyze verify /protected/admin/new-observation-bundle/tool-wiki-observation.service /protected/admin/new-observation-bundle/tool-wiki-observation.timer
```

The bundle contains the uninstalled service and timer units plus `runtime.sha256`. The renderer refuses an existing output directory; inspect the generated bytes and compare them with the reviewed runtime, configuration, and actual file digests. It does not create an account, initialize the database, install units, set secrets, enable a timer, or bypass host policy.

In a separate authorized administrator step, create and migrate the protected observation database using the reviewed `initializeObservationState` and `migrateObservationRecoveryState` APIs with the exact service configuration. Do this before any timer starts. The observer itself calls neither API and refuses absent or old state. Test the pinned executable and bootstrap, verify directory owner/mode and service-account read/write boundaries, then install the reviewed unit files and enable the persistent timer only under the host's approved change process. The unit checks the runtime hashes before each tick, retains exit codes, has no restart loop, and leaves cross-process exclusion to the durable observation lock. A busy or deferred tick exits 75; failure and cancellation remain non-success. Never delete a stale-looking lock to force progress.

Host acceptance still must show the actual service account, immutable runtime/trust pins, protected directory ownership, systemd syntax and effective sandbox properties, timeout/termination behavior, DNS and fixed-origin HTTPS GET, timer restart/recovery, database backup/restore, and failure diagnostics. No such host acceptance has been performed here.
