# API-model unresolved recovery connection

`reconcileApiActivity(runs, artifacts, {executor, selection}, guard, commandId, signal)` returns `recorded` with the original `applied|duplicate` acknowledgement and attempt, `refused` with existing StoreRefusal, or `cancelled` with the unchanged attempt. Cancellation means no recovery query was dispatched; it says nothing about physical work. Operational errors throw `ApiRecoveryError` with detached preparation/locator and original cause.

The adapter/SelectedActivity association belongs to trusted factory composition. The helper compares its full bindingDigest/requestedType/matchedType/stepCode/className selection projection against verified retained history, and checks actual executor kind/version and all seven unsupported capabilities. It cannot introspect an opaque adapter's configured selection or detect a composer falsely pairing an executor and descriptor. Real tests construct both from the same accepted selection. A wrong composer could misattribute unsupported observation; this path cannot start, stop or release work. Root explicitly accepted this existing-port limitation on 2026-11-05.

Before awaiting, decode and detach AttemptGuard, command ID and accepted selection projection. Delegate artifact/history validation to claim-history.readExecutionHistory. Only version2 active preparing/prepared/claiming/ready/turn_pending/turn_returned checkpoints, directly or inside reconciling/unresolved, are supported. Queued, settled, version3 logical recovery and version4 write attempts return state_conflict. Check exact submitted run/attempt revisions before a fresh query. Extract preparation/locator from that checkpoint; verified history owns its full correspondence.

A previously retained command must be an unresolved execution fact with reason unsupported and exact reply bytes decoding to the corresponding strict unresolved/unsupported preparation or locator shape. Reverify those bytes and correlation, then delegate the exact original command to recordExecution for provider-owned target/content/owner replay. No renewed lease, external query or new artifact occurs on replay; current provider ownership still authorizes it.

A takeover or intervening write therefore refuses publication. Await durable acknowledgement before returning recorded.
