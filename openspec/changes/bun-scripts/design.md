## Context

An initial read-only scan at d49fdad84 found 302 candidate files: 256 runtime candidates, 22 verification candidates, 3 historical candidates, 14 browser candidates and 7 configuration candidates. This is a seed, not a completeness proof: filename/shebang/main detection misses generated script strings, inline CI/Ansible logic and unrecognized entrypoints. `script-inventory.md` retains the seed and the limitations; executable acceptance requires the complete consumer inventory.

## Goals / Non-Goals

Convert all first-party executable logic to Bun, including internal CI/dev/gates, while the linked `puni-cli` change embeds client operations. Preserve ownership, trust, process lifetime, argument boundaries and safety behavior. Browser code, third-party executable implementations, declarative configuration and historical evidence are not language-port targets.

## Decisions

**B1. Scope assumption.** The broader reading of the request includes first-party internal scripts, not only shipped client scripts. Runtime entrypoint content and active consumers determine scope, not extension alone. A Bun-supported `node:` import is supported library usage, not a Node executable requirement.

**B2. Inventory ownership.** Track each executable's owner, current runtime/callers, replacement, client exposure and verification. Include package/Nx/CI/container/Ansible callers, remote payloads and generated helpers. Classification and validation are production code with controlled fixture repositories that exercise unknown/new/generated entries. Historical/adversarial script bytes are explicitly modeled test inputs; they are not accepted as new active shell implementations or shipped client launchers.

The inventory foundation captures an independent Git/worktree file universe before finite package/Nx/GitHub collectors discover execution sites. Each site retains its structural location, exact body digest and execution context; declarations reconcile against discovery and cannot select the scanned universe. Symlinks/gitlinks and dynamic/compound bodies remain explicit boundaries. Coverage of generated, remote and infrastructure execution requires their later collectors; a complete declaration list for the initial collectors does not certify Bun compliance or complete repository coverage.

**B3. Process behavior.** Use Bun process/file APIs with explicit argv and environment. Model success, expected nonzero outcomes, cancellation and bounded convergence explicitly. Missing required tools and malformed/unreadable trusted state fail. Keep secret-bearing input out of diagnostics. Preserve signal forwarding, child ownership and cleanup across process trees; a port that only spawns the old shell/Node body is incomplete.

The existing FileSink owner moves to `@shared/bun-output`; Burokrat keeps its old aliases and diagnostic prefix. Its native tails, cancellation and one-shot bounded diagnostic remain shared. A narrow `failWrites` capability lets Dash end a pending API write after its admission/status budget while stopping queued writes, unreferencing sinks and observing any native tail. Root completion requests terminal exit only after those owners and queue cleanup settle. Native wait errors are explicitly unconfirmed: report once through the bounded owner and retain the live queue callback, signal listeners and a referenced wait. Only trustworthy native termination permits status settlement and release; unresolved authority requires operator intervention.

**B4. Gate ownership and locking.** Port gate and heavy-lock semantics together before switching callers. Retain checkout under the host-wide lock, complete pinned-SHA receipt, frozen install, required full checks, queue bounds, permission/dirty-tree refusals and cleanup on cancellation. Use host-supported exclusive-lock primitives through an explicit owned process/descriptor lifetime rather than an existence-only lockfile. Rehearse competing processes and injected child/cleanup failures.

The shared Bun adapter `@shared/heavy-lock` gives Dash and tools the same native mutex/epoch primitive without product-to-tools imports. Its `holdLock` callback owns the descriptor through settled work; queue/status code owns the existing record protocol and canonical path selection. Native loading is lazy, and unsupported ABI, missing symbols, malformed native responses and close failures refuse rather than selecting another locking mechanism. FFI remains a pinned runtime/platform qualification boundary; a passing Linux probe does not establish another platform or permit a caller switch.

Queue cancellation stops admission promptly, but never races already-entered work or releases its mutex early. Status reports records, including claiming/pre-queue/corrupt PID observations, without certifying kernel ownership or reclaiming entries. Queue admission validates active metadata, retains arrival counts separately and still attempts once at a zero budget. Only ESRCH proves a dead process; the shell's EPERM-as-stale assumption is tightened to refusal. Known cleanup actions are attempted independently under flock and failures throw with retained causes, replacing the old EXIT trap's diagnostic-only cleanup policy. Production path selection remains separate from explicit fixture paths.

The executable foreground adapter is owned by Dash as `puni dash ops lock status` and `puni dash ops lock run ... -- <argv...>`. It shares the typed Bun queue/status operation with repository callers. Work receives its first-arrival count and elapsed whole seconds after admission, before payload entry. Production fixes the canonical inode; fixture paths stay below that boundary. INT/TERM withdraw queued work; active foreground work settles before the holder returns its first interruption status. The payload retains native IO, caller cwd and environment. A holder-targeted signal does not automatically kill its tree. Killing the actual mutex owner can release flock while descendants remain and never proves their absence. Dash's separate detached hold-file owner must survive frontend death until compute/watch settlement; it is not replaced by the foreground owner. Gate shell callbacks and current defaults stay until their Bun implementations and installed callers are verified.

The first source-level checkout primitive executes wholly inside native admission. Its caller supplies an independently captured trusted absolute Git executable, immutable full commit and captured absolute lookup PATH. Git runs with only that PATH and explicit controlled Git settings; arbitrary caller and later full-step environments are not preserved implicitly. The selected canonical filesystem directory must equal Git's effective working-tree root, compared without trimming pathname bytes. Discovery, checkout, status and recovery disable hooks/fsmonitor and ambient Git overrides. Effective executable filters and gitlinks in the committed original and target trees refuse before helper-sensitive operations; status explicitly ignores submodules. This does not claim an independent index scan or recursive submodule verification. No fetch/network authority is supplied, and stable cooperating metadata/parent directories remain a premise rather than a hostile-filesystem sandbox.

The operation retains a referenced executable owner through pending work and owned report/release settlement, including when no child or other native event-loop handle exists. Work receives a closing direct-child launch capability. After work returns or fails, new launches refuse and all launched direct children and owned IO settle before restoration or release. Missing or erroneous native terminal evidence retains ownership and visible diagnostics; neither numeric status nor a deadline establishes termination. This is not yet the complete install/Nx/pool process-tree owner: those adapters must establish required descendant settlement before composition. A direct child exiting does not establish that its descendants ended.

Successful keep-mode work retains the selected checkout; explicit restore-mode work restores on success as well. Failures requiring recovery are handled while still admitted. Recovery independently verifies the saved full commit and symbolic reference. A moved/deleted original branch is never reset; recovery attempts the saved commit detached and reports74. Failed restoration retains74 precedence with independent primary/report/release failures. After the admitted callback settles, a queue/native-close failure returns a nonpassing release outcome70 and cannot initiate rollback outside ownership; the settled keep or restored tree remains. A first interruption recorded only during that late release phase likewise cannot start post-release checkout recovery. Temporary umask022 is restored under the dedicated executable-owner premise. Canonical shell callers and parent2.2 remain unchanged.

Signal semantics refer to the first recorded interruption, not first wall-clock delivery across synchronous Git. Every modeled returned outcome carries an independent first-control observation: none, native SIGINT/SIGTERM, or independent external cancellation with its original opaque reason. An external Context.signal is not a second native-signal adapter. Handlers remain through owned work, recovery, reporting and release. Synchronous Git cannot process JavaScript cancellation promptly; an event-loop checkpoint services queued callbacks before discarding handlers. Status precedence is restoration74, operational/report/release70, then an existing nonzero work/refusal status. First recorded interruption supplies130/143 only when status would otherwise be0. Its independent observation remains available even when a primary failure wins. An interruption first recorded after callback settlement preserves the already-settled tree without post-release Git operations.

A first interruption recorded at the final checkpoint inside the admitted callback still requires recovery before callback capture. Recovery is rechecked through a one-shot latch; newly created recovery/report failures settle before return. Every independent child nonzero observation contributes its own failure even when work or an earlier child already selected the status. Restoration74 denotes an actual failed recovery, not an ordinary work exit74.

**B5. Deployment recovery modes.** Ordinary additive migrations keep full applied-name/hash capture and exact-addition reversal with final ledger comparison. Explicitly approved stop-the-world windows retain their specified snapshot/previous-code restoration sequence and writer exclusion; they do not attempt ordinary additive rollback. Every failed recovery is loud and names the pinned manual completion procedure. Language conversion changes no migration policy.

**B6. Trusted toolkit and remote bootstrap.** Coordinate the Bun launcher with `puni-cli`'s new artifact identities; historical trusted bytes retain their old identity. Remote first-party scripts require Bun before execution, without a hidden Bash fallback. External tools remain explicit prerequisites, and their exit codes prove only their documented contracts. Bootstrap, installation and generated payload tests exercise the delivered bytes and path selection.

## Risks / Trade-offs

Locks, signals, shell quoting, env inheritance and working-directory assumptions are behavior, so direct translation without process-level tests is insufficient. First-party shell fragments hidden in YAML or generated strings require consumer traversal. Tests that intentionally supply hostile/historical scripts need explicit fixture classification without a broad executable exemption.

## Migration Plan

Complete inventory and production coverage guard, introduce shared process/file primitives as their first consumers require them, then port gate/locks, development/release operations, trusted toolkit/bootstrap, infrastructure/remote/application operator scripts and verification runners. Switch each consumer only after its controlled rehearsal and negative proofs pass. Embed client operations through `puni-cli`. Finish with an active-consumer census and exact-commit gates; remove old active script bodies only after callers move.

## Open Questions

None blocking implementation. B1 records the proactive scope assumption. Host-specific observations and actual activation receipts are verification work, not assumed from local tests.

The C32 Bun compatibility entry decodes the former status / -- argv boundary into the same Dash owner. The existing shell default and gate callbacks remain until their coherent caller conversion. Optional unset/empty legacy queue variables retain Bash parameter-default behavior. Wait input now requires canonical nonnegative safe decimal integers rather than accepting unchecked Bash arithmetic; poll keeps its existing canonical one-through-thirty bound. No environment key redirects the canonical mutex. Decode runs inside the executable owner so usage failures also receive bounded output and cleanup.

Refusal-time records are informational observations captured before ticket cleanup: earlier ticket labels/PIDs (including an explicit vanished state), or the observed holder PID publication. They do not certify kernel ownership. Native Linux lifecycle controls cover queued INT/TERM withdrawal, holder-only first-signal deferral, inherited process-group signals, missing/nonexecutable payloads and real FileSink backpressure/closed pipes. The rejected-wait fault lives beside the existing tool-devsync isolated subreaper supervisor; its own descendant cleanup completes before fixture deletion, avoiding a Dash-to-tool dependency cycle. These local controls do not qualify installed artifacts, other platforms or host gates.

The detached holder uses a hidden, versioned operation in the same selected protected PUNI artifact. The controller exclusively reserves an owner-only physical diagnostic log; both helper outputs inherit that one descriptor. Fixed typed operands pin the controller's full PID/boot/start identity independently of diagnostic bytes. The child publishes its own immutable full birth token before queueing. A second exclusive token pathname carries a tagged decision: Ready names the admitted child's full birth, Cancel names the withdrawing controller's full birth, and Retired names the child whose ledger-authorized unready hold was withdrawn. They compete by exclusive publication, so cancellation or retirement cannot replace a Ready winner. The existing child hold bytes remain unchanged. Every decision retains its tag and identity through confirmed termination and authorized generation cleanup. A Ready winner survives frontend interruption and frontend death; release requires the compute ledger's authorization. Diagnostic text, parent liveness and numeric exit promises alone grant no release or cleanup authority.

Actual native termination is observed independently of numeric status. Missing or erroneous native termination retains unresolved authority; numeric disagreement fails completion while an error-free native termination permits independently authorized cleanup. A retained child can settle after verified removal of its unchanged original hold token or an explicit native signal, preserving the failure. The parent's exit projection is lazy so unattended durable holders do not produce unhandled rejection promises. Restart adoption, same-identity ledger idempotence, pending watcher shutdown and readiness-qualified new admission must be converted with the actual callers before the old default is removed. Previously admitted legacy Bash holders need a separate continuity/drain rule: absent new readiness evidence alone does not prove their old flock was lost.

Fast refusal can finish before a live birth observation. After an actual error-free native-end callback only, cleanup can derive the full token from the selected protected producer within the exclusively reserved, unchanged physical log generation whose token/decision absence was rechecked before spawn. It still checks child PID, controller boot, any captured live birth and exact previously observed inode/bytes. This is generation-derived producer authority, not independent observation of the deceased start time; live handoff and restart adoption cannot use it. Replaced known evidence remains retained. A first withdrawal reason is latched, and a throwing reporter does not bypass independently authorized terminal cleanup.

Watcher ownership is asynchronous and serialized. Shutdown aborts and awaits pending acquisition through its terminal cancellation or Ready handoff before closing the runtime ledger. A Ready helper outlives that frontend. A restarted watcher first reconciles the existing namespace and full live birth; pre-ledger Ready can be adopted only with the exact child hold and canonical PID/label. The selected fully namespaced helper prefix and injected wall/monotonic clock ports are captured before asynchronous resolution.

Guard adoption and retirement use the same immediate SQLite write fence as admission. Recording the same full birth and mutex is idempotent and retains the original since instant. A refused handoff cannot release a concurrently adopted shared holder. Retiring a recorded unready legacy guard requires all admitted compute to have settled, irrespective of queued demand; retiring a qualified settled guard additionally rechecks queued demand. Retired is published before removing the exact child token, leaving the full child identity available after a controller crash. The holder checks withdrawal before publishing Ready, including callback entry after immediate acquisition. A known live legacy guard keeps continuity for already admitted work while new admission waits for current Ready.

An ended recorded guard is a separate recovery case: full original process termination permits replacement even while compute remains charged. The controller first commits lost-authority attribution to every unreleased job without changing reservations or compute state. It retains the matching full database record through physical cleanup and clears only that same birth and mutex afterward. A zombie leader beside live threads has not ended. Unreadable or malformed process inspection remains a failure.

Cleanup removes the private physical log generation before the final complete helper identity witness. Cancel needs the child hold as that witness; Ready or Retired can be the final witness after the hold is absent. A cleanup failure or crash retains sufficient identity for retry. A restart snapshots the current generation only after qualifying the full helper as ended; it makes no claim to possess the original controller's historical inode snapshot. A legacy log-only generation can be cleaned under the database write fence using its matching qualified dead record as the final witness. A log-only generation without that identity, an unknown basename, a replaced token or an unreadable generation blocks automatic cleanup visibly. Confirmed-end overlapping reconcilers may observe an already completed cleanup; live evidence disappearance remains strict.

A healthy native generation still queued behind another canonical owner retains its turn while demand remains, including after frontend death. It may later publish Ready for restart adoption; absent Ready before acquisition alone does not make it a legacy admitted guard that needs retirement. Removing its turn on a periodic grace timer would lose FIFO position without advancing admission.
