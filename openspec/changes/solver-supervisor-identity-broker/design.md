## Goals / Non-Goals

Establish effective supervisor identity for the just-installed invocation while preserving the existing admission boundary. This packet implements only disposable startup experiments. No production service change or activation/adoption claim follows from its checks.

## Decisions

1. **Execution closure.** Keep one canonical constant Bun `-e` bootstrap used by unit generation and expected-argv comparison. Read the bundle once, hash that Uint8Array and return the same object from `Bun.plugin` onLoad. Use a dotted private relative specifier with onResolve redirect; the prior pinned-runtime spike found bare specifiers unsuitable. Explicitly call the bundle's exported decoder and entrypoint; `import.meta.main` is false. Read config once, hash that buffer, decode that buffer and pass the decoded value into startup without a second pathname read. Read/hash the executing runtime through `/proc/self/exe`. Scan the built single ESM bundle and refuse non-builtin residual imports; `--no-install` alone does not close resolution.

2. **Startup policy.** Candidate direct-Bun argv includes `--config=/dev/null --no-env-file --no-install -e <literal>`. Use an explicit trusted cwd. Remove startup injection and dynamic-loader environment before Bun exec. The measured inputs are cwd `bunfig.toml`, cwd `.env`, `BUN_OPTIONS`, `LD_PRELOAD`, `LD_LIBRARY_PATH` and `LD_AUDIT`. Tested `NODE_OPTIONS=--require`, `BUN_CONFIG=<path>` and `BUN_CONFIG_PATH=<path>` had no preload effect; do not invent a config environment API from their names. Global-home config probes here also had no effect in this invocation form. No result establishes that every BUN_CONFIG variable is inert.

   The spike proves a clean child environment plus explicit flags blocks measured faults; it does not prove a systemd unit environment policy. For the direct-Bun unit, start with explicit `UnsetEnvironment` entries for measured executable inputs and conservative `NODE_OPTIONS`/candidate config inputs; enumerate and verify permitted Environment/EnvironmentFiles/PassEnvironment/UnsetEnvironment and manager inheritance in the disposable unit round-trip slice. `Environment=` alone is insufficient. systemd has no assumed wildcard clear-all here. If this cannot establish the bounded startup environment, stop for design review rather than silently inserting an `/usr/bin/env` wrapper: that changes the canonical executable/argv, and loader input can affect the wrapper before it clears the environment. Linux loader/system runtime integrity remains a host trust boundary; `/proc/self/exe` is not a libc attestation.

3. **Boot report and readiness.** An invocation-lifetime host-private observer directory/listener is distinct from the backend-visible public socket. Each installer or broker query uses a fresh unpredictable observer nonce and bounded connection-local state; the observer remains available for repeated and concurrent queries throughout the invocation. Retain nonce handling entirely host-side; never place nonce in world-readable unit argv or public frames. After config admission, orphan sweep and public listener establishment, the supervisor answers the private challenge with a bounded closed report of nonce, protocol version and bundle/config/runtime hashes. Completing or refusing a query closes only that query connection and discards its nonce/state; it never unlinks the observer listener. Invocation shutdown closes the listener and removes only its owned private socket/directory, reporting cleanup failure; replacement must not leave an old listener serving. For the host installer, authenticity comes from connected-client kernel SO_PEERCRED, expected host UID and systemd MainPID, not report fields. The host installer also connects to the public listener and authenticates its kernel peer before accepting the report. These two host probes stay bound to MainPID.

   The backend client cannot compare a host MainPID inside its private PID namespace. Keep rejection of PID 0 and UID-only/payload identity. Prefer the root-owned online broker and TLS protocol below, subject to gates 1.2/1.3 and privileged provisioning proofs. The host installer's two MainPID/UID probes remain mandatory and separate from backend authentication.

4. **Effective manager anchor.** Resolve the named unit with typed D-Bus GetUnit, then decode closed Unit/Service property responses. Include ExecStart's executable/argv tuple, MainPID, InvocationID, effective UID, FragmentPath, DropInPaths, NeedDaemonReload, ActiveState/SubState and the startup-policy properties. Check exact expected executable/argv and admitted effective property values; file text and `systemctl cat` are not this anchor. Define stable identity fields independently from volatile timestamps. Snapshot before both connects and after both connects. PID/InvocationID instability discards all connected evidence, then retries the whole observation within a fixed absolute deadline; a new nonce belongs to each new observation attempt. Per-call timeouts consume that same budget. Missing/null/malformed properties, credential failures and unexpected effective config fail rather than default. Final installed hashes of all four payloads must match, still under the same edge lock, before reporting identity success.

5. **Root trust and publication.** The [proposed ADR](../../../docs/adr/0062-root-authority-publishes-live-supervisor-identity.md) records the preferred ownership decision and alternatives. Install an independently protected broker runtime/bundle at `/usr/local/libexec/wbs-solver-identity/{bun,identity-broker.js}`; every ancestor and target must be root-owned and protected against supervisor-UID write/rename/symlink replacement. Never execute the user-owned supervisor bundle as root. `/etc/wbs-solver-identity/admission.json` names one approved service/UID, exact startup policy, Bun/bundle/config/unit hashes and fixed probe paths. Only an authorized root provisioner may publish that baseline atomically with readback; the broker cannot change it or auto-adopt observed hashes. A candidate/installed mixed tuple refuses rather than granting adoption.

   `/etc/wbs-solver-identity/broker.key` is root-owned 0600 and separate from supervisor invocation keys. Root-installed public pin `/etc/wbs-solver-identity/public/broker.crt` is protected by every ancestor, not just file mode. The backend receives only that public directory and broker-owned runtime directory `/run/wbs-solver-identity/`, as separate read-only directory mounts at `/run/wbs-solver-identity-trust/` and `/run/wbs-solver-identity/`. Socket connect permission does not imply directory write permission. Preserve runtime directories across socket replacement. No private key, admission baseline, systemd bus, host /proc, cgroup or Docker socket is mounted into backends. Root runtime and pin rotation are privileged versioned operations, with explicit client rollout/readback and temporary refusal permitted; they are not broker API operations.

   Broker startup gets its own explicit pinned-Bun environment/config/cwd policy and generated system-unit proof. It may observe the fixed user manager, probe fixed sockets and read fixed admitted files; no Docker calls, service lifecycle, installed writes or activation. Do not assert a capability-free process can read the supervisor's 0600 config. Proposed filesystem/socket-family/capability restrictions must be proved against the actual required reads and D-Bus path. The broker never acquires edge.lock: installer restart/proof already holds it, so a nested broker/ExecStartPost acquisition would deadlock. Root baseline publication has a separately authorized atomic provisioner operation; changing/inconsistent baseline makes observations refuse.

6. **Fresh online broker observation.** Generate a fresh in-memory private key/certificate for each supervisor invocation after captured-code startup admission. Include its public certificate in the private boot report and configure that same key on the public TLS listener. Do not persist/export the invocation private key. Select and pin a maintained bundled certificate-generation implementation in its production slice; a disposable openssl subprocess is not that decision.

   The broker exposes only a bounded TLS JSON-line session with two closed request types. `resolve-current {version, nonce}` uses 32 random bytes in canonical encoding and returns `{version, nonce, observationId, invocationId, certificate, artifactIdentity}` after a new stable observation. The observationId is unpredictable and connection-local. `confirm-current {version, observationId, nonce}` uses a new nonce and returns `{version, nonce, observationId, invocationId, certificateDigest}` only after another new observation confirms the session's invocation, certificate and approved baseline. It is single-use and closes the broker session. No caller-supplied unit, path, PID, command, policy or expected hash is accepted. No live-state success is reused to answer a new resolve/confirm.

   Each observation brackets a fresh connection/challenge to the invocation-lifetime private observer and a public TLS connection with typed D-Bus snapshots. Concurrent queries keep distinct bounded nonces/state; installer success does not consume or remove the observer used by later broker observations. Both host-connected peers must equal expected UID/MainPID; public leaf DER must match the reported invocation certificate; captured hashes must equal root-approved baseline; stable InvocationID/MainPID/startup policy must agree before/after; final installed four-artifact hashes must match. Broker observations never send solver start. Public TLS host probes are explicitly zero-work connections, distinguishable before backend cgroup/start admission, with no solver authority. Private host challenge and backend nonces are distinct. Broker restart destroys session observations; absent or hung broker never falls back to a cached expectation.

7. **Backend per-attempt protocol.** Read/validate the root-installed broker pin at its fixed boundary. On one broker Unix TLS connection, require completed successful handshake, no authorization error and exact leaf DER before sending resolve-current; `open` alone permits no application write. Validate the closed resolve reply, nonce/version, certificate bounds and identity. Connect to the solver Unix TLS listener using the returned certificate as sole CA and exact leaf pin; no session cache, 0-RTT, early work or plaintext fallback. Exchange bounded `hello`/`hello-ack` carrying a fresh per-connection nonce and expected invocation, without a solver request or authority options. Supervisor retains its existing kernel peer/cgroup/container caller admission before work; host zero-work probes follow their separate narrow state.

   On the still-open broker TLS session send fresh-nonce confirm-current. Only exact confirmation releases the existing start frame on the already authenticated solver connection. Supervisor also checks its invocation and per-connection handshake state before runner/create/attach/start. `SolverSupervisorConnect` must resolve only after TLS pin, hello and confirmation admission, not merely Bun.connect completion. Unexpected early frames refuse instead of implicit buffering; bound frame bytes, pending states and concurrent broker observations. Failure closes both sockets and rejects pending promises. Existing bind/abort, SQLite fencing, child deadline and Docker lifecycle remain intact.

   A byte relay cannot forge the pinned TLS endpoint; a foreign host relay also fails existing caller PID/cgroup admission on its upstream connection. Test both. TLS does not identify the immediate kernel peer when an authorized same-container process relays traffic; this remains within that authorized caller boundary. No claim expands to hostile supervisor-memory access or root-equivalent Docker-group compromise.

8. **Restart/race bounds and deployment wiring.** Each invocation changes its key. A cached A pin cannot authenticate B; resolve(A) then confirm(B), a baseline/policy change observed through the final confirmation observation, broker restart or unavailable/raced refresh refuses the whole attempt before work. Retry only modeled restart instability from a new broker session/resolve with new nonces; malformed authority, pin failure or unreadable trusted material refuse immediately. Proposed initial limits, to measure before acceptance: one absolute client deadline capped by remaining childDeadlineAt and 3 seconds, at most three whole attempts, each subcall at most 750 ms and never beyond remaining global time. Broker independently bounds calls/sessions/concurrency. Baseline/policy freshness ends at the final confirmation observation. A baseline/policy update after confirmation while the authenticated supervisor remains alive does not instantly revoke that already confirmed connection; its start may proceed within the existing deadline and connection state. Subsequent resolve/confirm must observe the updated authority and refuse any now-unapproved tuple. Confirmation is a finite observation point, not an atomic promise against all future baseline/policy updates or restart instants; no serialized online revocation mechanism is introduced. If the admitted process dies after confirmation, its authenticated connection dies; reconnect requires new admission. Prove single-main-process shutdown with no surviving listener/key-bearing children, including restart after bound; stronger instantaneous serialization is not claimed.

   Docker dev currently has a read-only stable solver-directory mount; preserve it and add distinct read-only broker-runtime/public-trust mounts. Apply the same contract to generated production Compose and deployment validation, not dev alone. Never place a rotating supervisor pin in backend startup env; configure only fixed trusted paths and refresh online.

   k3s base `deploy/k8s/wbs/base/backend.yaml` currently omits readOnly on solver-runtime while dev overlay sets it. The future slice must explicitly make base solver mount read-only and add separate Directory hostPaths for broker runtime and public trust, read-only and without subPath inode pins. Update generated dev-environment mounts, admission policy and desired/live first-start validation together. Root-provision each eligible node; scheduling onto an unprovisioned node refuses rather than borrowing another node's identity. Preserve and separately test the containerd/workload caller identity branch; Docker PID/cgroup assumptions do not establish k3s admission. Prove directory-mount survival through broker and supervisor restarts on both deployment paths.

## Risks / Trade-offs

The broker is a deliberate privileged component and online availability dependency. Root provisioning, kernel/user-manager integrity, protected runtime/trust paths and supervisor process memory are trusted. Same-UID public-socket replacement remains a rejection case; arbitrary Docker-group/root or memory compromise is outside this contract. Pin publication does not solve root-equivalent compromise.

Private readiness alone cannot authenticate a distinct public listener. Independent D-Bus reads are not an atomic snapshot; before/after convergence is required and cannot promise resistance to a hostile system manager. PID reuse is narrowed by InvocationID, live connections and bracketed observations. Active service plus existing socket is insufficient. `bun:ffi` still loads host libc; this design attests Bun's executable and captured application/config bytes, not every mapped library or a compromised kernel/user manager. A root/same-user attacker able to modify trusted manager/runtime state exceeds the cooperative deployment lock boundary; a foreign listener merely sharing the expected UID is still an explicit public-client rejection case.

## Migration Plan

Implement production TDD slices only after gates 1.2 (actual generated unit policy) and 1.3 (namespace-compatible authentication/expectation refresh) are proven and reviewed. Keep existing external-dependency dormancy and existing installer failure semantics. Version any new private/public identity exchange explicitly and refuse absent identity support; never fall back to old active/socket checks. Provision root broker authority before enabling upgraded clients; never auto-adopt whatever bytes are installed. Baseline transitions may temporarily refuse work, never accept mixed tuples. Validate protocol-version compatibility and desired/live mounts before rollout; old incompatible clients refuse explicitly. Root-provisioning credentials and separately authorized exact-SHA host acceptance/live rollout are later gates. No production rollout is included here.

## Open Questions

The actual direct-Bun systemd environment projection and literal argv round-trip remain unproved. The preferred broker protocol still requires real Docker/k3s, root-path protection, generated supervisor/broker unit policy and restart/refresh proofs; the host installer MainPID probes remain mandatory. The exact typed UID observation also remains unproved. These are implementation gates with refusal on failure, not permission to weaken the contract.
