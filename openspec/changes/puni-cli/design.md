## Context

At `origin/main` d49fdad84 the three CLIs already use Optique 1.3.6. They expose `navigatorParser`, `dashParser` and Burokrat's `installedGrammar.parser`. The installed Burokrat grammar differs from its source validator grammar. Dash performs additional coherence validation after parsing and keeps a lazy MCP-token execution path. Burokrat verifies a packaged toolkit and then executes its validator or hashed launcher. Application/product lint boundaries forbid unrestricted app-to-app imports.

## Goals / Non-Goals

Compose a discoverable, installable PUNI command without changing who owns planning, static judgment and runtime effects. Embed client operations, preserving existing failure, trust and startup contracts. Historical records remain verifiable; source checkout paths and legacy binaries are absent from the final client interface.

## Decisions

**C1. Public spelling.** The user-specified canonical namespaces/aliases are binding. Optique is the intended library, consistent with ADR 0064. Root-only usage failures exit 2; known namespaces retain their existing exit contracts, including Dash non-release `ops` exit 64. Diagnostics identify `puni` and the selected canonical namespace.

**C2. Composition and ownership.** `apps/puni/cli` owns the root parser, dispatch and installation. Existing providers publish separate grammar and runtime facades through exact `@puni/<tool>/grammar` and `@puni/<tool>/runtime` aliases. Their implementation remains provider-owned. `apps/puni/eslint.product.mjs` follows the existing judge-facade precedent: exact grammar aliases only for root grammar composition, exact runtime aliases only for dispatch, and a separate packaging facade only where the builder requires one. All inherited ring/runtime/product/scope constraints remain in force. A real boundary fixture must reject private provider imports and runtime imports from the grammar file.

**C3. One grammar.** The root composes real typed grammars through Optique commands with aliases, not remainder-argv forwarding. Complete the seven delegated Burokrat grammars from `twilight-cli-optique` 3.4. Dash's current coherence rules become a shared validation function invoked by every executor path. Context-aware formatting supplies the actual invocation prefix rather than rewriting an already formatted error string.

**C4. Import-safe execution.** Provider startup moves behind `import.meta.main`; exported executors accept typed requests and explicit invocation context. The root dynamically imports only the selected runtime. Burokrat uses its installed executor and verified toolkit boundary, never a direct source-validator shortcut. Navigator remains offline; Burokrat grammar/help reads no clock or authority state. Tests inject external IO only at existing boundaries.

Dash handlers and its reusable dispatcher return explicit numeric statuses; ordinary completion returns0 and resources/ops preserve their lower-level status. The standalone and PUNI executables assign that returned value. Library execution never saves, restores or derives a status from process.exitCode, so sequential and overlapping invocations remain independent.

**C5. Installed runtime.** The PUNI builder creates Bun-targeted assets from the provider facades, alongside their required non-code assets and trusted dependency closure. Paths resolve from the installed artifact. The public package exposes only `puni`; new package/release names use PUNI. Transitional old entrypoints exist only while callers migrate and are removed from final bins/current client docs.

**C6. Helpers and secrets.** Pool import receives the shared protected launch prefix: `/usr/bin/env`, explicit removals of the four startup variables in C10, the selected `process.execPath`, `--no-env-file`, `--config=/dev/null`, the installed entrypoint and canonical `dash`; it appends `mcp token`. Direct Bun-plus-entrypoint invocation bypasses shebang controls and is forbidden for generated helpers. Alias choice does not leak into generated integrations. Preserve shell quoting for external client configuration formats that require a command string; the first-party executed helper itself is Bun. Exercise the actual stored invocation with paths containing spaces and secret sentinels.

**C7. Trust migration.** The Bun launcher/bootstrap port is coordinated with `bun-scripts`. Changed role bytes produce new toolkit/release/activation identities; changed layout or execution semantics also require an explicit format version; supported historical decoders verify old bytes without relabeling/re-hashing them as a new release. Installed validation, trusted-toolkit closure checks and candidate isolation remain before execution. Tamper and candidate-controlled-environment negatives must survive through the packaged root.

**C8. Client inventory.** Client exposure means an operation appears in current installation/operation instructions, is emitted into a client integration, or ships as an executable asset. Such operations get an owning namespace and installed-artifact test. Internal development/CI/gate scripts still convert to Bun under `bun-scripts`; no operation is omitted merely because its old entrypoint lived in `tools/` or an application directory.

**C9. Verified Burokrat process boundary.** Astra's source review selected a one-shot versioned JSON request on stdin to the verified Bun validator child. The bridge is part of the hashed validator role, accepts only the installed validator request union (excluding source-only commands), reads raw stdin with fatal UTF-8 decoding, validates the closed versioned transport once, and calls typed handlers directly. It restores the explicit undefined fields that JSON omits from Optique requests. It never re-enters the argv parser. Lint retains the verified launcher, external activation selection and immutable validator snapshot; it cannot become a direct lint-ci call to the installed validator. Typed activation preparation preserves installed toolkit identity. This chooses a process boundary over importing the validator into PUNI, because existing handlers own process environment, cwd and exit status and a shared process would weaken candidate isolation. The initial trusted bootstrap must still sanitize Bun startup; a later child cannot undo an executed preload.

The child uses the running Bun executable, disables env-file loading, runs outside the candidate and receives an explicit trusted environment with its verified dependency closure. Capture caller cwd and anchor ordinary relative host inputs by prefixing that directory without lexical normalization, preserving native symlink/parent path semantics. Already canonical-absolute-only report/authority inputs retain their original spelling for existing refusals, and repository-relative selectors stay repository-relative. Workflow binding receives an explicit caller-directory context for both its file and prompt root without changing the child cwd. The provider-owned validator-paths.ts records the exhaustive field distinction; nested artifact documents and their digested bytes remain untouched. Preserve command stdout and nonpassing verdict statuses without a second generic error. New validator bytes require new package/toolkit/activation identities; supported historical Bash activations remain verifiable; current Bun execution refuses them before launch.

**C10. Startup precedes application authority.** Follow [ADR 0079](../../../docs/adr/0079-sanitize-puni-startup-before-bun-runs.md): the installed Bun script has an OS env shebang that removes BUN_OPTIONS, BUN_INSPECT_PRELOAD, NODE_OPTIONS and BUN_BE_BUN before selecting Bun, then passes --no-env-file and the tested equals-form --config=/dev/null. Helpers use the same contract with the currently selected absolute Bun path, which must not contain an equals sign because env interprets it as an assignment. Installed script and operand paths retain equals signs. Compilation is not the isolation mechanism: pinned compiled binaries still accept preloads and runtime-mode overrides, and their virtual filesystem changes helper/asset resolution. This supersedes the original C6 bare Bun prefix. Initial Linux evidence does not certify Mac env behavior, a real package, or the MCP budget; those remain explicit installed checks.

**C11. External installation and Git metadata.** The ordinary validator child uses a trusted, stable installation physically outside the selected candidate. After package/toolkit verification, physical checks cover the installation, executed validator and dependency closure, including symlink destinations. Candidate-local installations refuse visibly. Verification does not establish immutability: installation ownership and stability are explicit prerequisites. Per-invocation random toolkit snapshots were rejected here because coverage runtime identity hashes actual artifact and closure paths; relocation of those identities needs its own versioned contract. Lint retains its existing separately verified snapshot.

Git and its executable search path are trusted prerequisites; Git must report a supported release version at least 2.36.0 (plain upstream or canonical Apple/Windows vendor form; release candidates and unrecognized suffixes refuse) so core.fsmonitor=false disables monitoring instead of selecting a hook pathname. The ordinary child's explicit environment excludes user HOME/XDG/locale/credential/SSH/TMPDIR state, nulls global/system Git configuration, forces hooksPath=/dev/null and fsmonitor=false through provider-owned Git configuration entries, disables replacement objects and interactive prompts, and denies all transport protocols. Only lint-ci receives the selected caller-anchored CI binding; the verified dependency closure always overrides caller input.

The shared working-selection boundary refuses every loaded nonempty clean/process filter command, including included and worktree configuration, before freezing working bytes. Conservative refusal includes unused definitions and earlier nonempty definitions overridden by later empty values; silently disabling them would change selected-byte semantics. The premise covers stable operator-owned Git metadata, worktree/common metadata and included configuration for the complete operation. A concurrent hostile writer of that metadata is outside this contract and would require a guarded Git projection or stronger filesystem isolation. This does not claim a general Git sandbox. Activation preparation's existing in-process subprocesses remain separate trust-port work.

**C12. Typed preparation paths and installed authority.** Preparation uses the existing typed provider APIs without reconstructing argv. Host inputs use the captured caller directory: candidate repository, review record, destination, work and check runs; toolkit activation also anchors audit strata and an explicit toolkit, while relocation anchors its base activation. Candidate policy/mapping/launcher/validator-entry selectors and candidate SHA/lane/cwd identities remain verbatim. Parser-owned undefined options retain provider defaults. The verified installed toolkit supplies the default directory and authoritative expected identity, including when an explicit toolkit is selected. Returned report lines keep LF separation/final LF, and relocation completion precedes the returned status. Existing provider refusal and partial-destination behavior is preserved. The current direct preparation wiring does not establish C11 child-environment isolation or complete the coordinated Bun launcher/self-check port.

**C13. Versioned Bun execution.** [ADR 0080](../../../docs/adr/0080-version-the-bun-toolkit-execution-format.md) fixes toolkit schema 2 and activation schema 4 with launcher.mjs paths, retaining original-byte supported historical toolkit1/activation3 verification independently from execution compatibility. Supported toolkit1 is the pre-migration five-role, closure-bound producer layout; earlier four-role/unbound layouts remain unsupported and previously ignored extra role keys now refuse. Current Bun execution refuses historical formats before any role launch and pins its exact Bun runtime. The package manifest/selection/marker/validator transport contracts retain their versions. The snapshotter is the selected authenticated role; shared startup code is bundled into delivered helpers. Prepare producers, defaults, self-checks, archive/bootstrap, CI and installed lint must switch coherently; reader support alone does not complete that port.

**C14. Installed lint owns its selected process chain.** Activation optionality applies after installed package/toolkit2 integrity, supported Git, actual candidate worktree and external installed-runtime preflight; missing/unsupported Git and invalid candidates fail before launcher execution even when activation is absent. This deliberately tightens the old absent-activation shortcut so no candidate-owned launcher executes before placement is established. The verified installed launcher remains the installed route's authority; a selected activation's launcher is verified with the full artifact set but neither recursively executed nor required to equal it. Archive admission retains its separate toolkit-release join. The standalone launcher accepts a closed fatal-UTF8 --puni-lint-v1 stdin envelope, separate from the ordinary validator union. Its typed selection maps working to lint-local/observe, staged to lint-local/ratchet and committed to lint-ci; only committed receives the selected CI binding. Root/selection absence is optional inactivity only when truly absent; dangling links, unreadability, malformed selection and broken selected packages refuse without a flat fallback. A flat current root is a complete activation4 package. The closure defaults from the configured archive root before selecting a version and retains transport/operator authority; activation role verification alone does not authenticate it.

The launcher verifies physical placement of authority metadata, roles, closure and scratch against the actual Git worktree root under the shared C11 environment/version contract. It runs the authenticated selected snapshotter through protected selected-Bun startup, then the captured validator through its existing typed stdin bridge. It preserves raw output and verdict statuses; required zero status additionally needs schema1/enforce/ci-preselected/accepted/certified report fields, with legitimate extra report fields allowed. Typed usage/configuration and activation refusals map to64/78; unexpected implementation/spawn failures and unsolicited signals remain failures.

The asynchronous launcher owns its two sequential detached stage process groups, forwards SIGINT/SIGTERM, prevents the next stage after cancellation, escalates after bounded grace or repeated cancellation, and awaits child/output settlement before scratch cleanup. Executable boundaries subscribe to signals and pass a typed interruption subscription into the API. The installed parent isolates the launcher and delivers cancellation through the ordered private channel below, awaiting its cleanup without a competing escalation timer. Ownership covers ordinary descendants in the inherited group, not deliberately escaping daemons. Linux Bun1.4.4 detached/group-signal behavior was probed by Astra; the actual launcher and other platforms still require their own tests.

[ADR0082](../../../docs/adr/0082-order-installed-lint-controls-over-private-ipc.md) replaces native parent signal replay with a private Bun IPC lane because pinned-runtime probes observed coalescing, reordered reasons and pre-handler death. The distinct closed --puni-lint-parent-v1 mode requires an actual IPC channel; older closed --puni-lint-v1 launchers reject the new marker before operation IO instead of ignoring an environment opt-in. After the handshake, constant internal dispatch calls the unchanged standalone request core, without user argv reconstruction or parser re-entry. The launcher binds broker/output/message/disconnect handlers before sending puni-lint-ready-v1; the parent sends recorded puni-lint-SIGINT-v1 / puni-lint-SIGTERM-v1 messages in order, then puni-lint-start-v1. Start gates operation IO; prior cancellation can finish without stages. Later controls use the same broker as native signals. Unknown/duplicate controls and premature disconnect cause failure plus child-owned cleanup. After executable lifecycle settlement, puni-lint-finished-v1 distinguishes expected channel closure; it is not evidence of detached-stage absence. Normal status1 survives cancellation. The child removes channel listeners and immediately exits; no extra finished acknowledgement or parent escalation timer is used. The standalone --puni-lint-v1 archive/direct route retains its native-signal contract.

PATH is frozen once against the physical trusted runtime directory before either Git probe or stage changes cwd. Absolute components remain verbatim; relative components are prefixed without lexical normalization, and empty components name that trusted directory. A relative/empty component with a delimiter-containing trusted directory refuses because the anchored PATH cannot represent it. Every Git probe and stage reuses this environment.

The installed route receives Git lookup authority already selected by its trusted caller, independently of the provider installation whose placement is being checked. Its preflight accepts the factory-created frozen LintRuntime unchanged, verifies that cwd against the discovered candidate and passes the same frozen PATH to the delivered launcher. Selecting or verifying a provider toolkit cannot change the lookup origin. Git, the frozen search path and its origin remain trusted and stable prerequisites; this is not authentication of arbitrary PATH entries or a general Git sandbox. The archive launcher retains its established trusted-runtime directory contract.

The executable owns lazy Bun FileSinks and per-channel native operation tails. Normal output awaits write and flush and preserves complete binary bytes. One first-terminal cancellation/failure latch releases both channels' API waits; asynchronous output callbacks must use this interruption source. The child does not add a competing cancellation race that could hide an earlier output failure. After cancellation or failure, remaining child bytes are drained without outward delivery. Cancellation may explicitly abandon native sink operations after unreferencing them; abandonment never counts as a flush. Replayed output cancellation does not count as a second signal and cannot shorten cooperative group cleanup.

Unexpected failure receives at most one one-second diagnostic through the same stderr sink, ordered behind its actual native tail. A failed stderr is not retried, and expiry/disposal prevents starting a later write or flush. No Node writer or automatic Bun reporter substitutes for this owner. Reporting and disposal failures produce a nonzero terminal outcome. Only the standalone executable calls process.exit after ownership settlement or unconfirmed group cleanup's retained-scratch failure and bounded diagnostic attempt; reusable APIs return or throw. A confirmed absent group permits scratch removal; unconfirmed cleanup reports its process-group identity and retained scratch path through usable stderr.

**C15. Git preflight belongs to cancellation.** Lint's version and actual-root queries use asynchronous owned process groups under the invocation's interruption source, before any activation role. A recorded cancellation prevents the next probe or role, preserving controlled130/143 after cleanup. The released-version response validator is shared with unchanged ordinary synchronous callers. This fixes a confirmed Bun1.4.4 boundary: a synchronous probe defers the JavaScript signal handler; PID-only signaling leaves Git running, while group signaling can make the actual launcher return failure1 before observing cancellation. A normal exit1 is never rewritten as cancellation, because it may mean unconfirmed inner cleanup.

The staged provider facade exposes dedicated typed executeLint with explicit installation, output, interruption and selected-activation context alongside the existing52-command dispatcher. Current package/toolkit2 verification, native external placement and owned supported-Git/actual-root preflight precede optional inactivity. Its actual launcher is a separate group; the parent delivers first and repeated controls over the ordered private IPC lane and awaits its streams and own lifecycle without competing escalation. The launcher owns its separately detached roles. Outward failure stops delivery, requests termination and drains while retaining additional diagnostic/cleanup evidence. An unsolicited launcher death leaves nested cleanup unconfirmed; launcher-group absence proves no detached-stage absence and grants no permission to delete inner scratch. Producer defaults remain legacy until the coherent switch in C13 is complete.

## Risks / Trade-offs

Importing provider runtimes during grammar construction would break help isolation and token-helper startup. Generic app allow rules would weaken boundaries. Renaming toolkit files without a new identity would invalidate historical trust. Static command inventories can miss generated/embedded scripts, so acceptance compares concrete consumers and generated artifacts with the inventory.

## Migration Plan

Land provider facades and root grammar, then import-safe lazy execution, complete delegated grammars, Bun trusted packaging, client-operation embedding, consumer/name migration and installed verification. Retain migration scaffolding only until its callers move. Run each provider's existing tests, root packaged tests, boundary negatives and required gates. No package publication or deployment result is inferred from local build success.
