## Decision and existing boundaries

The owner selected WBS/SQLite on 2026-11-17. WBS will accept plan references, attribute operator assertions and consume them on an explicit application request. Each operation uses the authenticated be-01 boundary. Navigator's local `plan-reference`, `receipt-to-commands` and `admit-progress` keep producing artifacts. Dash records operator evidence. Burokrat’s strict record contracts check supplied consistency.

The ordinary WBS v11 export comes from `libs/wbs/application/core/src/http/project.routes.ts` and the plan-document resource. The isolated export path reads several resources. Its existing GET alone cannot establish atomic acceptance. Connected v12 documents carry other projects and fall outside the first tranche. Browser `PlanRead.seq` and `projectRevision` describe the delivered read and project. Neither identifies the complete accepted export. Navigator's `planningCommit` and `sourceBaseCommit` continue to be Git object IDs in the existing six-field PlanRef.

The ordinary command route calls `runCommandBatch` with a caller and operations. Its payload ID identifies the project. The claimed-runtime route requires a live claim, receiver generation and execution identity and supports a narrower command set. Neither route has an accepted-reference register, issuer policy or progress-consumption key. A saved-plan capture has its own identity and lifecycle.

## Accept the reference

Protected WBS installation state supplies the repository binding and the separate grants to accept references, submit assertions and apply them. For each new write the admitted SQLite writer rechecks retained verifier evidence for the human using be-01's direct sign-in path (a verified native first-party session or verified upstream human sign-in subject), current credential scope and organization/project access. Match that human subject to the protected grant for this operation, organization, project, repository and change. Machine and MCP-consent credentials act as their pinned agent, even when their account belongs to the granted human. A delegated credential, an absent verifier, a generic `human` runner label or a matching account ID cannot establish the operator. Preserve the existing verifier, current-access and revocation checks in addition to these scoped grants. In particular, the wire caller cannot select an authentication kind.

The acceptance request supplies the original ordinary v11 export bytes, original requirements bytes, operator-selected planning and source Git object IDs, repository/change, complete reference and tasks. Validate both byte inputs using the Navigator compiler's decoding rules, compute the requirements digest from the bytes and reproduce the reference and tasks. Match every binding, including raw export digest, task digest and the addressed WBS project. Acceptance records the asserted Git coordinates. Verification of the source content at those coordinates belongs to CI resolving the pinned artifacts.

Detect the live plan kind inside the writer turn. A valid ordinary export presented after the project became connected must refuse. For an ordinary live plan, compare every field of the supplied export with the writer-bound plan at the supplied valid export instant. Retain the original export and requirements bytes, complete reference, tasks, accepting subject and basis immutably. Compare the expected active version (explicit empty on first acceptance) and digest, then advance the accepted-reference version. A competing replacement or differing live plan returns a typed conflict with no partial record. An accepted-reference replacement cycle A → B → A yields a new acceptance version even when the final bytes equal the first. Ordinary editor changes are compared by the live contents observable at application. There is no global edit-history fence.

Conceal a foreign project according to existing WBS rules. Check current read access before retrieving active or historical bindings. An active read returns the scoped accepted-reference version/digest and separate current write-basis token. A historical read by full scope, version and complete digest returns its original bytes, tasks and reference. Neither read samples a new export clock.

## Attribute an operator assertion

WBS records the verified human subject admitted under the operator rule above. A protected installation administrator controls scoped issuer grants and application grants. Ordinary project editing alone grants neither. An authenticated operator submits a stable assertion ID, complete schema-2 receipt and accepted-reference version. Record the original receipt digest/content, exact scope and policy revision under the authenticated issuer's identity. Scope covers organization, repository, project, change and allowed task/steps. Check current issuer permission and full plan/task/entry consistency. Equal retries reuse the attribution. Reusing the same issuer-scoped assertion ID with different content refuses. A receipt digest is content identity, and a batch/project ID cannot stand in for this assertion ID.

Protected policy must share the WBS serialization boundary for current admission and application. Missing, unreadable or malformed required policy is a trusted-state failure. A valid policy with no qualifying grant denies. A candidate cannot select policy, assert a verifier verdict, provision its own identity or promote an operator claim to execution evidence. Registration of an assertion changes no progress.

## Apply once in WBS

The retained write basis is named by a WBS version that advances on each accepted application or reference replacement. Normal WBS edits are detected by comparing the complete live contents under the writer turn. An authenticated caller explicitly submits the assertion ID/issuer, expected accepted reference digest/version, expected WBS write basis and a stable application command ID. Resolve the scope from WBS, authorize before disclosing retained state, and read the stored assertion. Derive the ordered `setProgress` and optional `setMeasure` operations from its entries and WBS-accepted task IDs/step mapping. Reuse the deterministic semantics of Navigator’s `commandsForReceipt` and Burokrat consistency in an importable shared boundary if needed. Preserve existing product import directions. Never apply a caller's substitute batch.

In **one SQLite writer transaction**, recheck the authenticated caller's current application grant, the issuer's current scope and policy, the active reference version/digest, exact live write basis and leaf/task/step identities. A versioned WBS write basis must cover all ordinary exported inputs including existing progress and measures. For an initial conservative implementation compare the complete live ordinary document at the retained export instant with the WBS-retained expected state. For this receipt path, stage every durable event the application would publish (including its dirty-project tree change) through the writer-bound event store. Capture the resulting ordinary document **after** those records have allocated the project's durable sequence. In the same commit retain that document, the next write-basis token and the original accepted result. Keep the approved reference and its original bytes immutable. Return the next token to the authorized applicant and expose the active token through the authorized read. After commit, push the already recorded event and sequence once via the committed delivery path. Do not invoke the ordinary post-commit recorder for those events. Existing `service/committed-fanout.ts` and `GatewayBroadcaster.pushRecorded` in WBS core illustrate the two halves. A lost live notification recovers by durable replay without advancing the sequence again. An unrelated normal edit may cause conflict. An operator resolves it explicitly by reviewing current state and accepting a new basis. Never silently rebase a stale write.

Serialize revocation, reference replacement and duplicate consumption with that decision. Persist the assertion consumption, application ID and immutable accepted result together with progress/measure changes and the WBS journal. Enforce uniqueness both on scoped issuer/assertion identity and on the complete bound receipt digest within the organization/project/repository/change. Hash strictly decoded canonical receipt content, so equivalent JSON presentations and different submit or application IDs cannot consume the same receipt twice. Bind the application ID to its immutable request. A reused ID with changed payload or target conflicts. A request with a fresh application ID for an already consumed assertion reads the original result and returns its original command ID. Only IDs that accepted a mutation name an application. A repeated consumed assertion returns its historical result to a currently authorized reader, including under a new application ID, without applying again. Authorize current read access first. Recover by matching original scope, canonical receipt content and mutation intent, allowing a different submission ID for equivalent content while preserving its original attribution. A conflicting binding still refuses. No new mutation is implied after revocation. A genuinely new assertion by an operator is a separate human assertion. Crash before commit rolls everything back. After commit a lost acknowledgment is recoverable from SQLite. Announcements leave only after commit. A compensating edit uses existing conflict-aware undo or an authorized new command and preserves the original consumption.

## Production qualification

Use the existing authenticated WBS route and current project-access checks. Protected installation still needs an identified administering/recovery principal, deployed authentication route, protected policy writer and initial authorized organization/repository/project/operator. Prove ordinary writers cannot replace that boundary. Source-level fixtures can exercise the transaction before any live enrollment. Automatic execution assertions require separate evidence for the protected runner, its release/invocation, exact source/run/plan/task and the predicates it observed. No credentials, live policy or runner are selected by this design.
