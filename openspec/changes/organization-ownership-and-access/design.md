## Context

Current project reads are deployment-wide; `project.owner_id` controls restricted writes, and `project_access` is recent-open history. Directory catalogs have global unique names. be-01 accepts current Auth0 OIDC identity and existing first-party password sessions; gw-01 validates subscription names but not project membership; mcp-01 replaces its own credential with an upstream token before calling be-01. Browser OIDC transaction and refresh state is in memory. Production's issuer and user inventory remain unverified.

## Goals / Non-Goals

**Goals:** Make organization ownership and current membership the sole WBS resource authority across HTTP, sockets and MCP; preserve existing local user IDs and legacy relationships; permit a later identity-provider swap through stable `(issuer, subject)` mapping.

**Non-Goals:** Change login methods, migrate providers, add Auth0 Organizations, enable SSO JIT or SCIM, transfer content between organizations, or introduce durable provider-refresh/session continuity in this stage. Browser organization binding does use shared revocation state so logout and credential rotation invalidate a copied old access-token/organization-cookie pair immediately.

## Decisions

### Ownership and roles

Add local organization, membership, external-identity, invitation, join-request and domain-verification records. Assign organization ownership to every root resource; dependent rows inherit through their parent but every query, reference and event path must resolve the same organization. Organization-scoped catalog names require replacement uniqueness structures staged for coexistence with old global indexes. Keep `project.owner_id` as creator/steward and `project_access` as history. The [role matrix](specs/organization-access/spec.md) is normative. WBS membership governs roles; current IdP scopes remain an additional ceiling until callers migrate. A super-admin may recover a restricted project, with the action recorded. An ownerless organization caused by external deprovisioning needs a separate audited recovery path; ordinary role changes cannot create one.

### Active organization and identity

Auth0 only establishes verified `(issuer, subject)` and, for onboarding, verified email. Resolve that pair to a stable WBS user; do not merge existing accounts on email alone. A signed-in password-only user keeps their local ID while verifying a newly supplied address with a single-use expiring email challenge; alternatively, linking an Auth0 identity requires fresh proof of both the password session and Auth0 session, a verified Auth0 email, and a collision-free issuer/subject mapping to that same local ID. Refuse onboarding until one path completes; render expiry, delivery failure and identity collision recovery. A browser selects an organization through a same-origin endpoint that checks current membership and binds the choice to its WBS session; switching rotates that context, clears organization-scoped frontend caches and requires socket reconnection. Bearer clients receive a short-lived WBS-signed organization context bound to the verified identity and audience. A raw Auth0 bearer token can authenticate onboarding or request a WBS context, but cannot authorize resource access alone. Internal MCP calls use audience-specific, short-lived signed delegation; be-01 verifies signature, audience, identity binding, organization and current membership. Gateway calls delegate by the socket's forwarded browser credential (`__Host-wbs_access` and `__Host-wbs_organization`, as sent, behind the gateway secret), which be-01 verifies through its ordinary browser authentication before rechecking membership and the project's organization; signed gateway tokens are reserved for the post-activation path. Caller-controlled headers and route IDs cannot select authority. A user with zero memberships can only use onboarding routes. Local development identity needs an explicit seeded membership; production-local mode remains forbidden.

For browser selection, credential replacement requires explicit reselection; refresh does not carry the selected organization forward. Logout and credential rotation revoke the prior browser binding through shared server-checked state, including when the entire old access-token and organization-cookie pair is replayed against another process or after restart. Every browser organization-resource mutation supplies its expected organization; missing or mismatched context returns typed `409 organization_context_changed`, performs no write and is never automatically retried. This equality precondition detects stale A→B tabs but does not claim to detect A→B→A selection history.

The explicit link has its own `POST /api/auth/link/auth0` start and `GET /api/auth/link/auth0/callback`, using a five-minute bounded in-memory transaction distinct from login. Start proves the current first-party password cookie and a fresh password; the callback requires the same cookie, state, nonce and PKCE exchange and Auth0's verified email. The SQLite mapping and email update commit in one immediate transaction after a fresh activation and collision check. The callback never invokes the login path that can create an account. Auth0 must allowlist the derived link callback URI before activation; no provider configuration is changed in this slice.

### Onboarding and administration

Once the identity has a verified email, look for a matching invitation, then an exact verified domain. A matching domain routes to the organization with a join-request action and forbids creation by that address; without a match, creation atomically creates organization and first super-admin membership. Creating an organization does not claim a domain. Invitations contain normalized recipient email, organization, role, random token digest, expiry, revocation and consumption state; 7-day default expiry is an implementation assumption. Acceptance compares the current verified email and consumes atomically. Join requests are unique while pending; approval rechecks domain verification, email and administrator authority and issues one invitation. Only acceptance creates membership, including after company SSO. Admins can grant viewer/member only. The members page and domain settings render permission loss and query failure explicitly.

### DNS verification

Slice 32 binds the initial challenge to a reviewed MIT policy asset and SHA-256 manifest. The directly declared `tldts@7.4.12` supplies ICANN and private public-suffix rules; versioned provider, relay and explicit suffix entries add deny rules. The checked asset is read on each claim decision. Domain settings list and challenge issuance require current super-admin authority; an immediate transaction rechecks that authority and replaces a pending digest, invalidating earlier TXT values.

Normalize domains to lowercase ASCII IDNA form, reject invalid/public suffix, relay and maintained public-provider entries, and compare exact domains. A super-admin requests a 256-bit random token for `_wbs-verification.<domain>`; store only its digest, bind it to organization and domain, expire it after 24 hours and recommend DNS TTL 300 seconds in the UI. Rotation invalidates older challenges. Query authoritative DNS with a bounded timeout and require an exact TXT value; a provider outage or malformed response is an explicit failed verification, not proof. Pending claims do not reserve a domain. A unique verified-domain key and transactional claim decide races; the loser receives typed 409. After initial verification, promote the verified challenge digest to a distinct bound ownership proof that periodic checks can use after the 24-hour challenge expires. Permit super-admin rotation without losing ownership; make the old proof valid only until the new one succeeds or 24 hours pass. Recheck every seven days. Warn on DNS failure; suspend onboarding after 14 days without successful proof. A suspended claim retains the unique owner and recovers to verified after a successful check of retained or rotated proof. Suspension leaves existing members and content intact. Release requires current super-admin authority, and transfer requires a new claim. The public-domain list is maintained as a reviewed, versioned policy input; unreadable or missing policy blocks claims and checks.

### HTTP, gateway and MCP enforcement

Slice 25 (task 2.5b) leaves delegation inactive in production. A trusted credential resolver must provide local user, mapped upstream pair, organization, client, grant, scope ceiling and credential expiry before the issuer may sign. A dedicated RS256 PKCS#8/SPKI pair is validated before the be-01 listener starts, but configuration alone never activates signing or verification. The only gateway consumer is `POST /internal/gateway/projects/:projectId/access`: service secret plus gateway-audience bearer, read scope, current membership and scoped project lookup, with an empty 204 answer. Every verified MCP or gateway bearer is consumed once by `(issuer,jti)` in shared SQLite before authorization or dispatch. Failed authorization still consumes it; retries require fresh tokens. The gateway client adapter remains unwired until tasks 6.1–6.3.

Slice 27 adds an inert `POST /api/auth/context` seam. In an explicitly enabled composition it verifies a native WBS session from exactly one browser cookie or Bearer carrier, checks signature, expiry, current account and selected membership, and signs a `wbs-be-01/direct` context for at most five minutes. `identity_kind: first_party` is an explicit signed variant; it has no fabricated upstream issuer, subject, client or grant. Direct contexts may be reused until expiry but every protected request rechecks current membership and the activation marker. An audience in the body is malformed; headers never select the organization. Browser cookies require same-origin requests, while Bearer-only clients may omit Origin. The route answers typed 401 for invalid binding and typed 403 for inactive or forbidden sources. Production continues to refuse both issuance and delegation verification. Task 2.4 still provides durable browser selection; verified upstream credential expiry and binding, MCP cutover and activation remain open.

MCP delegation (tasks 2.5, 6.4, 6.6, 2026-10-21): be-01 alone holds the signing key. mcp-01 presents its `INTERNAL_AUTH_SECRET` and the user's own upstream access token to three internal routes: `/internal/mcp/organizations` (consent's admitted memberships, or `pre_activation`), `/internal/mcp/delegation` (one single-use `wbs-be-01/via-mcp-01` token for one call, from the family's organization, user, client, grant and the access token's scopes, after the token still maps to that user and organization access admits the delegated principal), and `/internal/mcp/authority` (the family's membership and credential-rule facts for mcp-01's per-request and refresh check; no user credential, grants nothing). The verified token's `exp` is the credential expiry the identity port does not expose. With a configured key pair boot composes the live verifier and issuing authority; before activation nothing is listed or issued and organization access refuses every delegation, so configuration still creates no authority. A delegated credential has no trusted grant-lifecycle evidence, so a session policy refuses MCP. mcp-01 never forwards the raw upstream token for a bound family, including on a refresh retry.

Place authorization at the application service boundary and require repository queries to carry organization scope; Elysia controllers map expected auth, permission, missing-resource and conflict outcomes to typed 401/403/404/409. Every list/detail/write/export/import/batch/scheduler/history path and referenced ID must be checked. A gateway subscription, presence query, replay and forwarded command obtains be-01 authorization for its bound user/org; event routing includes organization. Recheck queued replay before delivery, invalidate sockets on membership changes and cap authorization leases so access ends within five seconds despite a dropped notification. A switch creates a new socket. mcp-01 binds selection to consent, code, grant, refresh family and access session; the signed delegation reaching be-01 includes local user ID, upstream issuer/subject, org ID, OAuth client ID, grant/family ID, scopes, audience and expiry. Its direct-upstream-token path is refused for resource tools unless it can establish the same binding. Current membership is checked on each tool request and refresh.

## Risks / Trade-offs

- Existing global catalog uniqueness and old writers require a bridge release. Do not open new organizations until every old reader and writer has drained and reconciliation passes.
- The current in-memory OIDC stores remain a restart limitation. Their durability is outside stage A; an organization context must never outlive its underlying session.
- The five-second gateway bound requires measured lease and invalidation behavior. Fail closed if membership checking becomes unavailable.
- Production may use a different identity mode or have users whose effective rights do not map cleanly to a role. Inventory is a hard activation gate.

## Slice 2.4B1: shared browser credential revocation authority

This slice establishes durable revocation state for the later logout, credential-rotation and refresh lifecycle wiring. It does not expose a public endpoint or activate organization-bound production behavior. The production composition remains `NO_BOUND_ORGANIZATION`.

The revocation key is the tuple `(verified credential kind, stable local user ID, SHA-256 of the exact verified access credential)`. Credential kind is native or OIDC. It is deliberately neither user-wide nor organization-wide, so revoking one credential pair leaves other credentials usable.

Add `browser_credential_revocations` with an additive migration and paired `down.sql`. Store only credential kind, user ID, lowercase 64-character digest, safe-integer credential expiry, and safe-integer revocation time. The tuple is the primary key. Keep user IDs for audit when an account is deleted. Never store raw credentials, cookies, refresh tokens, or email. Do not garbage-collect rows or reset revocations. Rollback may drop the table only after proving it is empty, including expired rows.

Expose a narrow application boundary for atomic, idempotent revoke and shared-store lookup. Repeating the same revoke preserves the original `revoked_at`; the same key with a different expiry throws. Every lookup reads shared storage without a process-local negative cache. An absent row in a valid migrated store is unrevoked. Missing/unreadable store, missing table, malformed matching state and failed writes throw; do not create, repair, or swallow errors.

For the later enabled composition, check revocation before membership listing, selection issuance, and resolving an existing browser organization binding. The committed revocation is the linearization point: requests after it refuse. A selection already in flight may issue its cookie, but protected resolution must refuse it after commit. Do not cancel transactions already authorized. Preserve delegation behavior; delegated requests cannot select a browser organization.

Acceptance proofs must inject each fault into the production path: an old intact token/cookie pair is refused across another process or restart after commit; removing the shared lookup makes that mounted test fail; a revoked token cannot obtain a new selection cookie and removing the selection check makes that test fail; other credentials and users remain valid; concurrent revoke/select remains monotonic and idempotent; unavailable authority and write failure surface as server failures without acknowledging revocation; rollback refuses every nonempty table; and production remains unbound. Record exact commands, outcomes and fault observations in `verify.md` after implementation.

## Slice 2.4B2: lifecycle fence, backend transitions and browser logout

### Decision adopted 2026-10-01

Following Astra high's source review and the user's standing authorization to resolve non-harmful blockers, adopt a shared durable browser-lifecycle fence. B1's per-credential `revoke()` alone cannot serialize logout against an in-flight refresh across processes. Do not claim that D2 is complete until this fence, lifecycle wiring and the server-acknowledged browser logout path all pass mounted proofs.

Coordinator decisions for this plan: (1) accept the durable generation fence and retained credential associations; (2) implement common native/OIDC server logout plus a separate frontend acknowledgment slice; and (3) refuse logout as `401 unauthenticated` when identity/association cannot be proved, while a proved retry of a committed closure is idempotent local `204`. These choices do not imply production activation or global provider-token revocation.

### Current seams

- `TokenStore` and `RefreshRecord` in `libs/wbs/adapters/auth/src/oidc-store.ts` hold provider refresh material in process memory and do not retain the verified access-credential tuple or durable generation.
- `refreshOidcSession` in `apps/wbs/be-01/src/controller/auth-oidc-endpoints.ts` uses unconditional `save()` when the provider retains its refresh token. That path can recreate or preserve a refresh session after another process commits logout unless completion checks shared state.
- The existing OIDC logout deletes local refresh state before attempting upstream revocation, and that failure-order property must remain.
- Password login and registration in `auth-password-endpoints.ts` issue credentials; common logout is currently mounted only with OIDC routes in `app.ts`.
- `SessionOwner.exit` in `apps/wbs/fe-01/src/runtime/session-runtime.ts` is intentionally local-only. It sends no request and revokes nothing, so a reload can restore the cookie identity.

### Durable lifecycle state

Add additive lifecycle migration(s) and paired `down.sql`, ordered after B1. The lifecycle record is keyed by a digest of the opaque OIDC browser-session correlation value and retains the stable local user ID, monotonically increasing generation, active/closed state, and current exact verified credential tuple. A companion association table retains every issued credential tuple `(kind, digest, expiry)` for that lifecycle and generation so delayed logout can prove its predecessor belongs to that lifecycle and revoke the currently active successor. Store no raw cookie, provider access/refresh secret, email or unverified token claims. This is coordination state, not durable provider refresh-token storage. Retain closed records, historical associations and old credential revocations; add no cleanup or reset. Rollback refuses if any lifecycle or association row exists.

Expose a narrow `BrowserAuthLifecycle` feature boundary with open, conditional replacement and close transitions. Refresh replacement validates the generation captured before provider I/O. Logout validates the presented exact credential against retained tuple-to-lifecycle history, then closes the currently observed active generation and revokes its current tuple in one shared-store transaction with B1. It does not require the caller's predecessor generation to equal the current generation. A retry against an already-closed lifecycle is idempotent local success only when the exact historical association is proved. Do not expose a DB handle or transaction graph to controllers. Missing, malformed, unreadable, stale-generation and write-failure state throws or maps to the typed refusal at the HTTP boundary; never initialize, repair, or treat it as active.

For OIDC, hash the existing opaque `__Host-wbs_session` correlation as the lifecycle key. Keep provider refresh secrets in the existing process-local `TokenStore`; after restart the browser must reauthenticate if that secret is absent. For native credentials without a refresh lifecycle, logout revokes the exact currently verified credential through B1; native replacement revokes only a proved predecessor, and an independent native login creates no synthetic shared lifecycle. Native-only registration and login retain their JSON token response; OIDC-configured password issuance retains its access-cookie response, so enabled browser logout also admits a sole native Authorization Bearer at the exact Origin. The same native proof may arrive in one access cookie; organization-selection and unrelated cookies are not identity carriers. The state-bound OIDC GET callback intentionally has no Origin and instead requires its browser binding and transaction state. Replacement clears the old correlation and organization-selection cookies (and the retired access cookie in native-only JSON mode) before the new session is used. OIDC requires the access cookie and matching correlation; a Bearer, mixed carriers, delegation or retired `x-wbs-token` cannot prove it. The narrow read-only native verifier shares the native HS256, subject, issue/expiry, `jti`, purpose, current-account and exact-byte digest checks with organization credential evidence. Never revoke all credentials for a user. An expired OIDC access token may be associated only by exact digest to metadata persisted when it was verified and issued, never by decoding its expired claims.

### Transition ordering

1. Before successful OIDC callback, native password-login or native registration issuance, classify replacement inputs. With a proved OIDC predecessor (access credential plus matching correlation), atomically close that lifecycle and revoke its exact current credential. With a proved native predecessor, revoke only its exact verified tuple through B1, including when the replacement is OIDC. Do this before opening a replacement OIDC lifecycle or returning cookies. If neither predecessor credential nor correlation is presented, treat the login as independent. If a predecessor/correlation is partially presented or mismatched, refuse replacement without side effects; never infer identity from unverified claims. Failed authentication never retires existing authority. The separate OIDC identity-link callback issues no replacement access credential and does not close the current lifecycle.
2. At refresh start, capture the matching local refresh record and its shared generation before provider I/O. On a verified provider result, atomically require that exact generation to remain active, revoke the predecessor, retain its tuple association, associate the successor and advance generation. Use this conditional transition whether the provider rotates or retains its refresh secret; remove unconditional `save()`. Identical access-token bytes cannot be reissued after revoking that exact tuple; refuse and require reauthentication.
3. Install replacement refresh material in `TokenStore` only after the shared transition wins and only if the local record still matches the captured record. Before provider I/O, acquire a nonblocking exact-record local claim and hold it through shared CAS and local installation or cleanup; a contender gets typed `409 refresh_in_progress` without `Set-Cookie`, provider I/O, or mutation. Different correlations remain independent. The claim closes the local interval where a losing completion could delete a winner whose shared CAS committed but local installation was pending. Logout, save, or replacement invalidates old ownership; releasing an old claim cannot release a successor. A losing completion neither overwrites nor deletes a winner. If provider use may have consumed the old secret but verification, identity lookup, or durable commit fails, remove only the still-owned local record, issue no cookie and require reauthentication rather than blindly replaying a possibly spent secret. Preserve the original failure if cleanup also fails. An explicitly unchanged provider secret followed by infrastructure failure is not classified as spent. If the process crashes after durable commit and before local installation, shared denial remains authoritative and a later refresh requires reauthentication because provider material is absent.
4. Logout proves the presented credential's retained tuple association, then atomically closes the currently active generation and revokes its current credential. Logout does not compare the predecessor generation with the current generation. A proved retry against a closed lifecycle is local idempotent success. Delete matching process-local refresh material before upstream revocation; provider failure after local commit cannot reopen authority or prevent local retry acknowledgment.
5. Refresh/logout races are decided by shared state. If refresh commits first, logout—even when carrying the predecessor—closes and revokes the successor. If logout commits first, refresh commit fails. A late response cannot restore authority because its exact credential is revoked. For native requests without OIDC lifecycle correlation, exact verified B1 revocation is the logout linearization point.
6. One app-scoped sign-out coordinator serves both account-menu and onboarding gestures when the bootstrap supplies the typed `server` capability. Capture the session credential and attempt revision privately, call `SessionOwner.exit()` and dispatch logout in the gesture turn, then join local `signed-out` and shape-validated server `204` before rendering signed out once. A nonempty native JSON token is sent only as Authorization Bearer; an empty cookie-restored session uses same-origin cookies only, without reading them in JavaScript or retrying through another carrier. A bounded abortable request treats timeout/cancellation as unknown, never as success. A newer session revision (including the same user with a new credential), unmount, `overtaken` or `fatal` blocks stale acknowledgment. Refusal, malformed response and network failure render outside the live-services branch without reopening a retired runtime; an unexpected local/adapter rejection is an ErrorBoundary fault. Startup `/me` results carry effect and session-revision ownership so a stale Strict Mode response cannot restore an identity after logout. The production bootstrap explicitly supplies `local` and sends zero logout HTTP while deployed backends run `BROWSER_SESSION_AUTHORITY=disabled`. Future activation switches this code-owned bootstrap capability only after every deployed backend runs `enabled` (see Production composition below); no response-driven fallback or legacy `204` is durable-revocation evidence. Keep switcher and stale-tab write work in 2.4C/4.6.

Success contracts preserve `204` for completed refresh/logout and `401 invalid_oidc_session` for missing, expired, replayed, closed or superseded refresh sessions. A simultaneous local attempt returns `409 refresh_in_progress` without `Set-Cookie`. Invalid/ambiguous logout identity is `401 unauthenticated`; a proved retry of an already-closed lifecycle is idempotent `204`. Invalid Origin is `403 invalid_origin` before store/provider mutation; storage defects are `500`; modeled upstream provider outages retain their explicit unavailable/refusal classification. Clear hardened cookies only after the appropriate committed transition. The contract concerns browser organization authority; it does not claim global revocation of an upstream account or non-WBS API use.

### Required proofs and boundaries

Use deterministic deferred provider responses and real SQLite shared transactions, without sleeps for synchronization. Prove logout-first and refresh-first outcomes across separate processes and restart; unchanged and rotating provider refresh tokens; two simultaneous refresh completions; exact predecessor/successor revocation; independent credentials; mixed access/correlation pairs and delegation refusal before side effects; write failure without success/cookies; and provider logout failure after committed local denial. Watch each safety test fail with its relevant generation check, association, transaction, or ordering guard removed and record `Proof:` comments and observations in `verify.md`.

Selection stays inert until activation in every composition (see Production composition below); a shared durable lifecycle does not itself activate organizations. Old organization-unaware processes also do not consult this fence. Production deployment still requires draining and fencing incompatible writers before activation. Existing switch/rollback gates remain open.

## Production composition: one browser session setting (batch 10)

`bootBe01` takes `BROWSER_SESSION_AUTHORITY`, a required operator setting with no default, so neither composition is chosen by omission.

- `disabled` is the composition before this slice: legacy logout, refresh and replacement routes, `NO_BOUND_ORGANIZATION` and refusing selection.
- `enabled` composes one `SqliteBrowserAuthLifecycle` (OIDC only), one `SqliteBrowserCredentialRevocations`, the native credential verifier and `organizationCookieBinding` keyed by the native session key under its own token type and audience. The OIDC routes receive the same lifecycle; the browser session authority shares the OIDC token store and provider revocation; organization selection and `SqliteOrganizationAccess` read the same revocation table that logout writes.

Lifecycle and organization binding are one setting, not two, because D2's immediate invalidation is what the lifecycle provides: a bound organization cookie without it would outlive the logout that should end it, and a lifecycle without the binding has no organization authority to invalidate. Before activation `SqliteOrganizationAccess` reads the marker before any binding and `SqliteOrganizationSelection` answers `inactive`, so both compositions answer every organization request identically; `boot-browser-session.db.test.ts` compares a fixed request matrix across them. To keep that true for an authenticated principal that carries no credential evidence (a native session issued before tokens carried a `jti`), selection reads the marker and its membership snapshot before the delegation, evidence and revocation checks. Nothing is listed and no cookie is issued before the revocation check passes, so the 2.4B1 ordering guarantee is unchanged; the in-flight race test now holds the selection between that check and issuance. Activation itself remains gated by tasks 7.1–7.3.

Rollout order: each deployed backend's environment gains the setting explicitly (`disabled` until operators choose otherwise), deployed backends switch to `enabled`, and only then does the fe-01 production bootstrap switch from `local` to `server` sign-out (design step 6).

## Slice realtime-auth: gateway project authorization (tasks 6.1–6.3)

One per-socket `ConnectionAccess` (gw-01) owns admission, leases and ordering. Every `project:` subscribe, every resume point and every lease renewal asks one `CheckProjectAccess` port bound to that socket's credential, never a client-chosen name. In production that port is `POST /internal/gateway/projects/:id/browser-access` (decision A14): the `gateway-browser` identity policy requires the gateway secret, refuses any `Authorization` header, then proves the forwarded browser cookies through be-01's ordinary browser authentication with read scope; the handler rechecks current membership and the organization-scoped project. 204 grants; 404 (absent or foreign) and 403 organization or scope refusals deny; 401 `unauthenticated` closes the socket 1008; anything else, including 401 `unauthorized`, is be-01 unavailable and closes 1013 with nothing granted. `/internal/resume` takes the same policy and replays only the subscriptions that principal may read; every other one is `denied`/`forbidden`. Cookies are forwarded as sent and never logged. Subscription changes and lease rounds run through one serial queue; a round checks every held project at once and at most one round is queued, so the 4.5 s bound (3 s cadence plus one 1.5 s check deadline) holds whatever the number of subscriptions and a subscribe never waits behind stacked rounds. One transport failure is retried inside the same deadline so a blue/green alias change does not close every socket; a deadline or a closed socket is never retried. **Production today:** before activation every authenticated socket reads every project (legacy access, the same as HTTP reads) in either browser session composition. After activation, `BROWSER_SESSION_AUTHORITY=disabled` composes `NO_BOUND_ORGANIZATION`, so every subscribe would be refused `no_active_organization`; `enabled` composes the selection binding, and the forwarded organization cookie path is proven against `bootBe01`'s own composition as well as the harness. Known cost (review F4): one check per held project per round, about 83 requests per second at 50 sockets × 5 projects; a batch route `POST /internal/gateway/browser-access {projectIds}` would make it one request per socket per round. Only a local-mode socket, which carries no credential, uses the grant-all `LOCAL_PROJECT_ACCESS`; `buildGateway` is the one production composition and selects it for nothing else. The deploy smoke's backend hop accepts be-01 refusing the unknown smoke principal (close 1008 after the resume) as proof that gw-01 reached be-01.

## Slices 2.4C and 4.6: expected organization and browser lifetime

### Context and accepted scope

Coordinator adopted this bounded C1/C2 packet on 2026-10-13 under standing authorization. Source baseline is `0ea6a1166242edf694294d1ed6e715fb7e1aed60`. ### C1: one expectation, independent authority

Use `X-WBS-Expected-Organization`. The HTTP boundary parses it once into absent, present or invalid request evidence; trim only HTTP surrounding whitespace, refuse empty and comma-combined values, and do not normalize organization IDs into another identifier. Headers are case-insensitive. Duplicate physical values appear comma-combined through Fetch `Headers` and are refused even when equal. Internal code receives a precise union rather than reparsing a string or treating absence as the active organization.

Resource operation classification is explicit: read or mutation. Carry that classification and parsed expectation to the access resolution that returns the operation's `ResourceAccess`. After ordinary authentication, revocation, current membership and credential-rule checks, an activated browser mutation requires a matching present expectation. Reads compare when an expectation is supplied. Only an explicit preactivation resolution preserves legacy behavior; a failed or corrupt marker never skips the check. A separately awaited preflight followed by an independent access resolution is insufficient: the operation must use the same resolved organization that was compared. Existing transactional membership/role checks remain in the committing store operations.

Keep the shared precondition refusal distinct from resource-specific 409 conflicts. Declare `409 organization_context_changed` in affected endpoint shapes so shape-derived clients recognize it as a modeled refusal, including raw-text/export and multipart/import routes. Encode the resource operation policy where the shared shape and binding can enforce it; do not guess solely from HTTP verb or `write-scope`. Test the mounted operation inventory against the production shape/binding list, with explicit classification or exemption for every route. The inventory must detect an omitted route, and its expected list must not be generated solely from the same policy annotation it checks.

| Organization operation family | Coverage owed by C1                                                                                                                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Project roots and catalogs    | List/detail and solution lookup reads; creation, import, metadata, recent-open writes; directory lists and commands                                                                   |
| Project dependents            | Work-item/schedule/history/export reads; command batches, undo/redo, steps, calendar markers, saved-plan and optimization-retry writes                                                |
| Shared organization resources | Spaces and their project membership, project rank, shared-people policy, capacity/directory relations and corresponding reads                                                         |
| Administration                | Members, invitation issuance/revocation, join decisions, domain lifecycle, SSO connections, session policy, provisioning administration and corresponding reads                       |
| Exempt control flows          | Identity/authentication, refresh/logout/linking, onboarding and invitation acceptance, membership choices, active selection/discovery, infrastructure/internal service authentication |

An exemption from the browser expectation never exempts existing authentication or permissions. Signed delegation retains its organization, audience, scope and membership rules; a supplied expectation cannot change it. Gateway service routes retain their existing browser/delegation authority contract and do not become browser resource writes merely because an internal check uses POST. Any actual resource command forwarded as a browser operation remains in the mutation inventory. Read-only organization selections or grants must not be inferred from arbitrary headers.

`GET /api/organization/active` returns only `{organizationId, name, role}` from current verified authority, using the same activation/revocation/membership/credential-rule decisions as resource access. It neither chooses nor resets a cookie. Its no-store responses and MCP exclusion mirror the existing browser membership and selection routes. The frontend may use it without an expectation to reconcile; a protected resource fetch is never a substitute for reconciliation.

### C2: the organization owns resource lifetime

Keep the account identity and organization selection distinct. Model the signed-in view as loading, inactive legacy, onboarding/selection, switching, active, lost access or failure. For legacy mode retain an explicit legacy context. An active organization runtime is identified by account plus organization and its transition generation; generations reject superseded completion and are not server authority. Never extend a bare account-key comparison to accept any same-account organization.

Create clients from the runtime's immutable organization context. Every organization resource read and mutation captures its expected organization from that runtime. Authentication/onboarding/selection clients remain independent. Existing module-level `browserClient` constructions in panels and utility APIs need an explicit bound-client/context seam; reading the newest organization from a global inside `fetch` would allow old closures to send B and defeats D3. A withdrawn runtime must be unable to issue new work or publish completed work.

Selection ordering:

1. Withdraw the current organization runtime synchronously and render switching with no old resource panels. Retire selected projects, streams, directory and catalog through the existing lifetime owners.
2. Serialize same-tab selection requests. Post the intended membership through the existing exact-origin selection route. Reject double submission while pending; transition generations still guard sign-out, replacement and cross-tab supersession.
3. Re-read active context after successful selection. Publish a new runtime only when that current response matches the intended membership and the transition remains current. A conflicting response renders explicit recovery/reselection; it never silently turns a request for A into selection of B.
4. On selection failure or lost response, keep resource content withdrawn. Render a failure and allow context discovery/reselection; do not restore old services or replay an organization mutation. An ambiguous selection completion can be reconciled by the read endpoint.
5. Preserve lifetime `fatal` and `overtaken` outcomes. A failed retirement cannot report a completed switch. Existing account sign-out/credential replacement also invalidate organization transitions and stale responses.

On initial load, discover onboarding and active context: a currently valid binding may restore its explicitly selected membership; absence requires an explicit choice even when only one membership exists. Creation or invitation acceptance refreshes choices rather than selecting. Add the organization administration navigation with the switcher. Existing email verification, Auth0 link recovery, invitations, members and domains keep their distinct rendered refusals.

Selection success sends a same-origin cross-tab invalidation notice containing no credential or authority. A `BroadcastChannel` notice is sufficient; it never selects the named organization, and focus/persisted-pageshow reconciliation plus request preconditions cover a missed notice. Withdraw retained resource UI before reconciling on these events. On organization-context mismatch, missing binding or removed membership, clear the whole organization runtime, including panels outside the project tree, and render recovery. Do not automatically repeat the mutation. Resource responses carry the originating runtime's generation so late reads/events cannot refill a successor. Remote membership removal is discovered through existing refusals/refresh or gateway policy; C2 promises no new instantaneous remote notification service.

### Rollout, risks and remaining gates

The immutable client context and backend refusal must land together before organization activation. Older activated clients missing the header will receive the intended 409. Header propagation and response unions touch multiple frontend consumers; contract and exhaustive-switch type checks are part of acceptance. Shared cookies can change after a successful discovery response; per-request expectations and generation fences remain necessary even with cross-tab notices. They do not promise linearizable global selection across every browser tab.

Keep deployed `BROWSER_SESSION_AUTHORITY` settings unchanged. Existing rollout still switches backends to enabled before frontend production sign-out changes from local to server. C1/C2 can use enabled authority and an activated disposable local database for proof; fake OIDC fixtures exercise the same verification boundary without claiming live Auth0 configuration. Live callback allowlisting, identity/rights inventory, mail/DNS adapters and scheduling, remaining gateway/MCP integration, key/epoch operations and activation/rollback evidence remain their existing tasks. Existing gateway primitives and lease work are preserved, not reimplemented here.

Completion of section 8 may close the local D3/switcher acceptance portions of 2.4 and 4.6 when their proofs pass. It does not mark the whole WBS item done, enable a deployment, or close other open task checkboxes. There are no unresolved product choices blocking C1; external operations remain behind the existing activation fence.
