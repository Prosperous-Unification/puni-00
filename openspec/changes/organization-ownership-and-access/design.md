## Context

Current project reads are deployment-wide; `project.owner_id` controls restricted writes, and `project_access` is recent-open history. Directory catalogs have global unique names. be-01 accepts current Auth0 OIDC identity and existing first-party password sessions; gw-01 validates subscription names but not project membership; mcp-01 replaces its own credential with an upstream token before calling be-01. Browser OIDC transaction and refresh state is in memory. Production's issuer and user inventory remain unverified.

## Goals / Non-Goals

**Goals:** Make organization ownership and current membership the sole WBS resource authority across HTTP, sockets and MCP; preserve existing local user IDs and legacy relationships; permit a later identity-provider swap through stable `(issuer, subject)` mapping.

**Non-Goals:** Change login methods, migrate providers, add Auth0 Organizations, enable SSO JIT or SCIM, transfer content between organizations, or introduce durable provider-refresh/session continuity in this stage. Browser organization binding does use shared revocation state so logout and credential rotation invalidate a copied old access-token/organization-cookie pair immediately.

## Decisions

### Ownership and roles

Add local organization, membership, external-identity, invitation, join-request and domain-verification records. Assign organization ownership to every root resource; dependent rows inherit through their parent but every query, reference and event path must resolve the same organization. Organization-scoped catalog names require replacement uniqueness structures staged for coexistence with old global indexes. Keep `project.owner_id` as creator/steward and `project_access` as history. The [role matrix](specs/organization-access/spec.md) is normative. WBS membership governs roles; current IdP scopes remain an additional ceiling until callers migrate. A super-admin may recover a restricted project, with the action recorded. An ownerless organization caused by external deprovisioning needs a separate audited recovery path; ordinary role changes cannot create one.

### Active organization and identity

Auth0 only establishes verified `(issuer, subject)` and, for onboarding, verified email. Resolve that pair to a stable WBS user; do not merge existing accounts on email alone. A signed-in password-only user keeps their local ID while verifying a newly supplied address with a single-use expiring email challenge; alternatively, linking an Auth0 identity requires fresh proof of both the password session and Auth0 session, a verified Auth0 email, and a collision-free issuer/subject mapping to that same local ID. Refuse onboarding until one path completes; render expiry, delivery failure and identity collision recovery. A browser selects an organization through a same-origin endpoint that checks current membership and binds the choice to its WBS session; switching rotates that context, clears organization-scoped frontend caches and requires socket reconnection. Bearer clients receive a short-lived WBS-signed organization context bound to the verified identity and audience. A raw Auth0 bearer token can authenticate onboarding or request a WBS context, but cannot authorize resource access alone. Internal gateway and MCP calls use audience-specific, short-lived signed delegation; be-01 verifies signature, audience, identity binding, organization and current membership. Caller-controlled headers and route IDs cannot select authority. A user with zero memberships can only use onboarding routes. Local development identity needs an explicit seeded membership; production-local mode remains forbidden.

For browser selection, credential replacement requires explicit reselection; refresh does not carry the selected organization forward. Logout and credential rotation revoke the prior browser binding through shared server-checked state, including when the entire old access-token and organization-cookie pair is replayed against another process or after restart. Every browser organization-resource mutation supplies its expected organization; missing or mismatched context returns typed `409 organization_context_changed`, performs no write and is never automatically retried. This equality precondition detects stale A→B tabs but does not claim to detect A→B→A selection history.

The explicit link has its own `POST /api/auth/link/auth0` start and `GET /api/auth/link/auth0/callback`, using a five-minute bounded in-memory transaction distinct from login. Start proves the current first-party password cookie and a fresh password; the callback requires the same cookie, state, nonce and PKCE exchange and Auth0's verified email. The SQLite mapping and email update commit in one immediate transaction after a fresh activation and collision check. The callback never invokes the login path that can create an account. Auth0 must allowlist the derived link callback URI before activation; no provider configuration is changed in this slice.

### Onboarding and administration

Once the identity has a verified email, look for a matching invitation, then an exact verified domain. A matching domain routes to the organization with a join-request action and forbids creation by that address; without a match, creation atomically creates organization and first super-admin membership. Creating an organization does not claim a domain. Invitations contain normalized recipient email, organization, role, random token digest, expiry, revocation and consumption state; 7-day default expiry is an implementation assumption. Acceptance compares the current verified email and consumes atomically. Join requests are unique while pending; approval rechecks domain verification, email and administrator authority and issues one invitation. Only acceptance creates membership, including after company SSO. Admins can grant viewer/member only. The members page and domain settings render permission loss and query failure explicitly.

### DNS verification

Slice 32 binds the initial challenge to a reviewed MIT policy asset and SHA-256 manifest. The directly declared `tldts@7.4.12` supplies ICANN and private public-suffix rules; versioned provider, relay and explicit suffix entries add deny rules. The checked asset is read on each claim decision. Domain settings list and challenge issuance require current super-admin authority; an immediate transaction rechecks that authority and replaces a pending digest, invalidating earlier TXT values.

Normalize domains to lowercase ASCII IDNA form, reject invalid/public suffix, relay and maintained public-provider entries, and compare exact domains. A super-admin requests a 256-bit random token for `_wbs-verification.<domain>`; store only its digest, bind it to organization and domain, expire it after 24 hours and recommend DNS TTL 300 seconds in the UI. Rotation invalidates older challenges. Query authoritative DNS with a bounded timeout and require an exact TXT value; a provider outage or malformed response is an explicit failed verification, not proof. Pending claims do not reserve a domain. A unique verified-domain key and transactional claim decide races; the loser receives typed 409. After initial verification, promote the verified challenge digest to a distinct bound ownership proof that periodic checks can use after the 24-hour challenge expires. Permit super-admin rotation without losing ownership; make the old proof valid only until the new one succeeds or 24 hours pass. Recheck every seven days. Warn on DNS failure; suspend onboarding after 14 days without successful proof. A suspended claim retains the unique owner and recovers to verified after a successful check of retained or rotated proof. Suspension leaves existing members and content intact. Release requires current super-admin authority, and transfer requires a new claim. The public-domain list is maintained as a reviewed, versioned policy input; unreadable or missing policy blocks claims and checks.

### HTTP, gateway and MCP enforcement

Slice 25 (task 2.5b) leaves delegation inactive in production. A trusted credential resolver must provide local user, mapped upstream pair, organization, client, grant, scope ceiling and credential expiry before the issuer may sign. A dedicated RS256 PKCS#8/SPKI pair is validated before the be-01 listener starts, but configuration alone never activates signing or verification. The only gateway consumer is `POST /internal/gateway/projects/:projectId/access`: service secret plus gateway-audience bearer, read scope, current membership and scoped project lookup, with an empty 204 answer. Every verified MCP or gateway bearer is consumed once by `(issuer,jti)` in shared SQLite before authorization or dispatch. Failed authorization still consumes it; retries require fresh tokens. The gateway client adapter remains unwired until tasks 6.1–6.3.

Slice 27 adds an inert `POST /api/auth/context` seam. In an explicitly enabled composition it verifies a native WBS session from exactly one browser cookie or Bearer carrier, checks signature, expiry, current account and selected membership, and signs a `wbs-be-01/direct` context for at most five minutes. `identity_kind: first_party` is an explicit signed variant; it has no fabricated upstream issuer, subject, client or grant. Direct contexts may be reused until expiry but every protected request rechecks current membership and the activation marker. An audience in the body is malformed; headers never select the organization. Browser cookies require same-origin requests, while Bearer-only clients may omit Origin. The route answers typed 401 for invalid binding and typed 403 for inactive or forbidden sources. Production continues to refuse both issuance and delegation verification. Task 2.4 still provides durable browser selection; verified upstream credential expiry and binding, MCP cutover and activation remain open.

Place authorization at the application service boundary and require repository queries to carry organization scope; Elysia controllers map expected auth, permission, missing-resource and conflict outcomes to typed 401/403/404/409. Every list/detail/write/export/import/batch/scheduler/history path and referenced ID must be checked. A gateway subscription, presence query, replay and forwarded command obtains be-01 authorization for its bound user/org; event routing includes organization. Recheck queued replay before delivery, invalidate sockets on membership changes and cap authorization leases so access ends within five seconds despite a dropped notification. A switch creates a new socket. mcp-01 binds selection to consent, code, grant, refresh family and access session; the signed delegation reaching be-01 includes local user ID, upstream issuer/subject, org ID, OAuth client ID, grant/family ID, scopes, audience and expiry. Its direct-upstream-token path is refused for resource tools unless it can establish the same binding. Current membership is checked on each tool request and refresh.

## Risks / Trade-offs

- Existing global catalog uniqueness and old writers require a bridge release. Do not open new organizations until every old reader and writer has drained and reconciliation passes.
- The current in-memory OIDC stores remain a restart limitation. Their durability is outside stage A; an organization context must never outlive its underlying session.
- The five-second gateway bound requires measured lease and invalidation behavior. Fail closed if membership checking becomes unavailable.
- Production may use a different identity mode or have users whose effective rights do not map cleanly to a role. Inventory is a hard activation gate.

## Migration Plan

1. **Inventory:** inspect deployed SHA, sanitized issuer/auth mode, users, Dany candidates, project owners, global catalogs, saved plans and relationship graph. Record a reviewed manifest; refuse zero or multiple Dany matches or access mappings that cannot preserve effective rights.
2. **Expand:** ship additive `migration.sql` and paired `down.sql` for identity mappings, organizations, membership and onboarding records plus nullable ownership mappings/shadow catalog structures. Preserve old columns and old-reader compatibility; test up/down on a copy of production-shaped data. No SQL is authored in this spec.
3. **Bridge:** deploy a version that writes legacy organization mappings for every new resource while preserving old behavior. Backfill existing rows idempotently, drain old writers, then reconcile again; require zero unmapped roots, zero cross-organization references and reviewed role parity.
4. **Enforce:** deploy organization-aware be-01/gw-01/mcp-01/fe-01 before activating the durable isolation marker. The deploy executor must prohibit routing an organization-unaware version once marked. Activate only after all old processes drain; enable creation of second organizations afterward.
5. **MCP credential cutover:** migrate the separate mcp-01 SQLite store with paired additive migration and rollback files. Add organization, stable user/identity and credential epoch fields to new family/session records; bind in-memory consent and codes to the same epoch. After every organization-unaware mcp-01 process has drained and been fenced from restart, and before the WBS isolation marker is committed, an MCP-store transaction advances a persistent epoch and revokes pre-activation families/sessions; activation waits for this durable acknowledgment. Every routable mcp-01 process checks the current durable epoch at exchange, tool call and refresh; reject old codes, old refresh tokens and null/old-epoch rows after restart; require fresh organization consent. Do not accept a direct upstream token or a refresh-retry call without current signed organization delegation to be-01. Pre-activation down migration must preflight absence of live new-format credentials; the permanent isolation marker blocks MCP-store reversal after activation. Missing, unreadable or malformed store/epoch state blocks service startup and activation. Pre-activation compatibility exception: until activation work withdraws it, before the epoch advances, mcp-01 still creates an **absent** store path (baseline plus binding migration, epoch 0) so existing dev, k3s and local first starts keep working; an existing empty, partial or unreadable file refuses. The store keeps a checksummed migration ledger, adopts a pre-ledger store only when it is exactly the baseline schema, and this release refuses any epoch other than 0.
6. **Rollback:** before activation, preflight and reverse paired migrations in dependency order without losing legacy records, and report the manual completion command on failure. After activation, both application downgrade and schema reversal across the marker refuse before changing routing or schema, even if second-organization data was deleted. Recover with an organization-aware release or forward repair. Test the actual swap abort path, which currently can continue restoring routing after schema reversal failure.

## Open Questions

1. Which exact production user ID is Dany's, and what are existing users' effective rights? Recommend: resolve from a reviewed inventory; block activation until unambiguous.
2. Which existing catalogs and saved-plan tables have global uniqueness or indirect references that need shadow structures? Recommend: finish a relation-by-relation inventory before migration design; refuse activation if any owner is unmapped.

## Slice 2.4B1: shared browser credential revocation authority

This slice establishes durable revocation state for the later logout, credential-rotation and refresh lifecycle wiring. It does not expose a public endpoint or activate organization-bound production behavior. The production composition remains `NO_BOUND_ORGANIZATION`.

The revocation key is the tuple `(verified credential kind, stable local user ID, SHA-256 of the exact verified access credential)`. Credential kind is native or OIDC. It is deliberately neither user-wide nor organization-wide, so revoking one credential pair leaves other credentials usable.

Add `browser_credential_revocations` with an additive migration and paired `down.sql`. Store only credential kind, user ID, lowercase 64-character digest, safe-integer credential expiry, and safe-integer revocation time. The tuple is the primary key. Keep user IDs for audit when an account is deleted. Never store raw credentials, cookies, refresh tokens, or email. Do not garbage-collect rows or reset revocations. Rollback may drop the table only after proving it is empty, including expired rows.

Expose a narrow application boundary for atomic, idempotent revoke and shared-store lookup. Repeating the same revoke preserves the original `revoked_at`; the same key with a different expiry throws. Every lookup reads shared storage without a process-local negative cache. An absent row in a valid migrated store is unrevoked. Missing/unreadable store, missing table, malformed matching state and failed writes throw; do not create, repair, or swallow errors.

For the later enabled composition, check revocation before membership listing, selection issuance, and resolving an existing browser organization binding. The committed revocation is the linearization point: requests after it refuse. A selection already in flight may issue its cookie, but protected resolution must refuse it after commit. Do not cancel transactions already authorized. Preserve delegation behavior; delegated requests cannot select a browser organization.

Acceptance proofs must inject each fault into the production path: an old intact token/cookie pair is refused across another process or restart after commit; removing the shared lookup makes that mounted test fail; a revoked token cannot obtain a new selection cookie and removing the selection check makes that test fail; other credentials and users remain valid; concurrent revoke/select remains monotonic and idempotent; unavailable authority and write failure surface as server failures without acknowledging revocation; rollback refuses every nonempty table; and production remains unbound. Record exact commands, outcomes and fault observations in `verify.md` after implementation.

## Slice 2.4B2: lifecycle fence, backend transitions and browser logout

### Decision adopted 2026-10-01

Following Astra high's source review and the user's standing authorization to resolve non-harmful blockers, adopt a shared durable browser-lifecycle fence. B1's per-credential `revoke()` alone cannot serialize logout against an in-flight refresh across processes. Do not claim that D2 is complete until this fence, lifecycle wiring and the server-acknowledged browser logout path all pass mounted proofs.

Coordinator decisions for this plan: (1) accept the durable generation fence and retained credential associations; (2) implement common native/OIDC server logout plus a separate frontend acknowledgment slice; and (3) refuse logout as `401 unauthenticated` when identity/association cannot be proved, while a proved retry of a committed closure is idempotent local `204`. These choices do not imply production activation or global provider-token revocation.

### Current seams

- `TokenStore` and `RefreshRecord` in `libs/wbs/adapters/auth/src/oidc-store.ts` hold provider refresh material in process memory and do not retain the verified access-credential tuple or durable generation.
- `refreshOidcSession` in `apps/wbs/be-01/src/controller/auth-oidc-endpoints.ts` uses unconditional `save()` when the provider retains its refresh token. That path can recreate or preserve a refresh session after another process commits logout unless completion checks shared state.
- The existing OIDC logout deletes local refresh state before attempting upstream revocation, and that failure-order property must remain.
- Password login and registration in `auth-password-endpoints.ts` issue credentials; common logout is currently mounted only with OIDC routes in `app.ts`.
- `SessionOwner.exit` in `apps/wbs/fe-01/src/runtime/session-runtime.ts` is intentionally local-only. It sends no request and revokes nothing, so a reload can restore the cookie identity.

### Durable lifecycle state

Add additive lifecycle migration(s) and paired `down.sql`, ordered after B1. The lifecycle record is keyed by a digest of the opaque OIDC browser-session correlation value and retains the stable local user ID, monotonically increasing generation, active/closed state, and current exact verified credential tuple. A companion association table retains every issued credential tuple `(kind, digest, expiry)` for that lifecycle and generation so delayed logout can prove its predecessor belongs to that lifecycle and revoke the currently active successor. Store no raw cookie, provider access/refresh secret, email or unverified token claims. This is coordination state, not durable provider refresh-token storage. Retain closed records, historical associations and old credential revocations; add no cleanup or reset. Rollback refuses if any lifecycle or association row exists.

Expose a narrow `BrowserAuthLifecycle` feature boundary with open, conditional replacement and close transitions. Refresh replacement validates the generation captured before provider I/O. Logout validates the presented exact credential against retained tuple-to-lifecycle history, then closes the currently observed active generation and revokes its current tuple in one shared-store transaction with B1. It does not require the caller's predecessor generation to equal the current generation. A retry against an already-closed lifecycle is idempotent local success only when the exact historical association is proved. Do not expose a DB handle or transaction graph to controllers. Missing, malformed, unreadable, stale-generation and write-failure state throws or maps to the typed refusal at the HTTP boundary; never initialize, repair, or treat it as active.

For OIDC, hash the existing opaque `__Host-wbs_session` correlation as the lifecycle key. Keep provider refresh secrets in the existing process-local `TokenStore`; after restart the browser must reauthenticate if that secret is absent. For native credentials without a refresh lifecycle, logout revokes the exact currently verified credential through B1; native replacement revokes only a proved predecessor, and an independent native login creates no synthetic shared lifecycle. Never revoke all credentials for a user. An expired OIDC access token may be associated only by exact digest to metadata persisted when it was verified and issued, never by decoding its expired claims.

### Transition ordering

1. Before successful OIDC callback or native password-login issuance, classify replacement inputs. With a proved OIDC predecessor (access credential plus matching correlation), atomically close that lifecycle and revoke its exact current credential. With a proved native predecessor, revoke only its exact verified tuple through B1, including when the replacement is OIDC. Do this before opening a replacement OIDC lifecycle or returning cookies. If neither predecessor credential nor correlation is presented, treat the login as independent. If a predecessor/correlation is partially presented or mismatched, refuse replacement without side effects; never infer identity from unverified claims. Failed authentication never retires existing authority. The separate OIDC identity-link callback issues no replacement access credential and does not close the current lifecycle.
2. At refresh start, capture the matching local refresh record and its shared generation before provider I/O. On a verified provider result, atomically require that exact generation to remain active, revoke the predecessor, retain its tuple association, associate the successor and advance generation. Use this conditional transition whether the provider rotates or retains its refresh secret; remove unconditional `save()`. Identical access-token bytes cannot be reissued after revoking that exact tuple; refuse and require reauthentication.
3. Install replacement refresh material in `TokenStore` only after the shared transition wins and only if the local record still matches the captured record. A losing completion neither overwrites nor deletes a winner. If provider rotation may have consumed the old secret but the durable commit fails, remove only that still-matching local record, issue no cookie and require reauthentication rather than blindly replaying a possibly spent secret. If the process crashes after durable commit and before local installation, shared denial remains authoritative and a later refresh requires reauthentication because provider material is absent.
4. Logout proves the presented credential's retained tuple association, then atomically closes the currently active generation and revokes its current credential. Logout does not compare the predecessor generation with the current generation. A proved retry against a closed lifecycle is local idempotent success. Delete matching process-local refresh material before upstream revocation; provider failure after local commit cannot reopen authority or prevent local retry acknowledgment.
5. Refresh/logout races are decided by shared state. If refresh commits first, logout—even when carrying the predecessor—closes and revokes the successor. If logout commits first, refresh commit fails. A late response cannot restore authority because its exact credential is revoked. For native requests without OIDC lifecycle correlation, exact verified B1 revocation is the logout linearization point.
6. The frontend calls server logout and requires both server acknowledgment and successful local project/session retirement before rendering successful signed-out state. Preserve `overtaken` and `fatal` outcomes and never restore a revoked runtime after failure. Model network/server refusal visibly. Keep switcher and stale-tab write work in 2.4C/4.6.

Success contracts preserve `204` for completed refresh/logout and `401 invalid_oidc_session` for missing, expired, replayed, closed or superseded refresh sessions. Invalid/ambiguous logout identity is `401 unauthenticated`; a proved retry of an already-closed lifecycle is idempotent `204`. Invalid Origin is `403 invalid_origin` before store/provider mutation; storage defects are `500`; modeled upstream provider outages retain their explicit unavailable/refusal classification. Clear hardened cookies only after the appropriate committed transition. The contract concerns browser organization authority; it does not claim global revocation of an upstream account or non-WBS API use.

### Required proofs and boundaries

Use deterministic deferred provider responses and real SQLite shared transactions, without sleeps for synchronization. Prove logout-first and refresh-first outcomes across separate processes and restart; unchanged and rotating provider refresh tokens; two simultaneous refresh completions; exact predecessor/successor revocation; independent credentials; mixed access/correlation pairs and delegation refusal before side effects; write failure without success/cookies; and provider logout failure after committed local denial. Watch each safety test fail with its relevant generation check, association, transaction, or ordering guard removed and record `Proof:` comments and observations in `verify.md`.

Production selection remains `NO_BOUND_ORGANIZATION`; a shared durable lifecycle does not itself activate organizations. Old organization-unaware processes also do not consult this fence. Production deployment still requires draining and fencing incompatible writers before activation. Existing switch/rollback gates remain open.
