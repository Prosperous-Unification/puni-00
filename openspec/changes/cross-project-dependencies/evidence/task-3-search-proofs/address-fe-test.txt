
 NX   The operating system refused the connection to the Nx Daemon socket (connect EPERM /tmp/.nx/1000/sockets/573dc6e4c8c9550395e2/d.sock). Continuing without the daemon.

Socket: /tmp/.nx/1000/sockets/573dc6e4c8c9550395e2/d.sock

Most often the socket belongs to a different user: a daemon left behind by running Nx under `sudo`, a different uid inside a container, or a working copy shared between accounts. If the socket is your own, a sandbox is refusing the connection instead.
If it belongs to another user, delete the socket above or set NX_SOCKET_DIR to a directory only your user can reach. If you are in a sandbox, allow unix sockets under the Nx socket root: `nx configure-ai-agents` writes that for Claude Code, and the per-agent setting is listed at https://nx.dev/docs/kb/nx-sandbox-unix-sockets


 NX   Nx was denied permission to create a plugin worker socket. Running plugins in the main process instead.

Plugins that expect isolation may misbehave, and this is slower than a worker.
Nx was denied permission to use its unix socket under /tmp/.nx or ~/.nx.
To fix this, do one of the following:
  - In `~/.codex/config.toml`, set `sandbox_workspace_write.network_access` to true and add /tmp/.nx or ~/.nx to `sandbox_workspace_write.writable_roots`. Codex has no setting that scopes sockets to a path, and `network_access` also grants general network access, so this is a broader grant than the other agents need.
  - Get permission to create sockets under /tmp/.nx or ~/.nx, or set NX_SOCKET_DIR to a directory you do have permission for.
See https://nx.dev/docs/kb/nx-sandbox-unix-sockets for details.
