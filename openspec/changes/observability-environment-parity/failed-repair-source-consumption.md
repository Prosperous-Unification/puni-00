# Task 118: consume the after-failure repair source

Design-only recommendation for root. Baseline: aa39 published `9034be7a2301f1944f30b524ada8f1a0303a7818`. No implementation, test, service, native observation, raw/image payload read, request construction, retained-state mutation or network operation was performed. The only deliberately written artifact is this report. Initial orientation reads accidentally used the tool's default login setting; subsequent calls explicitly used `login:false`; no startup warning was observed. No native provenance or passing R5 proof is claimed.

## Intent

Allow a fresh same-inode repair to name the exact independently recorded `afterFailedRepair` observation as a distinct historical relation. Preserve the original failed request, its immediate-postboot snapshot, reservation, failure, source pins and outcome. Validate the original failure and both independent capture relations, require independently accepted strict settlement of that exact reservation with K still charged, and freshly observe/admit the current original inode under the existing staging lock before any raw mutation. Continue to refuse operational admission while whole-input qualification remains unavailable. This is one complete conditional producer/consumer source unit, not operational settlement, a retry, completed content verification, or full observability parity.

## Decision and alternatives

1. **Recommended: additive repair request v2, semantic join to existing settlement v2, and current producer observations.** Both captures independently join the same immutable original metadata and native identity. They need not have identical schemas or digests. Keep the nine settlement names, records, latch and existing accounting semantics unchanged. A successful settlement cannot alone admit repair.
2. **Add settlement v3 with explicit source-observation and original-exact-capture digests in its HistoryBinding.** This gives a direct byte-level commitment from settlement to those two files, but is unnecessary if the consumer verifies the full transitive join below. It would expand an already completed mechanism and disqualify old settlements without proving the original observer's native provenance. Use this only if root interprets the requirement as a literal historical commitment to the two file hashes, rather than an independently verified relation; v2 did not make that commitment and cannot be retrofitted.
3. **Reuse `postBootEvidence` or accept only pinned JSON.** Reject: this either rewrites historical meaning or gives self-authored claims authority. Neither supplies a complete producer/consumer boundary.

No ADR: this is a reversible extension of the required existing recovery flow. Root should record one glossary definition in the existing observability terms section: **Repair source after failure** — a read-only observation of the original raw inode linked to a specific failed repair; it preserves that failure and grants no repair or debt-release authority.

## Independent history/settlement join

One worker-role function `read_failed_source(repair, request)` returns a typed internal relation, never an admission boolean. It:

1. Reads original v1 request and history using historical semantics, recomputes its sourceDigest from its recorded pin mapping, and joins the four original records. Reuse/refactor the existing settlement historical validator; do not duplicate a weaker version.
2. Joins source observation's six relation fields to original nonce, actual request hash, recomputed original source hash, exact reservation/failure byte hashes, and exact capture file hash. Joins original guest and all immutable original identities to original history. `rawBefore` is original expectedRaw; `rawAfter` is source expectedRaw; ready/failure times and ready/reservation identities agree with original records. Recorded original source revision is historical information, not a current pin requirement.
3. Reads selected settlement through the existing **complete strict namespace reader** and accounting API. Require accepted namespace for this original nonce, exact settled reservationDigest/grossBytes, no unresolved duplicate of that same reservation, and settlementDebtBytes exactly33554432. Never infer settlement from a certificate or accepted receipt alone.
4. Independently join settlement HistoryBinding to the same original nonce/request/source/request-binding/reservation/ready/failure/directory/raw identity. Read its pinned terminal capture through its own closed schema and join PID/start/unit/invocation/cgroup/creator/raw identities to both original ready and the exact failure capture. Original exact capture and terminal capture remain separate files and separate digest roles. Require all common facts to agree; timestamps establish separate observations and are not forced equal.
5. Require the source snapshot, selected settlement expectedRaw and certificate finalSnapshot to agree exactly. A changed timestamp/allocation/map means this historical current-source specimen is stale for this operation and refuses; no timestamp rebasing.

This is a complete transitive join: changing either capture to another original attempt requires changing immutable original request/reservation/failure/ready digests and is caught. Existing settlement v2 did not record the exact failure-capture hash or observation hash; the consumer must say so. It independently validates their relation now. If a literal settlement commitment to those hashes is required, use alternative2 and require it for new recovery; never pretend v2 committed them.

History validation remains usable after a successful new repair has changed timestamps: it validates immutable relations only. Fresh admission is a separate function. Update continued-lineage's v2 branch to compare its repair artifact `before` with the after-failure snapshot while preserving the inherited original postboot comparison against the original failed request. This prevents a new successful repair from becoming an unusable dead end for the existing seed/guest flow.

**A failed successor remains representable.** Keep its ordinary reservation, request-binding, worker-ready and failure schemas unchanged. The accounting reader must enumerate that failure, retain its full new G and continue charging the already retained K; it must not throw merely because the bound repair request is v2 or pretend the old settled reservation covers this new debt. `SettlementContext.read_history` must recognize both original repair request shapes and use the selected request's own expectedRaw and digest, with exactly one predecessor v1 relation for v2; derive its finite metadata roles accordingly, including the fixed external exact-capture path of that predecessor. Do not recursively call whole-ledger accounting from that immutable history parser. A fixture must fail the successor after readiness and verify this accounting result through the actual reader.

This does **not** permit a second settlement operation: the existing one-settlement namespace/debt policy and consumed latch remain strict. Attempting to settle the failed successor when the predecessor settlement exists must refuse before latch consumption/publication under the current policy, while both failures remain intelligible and the new G remains charged. Repeated recovery chains or a second K/settlement namespace are outside this unit and are not silently enabled to make the new schema look future-complete. Add an actual production-path negative for that refusal. Recognizing the new failed-request shape and refusing forbidden second settlement is different from rejecting its history as malformed.
