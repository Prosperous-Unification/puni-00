# Test axes implementation shape

## Scenario identity

`openspec/scenario-allocations.json` is one versioned, append-only event journal. The only current index is derived from it. `import` reserves existing hand-written IDs unchanged; `allocate` issues the next unused ordinal in the capability namespace; `split` issues a new ID with the old scenario as predecessor; `rename` retains the ID and records its prior title and source revision; `retire` leaves a tombstone. A new allocation never reuses any ID present in the journal, including retired ones.

The `twilight-burokrat scenario` command reads this journal and a selected OpenSpec spec, then prints a proposed journal/spec edit. The caller applies and reviews that proposal. The allocator has no write side effect. Candidate/base continuity is deferred until Burokrat has a production rule path that can read both trusted base and candidate journal blobs. Comparing only a candidate journal with itself would let a deleted retirement event disappear. The approved B3 integration boundary is recorded in [the candidate/base design note](../../../docs/superpowers/plans/2026-10-09-test-axes-b3-candidate-base.md).

The current adopted set contains the three identified specs: the active `project-assignment-reads` spec and the `service-taxonomy` and `test-axes` change specs. These have 73 distinct identifiers imported into the first journal. The current command selects one spec path explicitly. The B4 whole-tree selector must choose an active canonical spec from `openspec/specs/<capability>/spec.md` or an active change's `openspec/changes/<change>/specs/<capability>/spec.md`; archived copies and a future synced duplicate are one scenario lineage, not separate obligations. Other legacy OpenSpec headings currently lack IDs (4,059 at import time); they are migration debt, not evidence of global provenance or full coverage. Burokrat must expose this debt as it expands adoption.

## Coverage boundary

The existing `project-assignment-reads` tests cite its three imported IDs. The pilot command joins only fresh reports from its declared API and Unit targets and prints a hand coverage table. B4 consumes the journal and the same selected scenario identities to produce certifying scenario and structural ledgers, enforce T2, and validate dispositions. The static Burokrat judges recorded reports; it does not run test targets.

## Level classification and runner evidence

`libs/shared/domain/test-levels` owns the pure ten-row precedence function. It has no runner or policy imports, and its caller supplies the frontend source root. Burokrat supplies Conformance, Architecture, Performance, Browser, frontend Node and manual membership evidence, then applies that function to the selected candidate. Devsync consumes the same public library for target checks. The shared-domain placement satisfies Nx's existing product and scope rules for the Burokrat application and the product-less devsync tool; Burokrat still owns discovery, thresholds and enforcement.

A collection adapter must produce either a nonempty file plan with its discovery inputs or an explicit `no-cases` result with a reason. The earlier pure planner had no production caller and was removed; the union is a required future runner-boundary contract, not an enforced Burokrat check today. The three new find-based memory/SQLite level targets currently clear their prior report, fail on selector errors, and refuse empty selections before Bun can default-discover another level. Performance currently has no fixture with declared thresholds; an empty Performance target must refuse with `no-cases`, without a passing JUnit report. Task 2.1 remains open until a real Performance fixture proves isolated execution. Manual requires a reviewed procedure and report bound to source and environment; its validator must refuse absent or stale evidence and may never synthesize a human pass.

The [Performance target design](../../../docs/superpowers/plans/2026-10-09-test-axes-performance-target.md) pins the candidate declaration, shared `libs/shared/domain/test-evidence` contract, the existing external Burokrat `RulePolicy.performance` authority, strict Playwright JSON discovery, immutable execution inputs and companion evidence binding. The policy pins exact config path/content digest, project, runner version and reviewed case-record digests; the registered Performance rule requires it even in observe mode. The adapter refuses an empty selection after clearing prior artifacts; a nonempty scratch-only candidate now runs exact Playwright discovery and execution in a detached committed checkout, collects one finite attachment per case, calls the Burokrat judge and writes JUnit plus a digest manifest. A fully evaluated threshold breach produces failing JUnit and a nonzero target. The shared declaration digest uses portable SHA-256 and agrees between Bun and Node. The Burokrat `candidate-identity` command uses the same candidate snapshot/hash as `check` and returns a non-certifying, versioned identity; the adapter checks its tool and project version before running. Playwright receives a minimal environment and a bounded asynchronous process.

The current `check --performance-evidence` JSON transport and collector manifest remain **non-certifying** (`certifies:false`). Manifest hashes alone cannot attest execution, and Burokrat does not yet read and recompute the JUnit/discovery/run bytes. Certification requires an externally authenticated receipt binding the manifest digest, invocation, candidate and trusted collector/runtime identity, followed by Burokrat verification of the bytes, case sets and comparisons. The manifest also needs raw discovery/run artifact bindings. The policy path is selected by the trusted external caller or an operator-provided environment value; the candidate declaration cannot choose it. Burokrat's own external-artifact reader remains the authority for policy containment, stable bytes, fatal decoding and semantic validation. The adapter invokes Burokrat from a fresh empty directory outside the candidate with an allowlisted environment, so candidate `bunfig.toml` preload cannot alter its verdict. It checks detached checkout HEAD, status and declaration/config bytes before and after Playwright discovery and execution. These snapshots detect persistent changes; a same-user write-and-restore between snapshots remains possible without stronger runtime isolation and is one reason the adapter cannot certify. The current candidate declaration is empty; the scratch fixture only proves the code path and creates no repository Performance obligation. A real reviewed nonempty repository fixture and run remain a separate hard gate for Task 2.1.

The current JUnit target additions cover separate store-memory Unit and Conformance runs, store-sqlite Conformance, frontend Unit/View commands, and distinct ordinary, packaged and portable Playwright Browser reporter paths. The frontend's UTC View, Auckland View, Node Unit and root Unit collections are distinct. Existing legacy targets remain intact; `wbs-store-memory:test:unit` is an explicit mixed aggregate. The portable Browser target ran and wrote JUnit, but Playwright's testcase entries carry `classname` rather than the `file` attribute that Burokrat's Bun report reader requires. A Playwright adapter must bind that classname to exactly one collected file in a companion manifest, reject ambiguous mappings, and bind each report to target, config, candidate and exact collected files. Report reuse or overwrite across invocations must be rejected before Burokrat treats it as coverage. Ordinary and packaged Browser execution remains unverified.

The Task 2.1a collection verifier is the additive `tool-devsync:test-levels:verify` target and `verify-test-levels-cli.ts`. It declares six Bun level targets and frontend Unit/View targets with four separately configured Vitest phases and exact JUnit output paths. Bun files come from each real shell selector; Vitest files come from each real config's `vitest list --filesOnly --json=<owned-file>` output, since piped stdout is empty with the installed Vitest version. It creates a unique temporary directory, refuses absent, unreadable, malformed, empty, nonregular, escaped or duplicate listed files, and removes its owned directory. Paths are canonical workspace paths before the shared classifier sees them. Every covered source/root test must be collected by a declared level target. Existing broad test targets have explicit allowed level sets; the FE Browser aggregate has exact member targets. Unknown targets, undeclared mixed targets and aggregate drift refuse. The CLI accepts a proposed project manifest for audit without changing the workspace. This establishes collection membership and report path declarations, not execution of the level targets, a candidate-bound report receipt or authenticated coverage. Browser, Performance and legacy targets are explicit inventory exceptions rather than verified Unit/View collection claims.

The Browser adapter has separate additive ordinary, packaged and portable level targets plus an FE aggregate. Each target requires a clean committed candidate and creates a detached checkout. Ordinary setup uses the repository setup script; packaged and portable modes build their artifacts in that checkout. The latter modes inventory every regular served file by path and digest, reject symlinks and special files, and recheck that inventory after discovery and execution. Runner timeouts kill the detached process group and reject at the deadline. Playwright discovery uses JSON only. Execution writes JSON and raw JUnit under one invocation, and the adapter compares exact config/project/file/full title identities and outcomes before writing normalized JUnit with explicit `file` attributes. Skipped opt-in cases remain skipped in JSON, JUnit and the manifest; a skipped case never counts as passing coverage, and an all-skipped successful run is refused. The raw artifacts, normalized report and manifest live in one immutable invocation bundle. `tmp/junit/browser/<mode>.current.json` is the only mutable publication point and is replaced with one atomic rename after the bundle is complete; readers pin it once, then resolve and verify the report/manifest pair with `readBrowserPublication`. The legacy shared XML and manifest paths are removed and cannot serve as reader fallback. Environment selection is fixed to CI mode with a validated port shift and optional regular Chromium selection. Burokrat's candidate identity is included. The manifest is explicitly `certifies:false`; Burokrat does not yet independently verify its raw bytes or an externally authenticated receipt, so the adapter's report is operational evidence only. Earlier sandboxed portable execution reported a Chromium `Operation not permitted` failure, and an approved unsandboxed run of the earlier collector passed both cases on 2026-10-09. The revised collector still needs a fresh real portable run. Ordinary and packaged collection also need fresh execution evidence, and Burokrat-side Browser consumption/classification remains open.

Invocation admission uses a short per-mode filesystem lock to replace an owner token and remove the previous pointer before candidate preflight. Publication reacquires that lock and requires the same owner token, so an older collector cannot publish after a newer attempt is admitted. A lock deadline refuses and removes the prior pointer; invocation failures leave that mode without a current publication.

The next Burokrat Browser slice is a standalone diagnostic over a committed selection and an external RulePolicy. The policy pins each permitted mode's exact config path, content digest and project selection. The reader captures the current pointer once, verifies owner and latest-request tokens, reads each required bundle file once as a regular file without symlinks, then rechecks pointer and tokens. It independently decodes Playwright discovery and run JSON and both JUnit documents, matching exact case identities, outcomes, counts, config, project and runner version to the manifest. It also checks the declared served inventory's normalized unique paths and digests. The diagnostic reports observed cases with `authentication:{kind:'absent'}` and `certifies:false`; it emits no verified coverage. Build artifact bytes and the Playwright process exit status are not published in the bundle, so the served inventory's digest claims and process success cannot yet be independently recomputed. An external authenticator and a registered rule integration remain required before Browser observations can affect scenario coverage or admission.

## Assumptions to revisit

The allocator derives the ID namespace from the final spec directory name and never renumbers after a scenario moves. Cross-capability moves need an explicit successor/predecessor policy before they can be automated. The first journal imports only currently identified active specs; expanding adoption requires an explicit reviewed import or allocation step.

## B3 production rule checkpoint

`SPEC-SCENARIOS` now reads the external `RulePolicy.scenarios.baseRevision`, requires a full SHA and a strict ancestor for committed selections, and requires an exact selected base plus ancestry to checkout HEAD for staged/working selections. It reads both journals and active spec bytes from selected Git entries with replacement objects disabled. A missing base journal requires an external bootstrap record naming the same base SHA, initial journal digest, reviewer and reference. Candidate events preserve the canonical values of every base event as a prefix. The verdict exposes a versioned evidence digest over policy, candidate, base, journal digests, bootstrap and selected spec bytes. Legacy unidentified headings become mode-sensitive findings. This verdict still has `certifies:false`.

Selector version 2 recognizes exact active main and change spec paths and ignores archive paths and fenced headings. It parses immutable Markdown ASTs, keys requirements by capability and exact title, retains canonical order, and appends new requirements by stable key order. It applies `ADDED`, `MODIFIED` and `REMOVED` without inferring an order between changes: competing operations are refused. A synced identical `ADDED` requirement is one lineage with a source alias. `MODIFIED` must retain canonical scenarios by ID or, for unidentified headings, exact title. Removal of an adopted requirement requires journal retirement. The evidence binds every active input path and digest, the effective requirements and aliases, applied operations and removals. The current repository's concurrent deltas are expected to require reconciliation; they are not automatically made passing. The rule does not yet provide the citation-removal ledger proof or a clean pilot API target, so Task 2.2 stays open. The current checkout-HEAD comparison is sampled during the specifications evaluation; a ref change during earlier candidate snapshot selection still needs a selection-bound invariant before staged/working verdicts can be trusted for certification.

## Manual evidence validator

Implement a standalone committed-candidate inspector in Burokrat evidence code before integrating Manual outcomes into B4. It consumes candidate disposition and procedure files plus an externally selected `RulePolicy.manual` that pins exact reviewed disposition and report digests. Use the existing stable external-artifact reader for policy, approvals, reports and environment observations. Missing, unreadable, malformed, ambiguous, unsupported, or escaping inputs refuse. The CLI captures UTC time once; the pure evaluator receives that instant for deterministic checks. Git identity strings, report claims, file ownership and mtimes never establish reviewer or operator authority.

Candidate dispositions identify a canonical scenario, a nonblank manual reason, a procedure path, and a nonempty unique set of touched module IDs. A versioned procedure record binds its scenario and title to ordered nonempty steps with unique IDs, instructions and expected observations. External review approvals bind the complete disposition and procedure digests, reviewed requirement/source scope, reviewer identity/reference, and `reviewedAt`/`reviewBy`. A report binds its run ID, scenario/title, disposition/procedure digests, source revision and full reviewed source scope, operator, ordered step observations, outcome, and a separately observed environment identity/digest. A second external approval binds the exact report and environment observation digests, run/operator/times, and accepting reviewer/reference. Unknown or duplicate records refuse. Success requires exactly one passing observation per declared step and an aggregate outcome that agrees.

The environment observation is a versioned external record with observation ID, environment ID, UTC observation timestamp, tested source revision and nonempty descriptive attributes; its tested revision must equal the report's source revision. The report uses `startedAt` and `completedAt`; the external acceptance uses `acceptedAt`. All timestamps must be valid UTC calendar values and satisfy `startedAt <= completedAt <= acceptedAt <= capturedNow`. Review and environment observation timestamps cannot be future values; the review deadline must be a valid UTC date no earlier than `reviewedAt`. Capture `capturedNow` exactly once in the CLI and pass it into the pure evaluator. A deadline is valid through its named UTC date; if the captured UTC date is later, refuse and name the scenario and overdue date.

Resolve the scenario through B3's effective canonical selector and journal lineage, refusing unresolved competing changes, unknown/retired IDs and ambiguous matches. Derive the containing requirement digest and each complete touched-module digest from selected Git objects and module indexes. Require source revision ancestry and reconstruct historical scope; any intervening change to the requirement, procedure, module contents or membership makes a report stale, including change-then-revert. Missing objects or incomplete history refuse. This deliberately invalidates all reports for a containing-requirement edit, including sibling-scenario edits.

The selected candidate uses the externally pinned B3 base for its current effective selection. The tested revision independently reconstructs its own immutable journal and all active main/change spec blobs; it must identify exactly one active scenario with the reviewed title and containing requirement. That tested commit may precede the current B3 base. Report/review procedure digests and step observations bind to the tested procedure; a later valid procedure edit makes currency stale. The selected disposition and its policy pin remain exact current-candidate joins, so declaration edits can refuse before currency evaluation.

For each commit in the full tested-to-selected DAG range, read a complete committed snapshot before filtering touched modules. The existing index checker establishes nearest-index ownership and complete membership. A versioned canonical module scope includes the module ID, index path, the index's own `{path,mode,blob}` tuple, and every owned member tuple in byte-sorted path order; child indexes belong to their parent while child descendants belong to the child. Compare each intervening effective requirement, valid procedure record and module scope to the reviewed tested scope, so an edit followed by a revert remains stale. An unrelated descendant stays current. A valid scope difference is stale; a missing object, ambiguous or malformed historical selection/index/procedure, incomplete Git graph, shallow boundary or graft refuses. Replacement objects cannot substitute selected bytes. All Git reads disable replacement objects, and history inspection covers merge branches rather than only the first-parent line. A newly reachable side branch that predates the tested commit need not contain the tested journal or procedure: compare every parent edge for changed relevant paths, including any README that may introduce ownership, and mark stale conservatively. Verify the complete object closure of excluded side parents; preserve leading BOM code points in Git path output so relevant path changes cannot disappear.

The inspector reports validation, currency, outcome and provenance separately and always emits `certifies:false`. Once all evidence is valid, a typed CLI verdict maps an overdue review to `state:overdue` and `validation:refused`, a consistent failed or skipped run to `state:failed` and `validation:passed`, a changed source with a passing run to `state:stale`, and a current passing run to `state:current`. The CLI emits JSON for these evaluated outcomes and exits zero only for current; missing, malformed, untrusted or inconsistent evidence instead exits one with a named stderr refusal and no JSON. A step aggregate is failed if any step failed, otherwise skipped if any step skipped, otherwise passed; a declared aggregate mismatch refuses. Overdue takes precedence over failed, which takes precedence over stale. The returned procedure digest identifies the tested procedure, with a separately named selected procedure digest. A policy-selected approval is an operator trust assumption; it is not independent authentication of a human. Synthetic passing fixtures must never create production coverage or passing Manual JUnit. B4 may consume a successful Manual observation only after its own provenance contract is met.

Assumptions: committed selections only in the initial slice; review dates use UTC and remain valid through the named date; external policy is the authority for exact review/acceptance identity and timestamps; the human-reviewed touched-module set is a scope assertion, not proof of a whole capability chain; conservative requirement/module invalidation is preferred to preserving reports across edits; no real procedure or human run is claimed until reviewed artifacts exist. The current repository remains a refusal while B3's active spec conflicts are unresolved.
