## ADDED Requirements

### Requirement: `fe-01` boots via Vite with React 18 and TypeScript

`apps/fe-01` MUST be a Vite-built React 18 single-page application. Development server MUST run via `nx serve fe-01` and provide hot module replacement; production build MUST output static assets ready for Caddy to serve.

#### Scenario: Dev server serves the app with HMR

- **WHEN** `nx serve fe-01` runs
- **THEN** a Vite dev server listens on the configured port
- **AND** editing a source file causes Vite to log an `hmr update` line to stdout for the changed module

#### Scenario: Production build produces static assets

- **WHEN** `nx build fe-01` runs
- **THEN** the output directory contains an `index.html`, a hashed JS bundle, and hashed CSS assets
- **AND** no Node.js runtime is required to serve the output

### Requirement: TanStack Router with file-based routing

`fe-01` MUST use `@tanstack/react-router` with its file-based routing convention. Routes live under `apps/fe-01/src/routes/`. The generated route tree file (typically `routeTree.gen.ts`) MUST be gitignored.

#### Scenario: A new route file is automatically registered

- **WHEN** a developer creates `apps/fe-01/src/routes/about.tsx` and reloads the dev server
- **THEN** navigating to `/about` in the browser renders the new route
- **AND** the route is typed in the generated route tree

#### Scenario: Generated route tree is not committed

- **WHEN** `git status` is inspected after `nx build fe-01`
- **THEN** `routeTree.gen.ts` does not appear as tracked or modified

### Requirement: shadcn/ui installed via `@nx-extend/shadcn-ui`

`fe-01` MUST use `@nx-extend/shadcn-ui` as the shadcn/ui integration. Components generated by the plugin MUST land under `apps/fe-01/src/components/ui/` and be importable via the `@/components` path alias. If the plugin fails on the chosen Vite+TanStack Router setup within a 1-hour spike budget, the fallback path MUST use the shadcn CLI directly with equivalent outputs.

#### Scenario: Generating a Button component via the plugin

- **WHEN** the Nx generator adds a `Button` shadcn component
- **THEN** the file `apps/fe-01/src/components/ui/button.tsx` exists
- **AND** `import { Button } from '@/components/ui/button'` resolves and typechecks in a route file

### Requirement: TanStack Table and d3 wired for later use

`fe-01` MUST list `@tanstack/react-table` and `d3` as runtime dependencies and MUST ship a minimal smoke example demonstrating each (a tiny table using TanStack Table and a tiny SVG via d3), so future features can import without adding deps.

#### Scenario: Build succeeds with both libraries imported

- **WHEN** `nx build fe-01` runs
- **THEN** the build succeeds with the TanStack Table and d3 smoke examples present
- **AND** the production bundle includes both libraries

### Requirement: TanStack DB configured for local/server dual-mode operation

`fe-01` MUST configure TanStack DB with two modes selectable at runtime: `local` (browser-persisted only) and `server` (sync enabled). Server mode MUST use the reconnecting WebSocket client from `@wbs/realtime` pointed at `gw-01`, with HTTP requests against `be-01`. In this change, no feature-level collections are wired; only the seam is in place and switchable via a config flag.

#### Scenario: Local mode keeps data in the browser only

- **WHEN** TanStack DB is initialized with `mode: 'local'`
- **THEN** no WebSocket connection to `gw-01` is opened
- **AND** no HTTP requests to `be-01` originate from the TanStack DB sync layer

#### Scenario: Server mode opens a WebSocket via `@wbs/realtime`

- **WHEN** TanStack DB is initialized with `mode: 'server'`
- **THEN** an authenticated WebSocket to `gw-01`'s `/ws` path is opened via the `ReconnectingWsClient` from `@wbs/realtime`
- **AND** subsequent `ping`/`pong` exchanges succeed end-to-end

### Requirement: `fe-01` ships as static assets served by Caddy, not a long-running process

The production deploy of `fe-01` MUST be a static asset directory served directly by Caddy. No Node/Bun runtime process for `fe-01` MAY run on the deploy host.

#### Scenario: Deploying `fe-01` does not start a container

- **WHEN** `nx run tool-deploy:deploy-fe` runs
- **THEN** the remote action is an atomic directory swap under `/srv/wbs/www/` followed by `caddy reload`
- **AND** no container named `fe-01` exists in `docker ps` on the remote
