## Context

The integration point is the outer dispatch. The ordinary gate resolves its target in the launcher, assigns `gate:<sha8>`, captures the external verifier into an outer-owned temporary directory, and passes its path in `H2PUNI_GATE_TRUSTED_LAUNCHER`. The only payload arguments are the fixed script and full commit. Dash already implements the difference between ordinary and calibration jobs in `runHostJob` and `calibrateHostJob`. The catalogue validates arguments after argv[0], so the outer launcher itself must fix argv[0].

## Decisions

1. In `bin/h2puni-gate.sh`, initialize selection from the command line on every invocation. Reserve only first-position `--calibrate`, require exactly two arguments and a nonempty second argument, then feed that target to the ordinary Git resolver. The tool-facing SHA is always resolved once to a full commit. Preserve the ordinary `${1:-HEAD}` path and its existing argument handling. Keep the existing 1800-second outer wait default, explicit override behavior, poll handling, non-export of the wait budget and cleanup trap.
2. Share the target, label, activation checks, captured verifier and read-only verifier-module resolution. At the final dispatch construct the fixed payload argv from the launcher root and resolved SHA. For ordinary use preserve the literal production `HEAVY_LOCK_JOB_TYPE=gate run_heavy_job -- …` call. The checkout verifier in `ops/switch-mode.ts` inspects the launcher at committed HEAD for a real call to that shim.
3. For explicit calibration refuse any set `DASH_JOB_ID` and require the existing fixed-path `read_host_pool_enrollment` to return `enrolled`. Propagate its error status and diagnostic. Report positive unenrollment as an unavailable calibration host with exit 70. This branch goes directly to the existing enrolled forwarding **function**, with operation literal `calibrate`, type literal `gate` and the same fixed payload argv. Existing `run_heavy_job` supplies literal `run` to that private function at its sole enrolled call site. The public `run_heavy_job -- command …` signature stays intact. Keep these two internal choices closed. Avoid any exported switch or new command taking arbitrary calibration payloads. No hostname, magic PATH or operator-set enrollment flag is needed.
4. In `bin/heavy-lock-lib.sh`, carry the internal operation argument to `ops job` within the present `run_enrolled_heavy_job` process, trap, wait and cleanup logic. Preserve stdin, Dash fd ownership, signal forwarding, exit statuses and required-tool refusals. The ordinary nested branch remains responsible for placement, catalogue exclusive ids and admission. The payload continues to independently check authority under the hold. Existing clean checkout, mode checks, verifier execution, frozen install, gate steps and restoration stay in their current owners.
5. Replace the gate-specific outer-inside-calibration example in the Dash resource guide with the public launcher command. Point the gate-host enrollment procedure at that command for `gate`. Document invocation from the designated launcher, use of the same partition for comparable measurements and the separate ordinary SHA receipt.

## Risks

The launcher test fixture configures sixteen 1-GiB disk units. Actual calibration admission tests free space for the entire configured disk budget, even when its tiny fixture gate uses almost none. Give the dedicated disposable calibration fixture a small valid disk budget **before pool initialization**, as in `ops/calibrate.test.ts`, and use an explicit zero queue-wait for the focused fixture where appropriate. Assert that value in the captured argv. Keep the existing ordinary default-wait control and existing concurrency fixture meaningful. This avoids spending 30 minutes behind a predictable fixture refusal. Live Dash owns its actual pool bounds. Calibration omits both memory properties but retains the execution timeout.

The fixture's fake systemd scope does not create a real kernel cgroup. A nested test that fails only the cgroup-placement check cannot establish the exclusive-unit failure. Use the existing simulated in-scope reader for that one local reproduction, and require the `gate_tree` diagnostic. In contrast, test the successful calibration through the true outer launcher and Dash calibration implementation in the existing private namespace. A verifier preparation failure occurs outside admission. A verifier rejection on candidate content occurs after admission.
