## Context

The scheduler (`libs/domain/src/schedule.ts` — it moved out of be-01 on 2026-09-02) is a deterministic millisecond pass (Fast). It is immediately visible, the sole fallback, and never labelled optimal. WBS has no optimization today. Dany approved adding an optional dual-objective mode using official OR-Tools CP-SAT. Architecture section 1 (toggle, PRI+Time concurrency, exact-hash SQLite cache, one generation per project) and sections 2-4 (behaviour, failure, test design) are all approved; this design records the settled technical shape.

## Goals / Non-Goals

**Goals:**

- Compute Priority-first (PRI) and Finish-first (Time) schedules with a real constraint solver, concurrent, behind a project-wide OFF-by-default toggle.
- Keep Fast unchanged as the preview and fallback.
- Cache validated results in durable SQLite; broadcast newly stored results so collaborators converge.
- Surface a compact comparison indicator without a toast or modal.

**Non-Goals:**

- No proven optimality (best-found only).
- No daemon, port, sidecar, or outbox.
- No fix to the known capacity/floor hand-off audit finding.
- No timer retry; no per-user objective.

## Decisions

- **Runner:** official OR-Tools CP-SAT in its own versioned Python package `wbs-solver`, invoked by Bun as a short-lived stdin/stdout CLI. No import, no daemon, no HTTP port.
- **Concurrency:** optimization ON computes PRI and Time concurrently for one canonical input. Engine Fast/Optimized and Objective Priority-first/Finish-first only select which cached output is displayed.
- **Objective mathematics and the priority numeric domain (Sol r6 Important 9):** `MAKESPAN = max finish`; `MOVEMENT = Σ |start(s) − baselineStart(s)|` against the quantised baseline; `PRIORITY = Σ w(s)·finish(s)`. The previous weight `w(s) = (P_max + 1) − p(s)` was unsafe on legal data: `asOptionalPriority` accepts any safe integer ≥ 1 with **no product ceiling**, so `P_max + 1` already loses integer precision at `Number.MAX_SAFE_INTEGER`, and multiplying that weight by a finish and summing over slices overflows CP-SAT's signed 64-bit linear expressions. Priority is an **ordering** in this product, not a metric, so the weight is now the **dense rank of the priorities actually present in the canonical input**: let `D` be the sorted set of distinct resolved leaf priorities (by `priorityByLeaf`'s nearest-ancestor floor rule) and `R = |D|`; then `w(s) = (R + 1) − rank(p(s))` with `rank` 1-based ascending, and `w(s) = 0` for a leaf with no priority above it. This preserves every pairwise ordering the raw numbers expressed, is stated here as a deliberate semantic choice rather than smuggled in, and bounds the term by `Σ w(s) × horizonUnits ≤ N·(N+1)·horizonUnits`. **The bound is checked, not assumed:** the request builder computes the exact worst case `Σ w(s) × horizonUnits` and refuses before spawn with the new failure reason `objective-overflow` if it exceeds `2^62`, which leaves CP-SAT its own headroom. `R = 0` — no leaf carries a priority anywhere — makes every weight zero, so `PRIORITY` is identically zero, stage 1 is vacuous, and PRI degenerates to Time; that is the honest semantics of “no priorities are set” and is stated rather than leaving `P_max` undefined over an empty set. PRI minimizes `(PRIORITY, MAKESPAN, MOVEMENT)` lexicographically, Time minimizes `(MAKESPAN, PRIORITY, MOVEMENT)`. These are **not** total orders: ties exist and production is not required to break them reproducibly.

- **Anytime staged lexicographic — one stage-status matrix (Sol r6 Critical 7):** lexicographic order is implemented as staged optimization, never as a weighted sum, and the wall-clock budget is divided by stage — `STAGE_BUDGET_SPLIT = [0.60, 0.25, 0.15]` of `budgetMs`, an exported constant, with a stage that finishes early donating its remainder to the next. Every stage installs the previous stage's incumbent as a solution hint. The prior text left two rules that could choose different outcomes for the same run and a task that still said “equality at the found value” for every stage; **this matrix is now the single authority, and the Python implementation, the response schema and the tests are all generated from it.** For stage `k ∈ {1,2,3}` with term `Tₖ`:

  | Stage status | Constraint added for later stages | Staging | Published result | `objectiveValues[Tₖ]` |
  |---|---|---|---|---|
  | OPTIMAL, value `v` | `Tₖ = v` (an equality is sound only here, because `v` is proved) | continue | last incumbent | `{ value: v, bound: v, status: 'optimal' }` |
  | FEASIBLE, incumbent `v`, bound `b` | `Tₖ ≤ v` — never an equality, because fixing an unproven incumbent is not lexicographic minimisation over the feasible set, while `≤ v` excludes no solution at least as good | continue | last incumbent | `{ value: v, bound: b, status: 'feasible' }` |
  | UNKNOWN **with** incumbent `v` | `Tₖ ≤ v` | continue | last incumbent | `{ value: v, bound: b, status: 'feasible' }` |
  | UNKNOWN, **no** incumbent, `k = 1` | — | stop | **nothing**; the variant fails with `no-solution` and Fast stays visible | n/a |
  | UNKNOWN, **no** incumbent, `k > 1` | — | stop | **stage `k−1`'s incumbent**, which is feasible for the original constraints and already satisfies every bound added so far | `{ value: null, bound: null, status: 'unknown' }` for `Tₖ` and every later term |
  | INFEASIBLE, `k = 1` | — | stop | nothing; `invalid-output` — Fast found a placement for the same graph, so this is a contract violation rather than a plan property | n/a |
  | INFEASIBLE, `k > 1` | — | stop | nothing; `invalid-output` — every added constraint is satisfied by the previous incumbent (an inequality at its own value, or an equality at a proved optimum), so a later stage cannot become infeasible unless the model is wrong | n/a |

  The `k > 1` UNKNOWN-without-incumbent row is the case the earlier prose decided two ways: a valid anytime result is **kept**, not discarded as `no-solution`. Because every stage only ever adds a constraint the previous incumbent satisfies, the incumbent of the last stage that produced one is feasible for the original constraints, and that is what is published. A partially staged result **is** cacheable: it is exactly the promise the cache makes, and `objectiveValues` records per term how far the run got instead of implying proof it does not have.

- **What Optimized guarantees:** two independent, multi-worker, time-limited best-found runs cannot guarantee that PRI's priority value beats Time's and Time's makespan beats PRI's — either run may simply find a better incumbent for the other's primary term — so that cross-objective claim is struck everywhere. What is guaranteed instead is checkable and is what the product needs: **each stored variant's own primary term, measured on the materialised schedule in the real domain, is no worse than real Fast's value for that term.** Three mechanisms make that true rather than hoped for: the quantised baseline is supplied as a solution hint and as stage 1's upper bound so the search starts feasible and can only improve inside the quantised model; Lemma A makes the materialised result real-feasible; and the real-domain publication guard falls back to Fast's own schedule when quantisation loses more than the search won. A run that cannot beat Fast publishes Fast's value, which is a valid result rather than a failure.

- **Time quantisation and the quantised baseline (Sol r6 Critical 2):** the previous “integer whole workdays computed by the caller” rule was false and the fixed-point replacement was still unsatisfiable. `durationOf` returns `ASSUMED_SLICE_WORKDAYS` for `days === null` **without** dividing by `width`, and `days / width` otherwise **without** calling `snapWorkdays`; `snapWorkdays` only removes floating drift near an integer and deliberately preserves genuine fractions. Widths outside the divisors of 48 are legal — the API accepts every safe integer width 1–1000 and estimates are arbitrary finite non-negative numbers — so no fixed denominator makes every duration exact. Three serial slices with `days=1, width=5` are 0.2 workdays each and Fast finishes at 0.6 workdays = 28.8 units at `SOLVER_QUANTUM = 48`; rounding each duration up to 10 units needs 30. **Real Fast's value is therefore not a satisfiable upper bound for the quantised model, and the earlier plan's hint and stage-1 bound were infeasible on legal data.** The satisfiable policy has three parts, and each is a lemma with a test:
  1. **Round durations up, never down.** `durationUnits(s) = ceil(duration(s) × SOLVER_QUANTUM)`, with `duration(s)` computed by Fast's exact rule. The rounding per slice is recorded in the request. **Lemma A (real-feasibility):** because every quantised duration is ≥ its real duration and every start is an exact unit multiple, any solution feasible in the quantised model is feasible in the real domain — no predecessor, floor, assignee or pool constraint can be violated by materialising it. So quantisation costs optimality, never validity.
  2. **The bound and the hint come from the quantised baseline, not from real Fast.** `fastHint` and `baselineOffsets` are the **quantised Fast baseline**: Fast's own placement re-run through the same `schedule()` code path over the rounded durations, expressed in units. It is a feasible solution of exactly the model the solver receives, by construction, so the stage-1 upper bound `term ≤ baselineTerm` and the solution hint can never make a Fast-schedulable plan INFEASIBLE. `MOVEMENT` is measured against those integer baseline offsets, so it always has an integer representation.
  3. **A real-domain publication guard replaces the false guarantee.** Before storage the materialised optimized schedule is scored **in the real domain** against **real Fast's** value for that variant's own primary term (`PRIORITY` for PRI, `MAKESPAN` for Time). If the optimized value is worse — which quantisation alone can cause, as the width-5 case shows — the stored variant is **Fast's own materialised schedule** with `objectiveValues[primary].status = 'quantisation-floor'`. That is a valid publishable result the design already permits (“a run that cannot beat Fast returns Fast's own value”), so the product guarantee below stays literally true and no valid plan is ever mislabelled `invalid-output` or `no-solution`.
  `notBeforeUnits`, `horizonUnits` and every returned offset are in the same units; Bun divides by `SOLVER_QUANTUM` before materialising, so what is stored is in the fractional workday unit Fast already uses. **The horizon is a real serial bound rather than the integer ceiling:** `horizonUnits = max(notBeforeUnits) + Σ durationUnits`, which every feasible schedule fits inside because serialising every slice after the last floor is itself feasible. It is checked against `2^31 − 1` before spawn and fails with `horizon-overflow` rather than being sent. `SOLVER_QUANTUM` is covered by `SCHEDULER_CONTRACT_VERSION`. The gate carries a width-5 three-slice serial fixture proving the hint is feasible, `MOVEMENT` is defined, and the stored variant's primary term is no worse than real Fast's.

- **Canonical input:** the exact argument tuple of `schedule(rows, edges, slices, notBefore, poolSizes, reach)`. Hashed: every `PlannedRow`'s `id`, `parentId`, `position`, `frozenNumber` and as-written `priority`, sorted by id; authored `{ predecessorId, successorId }` edges, sorted; the `slices` array **grouped by work item, groups ordered by work-item id, and each group's own order preserved as given** — the intra-item order is step precedence and carries meaning, the order *between* groups does not and must not be hashed, because production `WorkItemRepo.listByProject` selects work items with no `ORDER BY` and `slicesOf` emits each group in that row order, so SQL is free to hand blue and green different global arrays for one unchanged project. Each slice carries `workItemId`, `stepId`, `days` (null distinct from 0), `personId`, `width` and the sorted set `poolIds: readonly string[]`. Then `notBefore` entries as whole days from day zero (so `project.startDate` is normalised away rather than hashed); `poolSizes` entries; and `reach` from `project.dep_reach`. Excluded: Engine, Objective, the toggle, the display variant, clock, acting user, and request sequence — nothing in `schedule()` reads them. Objective, `contractVersion` and `budgetMs` are separate key columns, not hash inputs. Independently of the hash, `listByProject` acquires `ORDER BY work_item.id`: an argument tuple that varies between reads of an unchanged project is a Fast defect as much as a cache one, and the unchanged-hash proof is built through the real adapter rather than by reordering `rows` in a fixture.
- **Cache identity:** one SQLite table `optimized_schedule_cache` in the existing application database, declared in `apps/be-01/src/repository/schema.ts` with a forward migration under `apps/be-01/drizzle/`. Three companion tables ship in the same slice and carry `contractVersion` as a key column so co-existing releases never fence each other: `optimization_generation` keyed `(projectId, contractVersion)`, `solver_slot` keyed `(projectId, contractVersion, generation, objective)`, and `solver_queue` keyed `(projectId, contractVersion, objective)`. The cache's composite primary key is `(projectId, inputHash, objective, contractVersion, budgetMs)` → `generation`, `status` (`'ok' | 'failed'`), `scheduleJson` (NULL iff failed), `failureReason` (NULL iff ok), `createdAt`. A row satisfies a read iff `status='ok'` and every key column plus `generation` matches the project's current state. Integrity is declared in the schema, not assumed: `projectId` FK `ON DELETE CASCADE`, `CHECK (status IN ('ok','failed'))`, a CHECK tying `ok` to non-NULL `scheduleJson` + NULL `failureReason` and the inverse for `failed`, `CHECK (objective IN ('pri','time'))`, `CHECK (failure_reason IS NULL OR failure_reason IN ('timeout','invalid-output','no-solution','internal-error','oom','horizon-overflow','objective-overflow'))`, and read-time JSON validation that deletes an unparseable row and treats it as a miss. **Retention is two rules, because one was false (Sol r6 Minor 15).** Generation changes only when `inputHash` changes, so raising `budgetMs` or deploying a new `contractVersion` reuses the generation and inserts a *different* composite-key row — every superseded budget and version pair stayed part of the current generation and “only the latest pair is retained” was untrue. So: (1) allocating a new generation deletes every row of that project for that contract version in the same transaction, which is what makes an undo back to a previous hash a miss that re-solves with Fast visible throughout; and (2) when a new outcome commits, the same transaction deletes every other row for `(projectId, objective, contractVersion)` whose `(inputHash, budgetMs)` differs. Reads are keyed by the current budget, so nothing readable is lost. The resulting ceiling is exact and is the one the Risks section may claim: **at most 2 rows per project per live contract version**, with live contract versions bounded by the 30-day retirement rule above. **`apps/be-01/drizzle/**` is a prod-mode path, so every slice that lands a migration ships as a reviewed PR and is not self-merged.**
- **Contract version:** `contractVersion = "<SCHEDULER_CONTRACT_VERSION>+<solverVersion>"`. `solverVersion` alone was unsound, because durations, the leaf expansion and `baselineOffsets` are produced by Bun/domain code that the Python package version does not describe. `SCHEDULER_CONTRACT_VERSION` is an exported constant in `libs/domain`, bumped by any change to Fast semantics, `ASSUMED_SLICE_WORKDAYS`, `snapWorkdays`, reach or numbering semantics, resource tie-breaks, the canonicalizer, or the duration rule — and guarded by keying the Fast golden corpus on it, so an unbumped Fast change fails the corpus rather than silently serving stale rows.
- **Generations are per contract version, and cancellation is its own epoch (Sol r6 Criticals 3–4, Important 10):** the single pair of project columns could not survive the deployment topology this design says it supports. `SCHEDULER_CONTRACT_VERSION` is bumped for a canonicalizer change and blue and green run against one database, so an outgoing release computing H1 and an incoming one computing H2 for the same stored plan would alternately increment the one generation and delete each other's rows for ever — solver thrash in exactly the window the cache version exists to protect. The durable current identity therefore moves to its own table, `optimization_generation`, keyed **`(projectId, contractVersion)`** → `generation`, `inputHash`, `cancelEpoch`, `updatedAt`. Each release owns its own row and neither can supersede the other; the cache is already keyed by `contractVersion`, and `solver_slot` and `solver_queue` gain the same column so a stale release cannot dequeue or fence the other's work. The ceilings stay **global across both** — they count processes, not contracts. Retirement is explicit: a `(projectId, contractVersion)` row untouched for `GENERATION_RETENTION_DAYS = 30`, or whose contract version is marked retired at deploy, is deleted with its cache, slot and queue rows by the same maintenance path.
  Allocation within one release's row is one compare-and-swap transaction: read `(generation, inputHash)`; if the stored hash equals H, reuse the generation unchanged, so a backend restart on an unchanged plan allocates nothing; otherwise `UPDATE … SET input_hash = :H, generation = :seen + 1 WHERE project_id = :p AND contract_version = :c AND generation = :seen`, and in the same transaction delete the older generation's **cache and queue** rows. A losing writer retries and observes the winner's H rather than allocating a second generation for one input. This is what makes cold-read coalescing and “exactly one child per objective” implementable across processes, and it fences the H1→H2→undo-to-H1 ABA sequence, a cancelled child stamping `failed` over a live `ok`, and two writers of one key.
  **Slot rows are deliberately not deleted by allocation.** Deleting them freed the count before the corresponding processes were proved dead, so the next generation saw free rows while the old pair was still terminating and repeated edits could leave six or more real children running while SQLite counted two — falsifying the settled 4/16 ceilings outright. Allocation instead sets `cancel_requested_at` on the previous generation's slot rows and **leaves them counted until their owner releases them or heartbeat expiry reclaims them**, so the row count is an upper bound on live children at every instant.
  **Turning the toggle OFF advances a cancellation epoch, not the generation.** The toggle is excluded from `inputHash` by design, so an OFF transition cannot advance a generation that allocation is required to reuse for an unchanged hash — those two rules could not both be implemented, and the earlier tasks asked for both. OFF is one transaction that sets `optimization_enabled = 0`, increments `cancelEpoch` **for every contract version of that project**, sets `cancel_requested_at` on all of that project's slot rows and deletes its queue rows. Every spawn carries `(generation, cancelEpoch, attemptToken)`, and **every result, failure and eviction write is conditional on the generation still being current, the cancel epoch being unchanged, and `optimization_enabled` still being 1**, in the same transaction as its event — so a child that outlives a local cancellation, or belongs to the other backend entirely, can neither store nor broadcast. A local process handle cancels only local children and `PR_SET_PDEATHSIG` is irrelevant when the other coordinator is still alive, so the durable channel is the slot row: an owner's heartbeat reads `cancel_requested_at` and the project's epoch on the same round trip and kills its child when either moved, bounding real termination by one heartbeat interval. The gate carries the two-coordinator test: blue owns both children, green PATCHes the toggle OFF, both real children exit, and neither can store or emit an outcome.

- **Solver wire contract — one versioned schema, four consumers (Sol r6 Critical 1):** the residue of this finding was that three artifacts each described the request in their own words, so an implementer following the ordered tasks could build a different constraint graph from one following the later requirement. The prose is no longer normative. **`libs/contracts/solver/solver-wire.v1.json` is a checked-in JSON Schema and is the single definition of the request and the response**, carrying `wireVersion` as a required literal, the unit of every numeric field, and every field staged solving needs. Exactly four consumers read that one file: the Bun request builder and `parseSolverResponse` in `libs/contracts/solver/src/`, the `wbs-solver` Python entrypoint (which validates each request against the copy installed beside it with the pinned `jsonschema` dependency), and a shared golden-fixture corpus under `libs/contracts/solver/fixtures/` that both suites run. A contract test asserts the TypeScript types and the schema agree and that both suites accept every golden fixture and reject every negative one, so divergence is a red test rather than a runtime surprise. Request fields: `{ wireVersion, contractVersion, solverVersion, objective, budgetMs, stageBudgetSplit, quantum, horizonUnits, slices, edges, pools, baselineOffsets, fastHint }`; each slice carries `key` (`sliceKey`), `durationUnits` (integer units, Fast's exact rule rounded up, with the rounding recorded), `width`, `personId`, `poolIds`, `priorityWeight` (the dense rank) and `notBeforeUnits`. `edges` are already leaf-expanded with `reach` applied and already carry intra-item step-order edges, so Python never sees the tree or `reach`. Bun owns duration and graph derivation; Python owns placement only. The response is `{ wireVersion, status, offsets, objectiveValues }` with `offsets` in the same units; parsing is the named seam `parseSolverResponse(raw)` so framing failures are testable without a process. Bun independently re-validates every offset — including that each is a non-negative integer multiple of one unit within `horizonUnits` — plus every edge, floor, pool capacity, assignee non-overlap and the recomputed objective values before storing. The solver reads no clock, database, or other schedule.

- **Optimized-result materialiser — the pinned placement algorithm (Sol r6 Critical 6):** the response's `offsets` are an intermediate and are **never persisted alone**, because every bar and row consumes a whole `ScheduledSlice`. “Run Fast's annotation pass with the starts pinned” was not executable: Fast has no annotation-only pass. `placeSlices` chooses a slice, computes person and capacity availability, chooses its start, records capacity blockers, adds resource-successor edges and establishes the order `lateTimes` later consumes, all in one pass. The plan therefore **splits it**: `placeSlices` becomes `chooseStarts(canonicalInput)` followed by `annotate(canonicalInput, starts)`, with Fast's existing golden corpus proving the split is behaviour-preserving before anything optimized is built on it. `materialiseOptimized(canonicalInput, offsets)` is `annotate(canonicalInput, offsets / SOLVER_QUANTUM)`.
  `annotate` is fully determined by its inputs, with no clock and no map-iteration dependence:
  1. **Processing order** is ascending `start`, ties broken by the canonical slice order (work-item id, then intra-item index) — a total order derived from the hashed input.
  2. **Reservation reconstruction** replays the same person and pool ledgers `placeSlices` builds, but consuming the pinned start instead of choosing one. For a multi-pool slice the pool is chosen by Fast's own rule applied at the pinned instant: the first pool in the sorted `poolIds` with free capacity there.
  3. **`resourcePredecessorId`** is the last slice releasing the same person at or before this start; **`capacityPredecessorIds`** and **`capacityTeamId`** are the slices whose release at exactly this start freed the chosen pool, and that pool's team.
  4. **Resource-successor edges** are added from the reconstructed ledgers, so `lateTimes` receives the same DAG shape it receives under Fast, and float, criticality, earliest and latest are recomputed over the optimized placement.
  5. **`boundBy` precedence is the complete ordered list** `projectStart | notBefore | predecessor | stepOrder | person | capacity | optimizer`. The earlier invariant listed only the first four, which was a concrete bug: an optimized slice that starts later because its assignee or team is occupied is strictly later than every *listed* floor and would have been labelled `optimizer`, erasing its resource predecessor, its team and both wait counts. **`optimizer` applies only when the start is strictly later than every floor including `person` and `capacity`** — the deliberate-idle case, which has no value in today's union, so the union is extended rather than a floor misreported. Under `optimizer`, `resourcePredecessorId` is null, `capacityPredecessorIds` is empty and `capacityTeamId` is null, preserving the render invariant that those three are set exactly when `boundBy === 'capacity'`.
  6. `duration`, `estimated`, `width` and `effort` are input-derived and identical to Fast's for the same canonical input; both wait counters are recounted from the materialised slices.
  The FE mirror is scheduled rather than assumed: `apps/fe-01/src/lib/wbs-api.ts`'s union and the exhaustive `floorWordsOf` switch in `apps/fe-01/src/components/wbs/gantt-geometry.ts` both gain `'optimizer'` in the same slice. Fixtures cover an optimized start **equal to a person floor**, one **equal to a capacity floor**, and one **strictly later than both**, asserting predecessor edges, late times, both wait counts, the API union and the hover words — the previous watched reds only proved a false `projectStart` and a stray capacity field on an `optimizer` slice, and nothing required a genuinely person-bound or capacity-bound optimized slice to keep its explanation. The whole materialiser is proved through the real plan-read payload rather than against the domain type alone.
- **Cache DTO and codec (Sol r6 Important 8):** `scheduleJson` was called “the serialised full `Schedule`” with no shape and no codec, and `Schedule` carries `Map<string, ScheduledSlice>` and `Map<string, Scheduled>`, which `JSON.stringify` renders as `{}` — an implementation could pass every type-level materialiser test and store a row that reloads as an empty plan. The stored value is therefore a versioned DTO with explicit functions: `CACHE_DTO_VERSION`, `encodeSchedule(schedule)` and `decodeSchedule(json)` in `libs/domain`. Both maps become **arrays of entries sorted by key** (`slices: [{ key, …ScheduledSlice }]`, `workItems: [{ id, …Scheduled }]`); `waitingForPerson`, `waitingForCapacity` and `eventsVisited` are stored so the round trip is total and the read path invents nothing. `decodeSchedule` enforces the invariants and throws naming the defect: `dtoVersion` known, no duplicate key, every `slices` key equal to its entry's own `sliceKey`, and `workItems` covering exactly the projected ids. The gate proves a **non-empty** round trip through SQLite and through the real plan read, plus malformed-key, duplicate-key and missing-projection negatives.

- **Plan-read DTO and the Retry endpoint (Sol r6 Critical 5):** the plan added settings columns and cached rows but never said how `WorkItemService.tree` selects a variant into its existing fields, and no read could tell a freshly loaded client “pending” from “failed” — a failure event can move a client already connected, but it cannot reconstruct an initial page load. `tree()` therefore returns one additional `optimization` block beside the existing `workItems`, `slices` and the two wait counts: `{ enabled, engine, objective, inputHash, generation, contractVersion, budgetMs, displayed, variants: { pri, time }, comparison }`. `displayed` is `'fast' | 'pri' | 'time'` and names which schedule the existing arrays hold; `comparison` is `{ deltaDays, sameOrder }` and is present exactly when `displayed !== 'fast'`. Each `VariantState` is a tagged union: `ready` (an `ok` row for the current key), `pending` (no row and a live slot or queue entry), `retrying` (a `failed` row **and** a live slot or queue entry), `failed` (a `failed` row and no live entry, carrying `reason`), or `idle` (no row and no live entry, which is what the toggle being OFF looks like). **Selection rule:** the arrays hold Fast when the toggle is OFF, when `engine === 'fast'`, or when the selected variant is not `ready`; otherwise they hold the materialised selected variant. That makes a cold reload renderable in every state without a second request.
  The `retrying` state is also what resolves the failed-row dilemma: the marker is **never deleted before its replacement commits**, so every read during a retry would otherwise still render “unavailable”, while deleting it would make the next read auto-spawn — the timer retry Dany rejected. The distinct in-flight state is the live slot or queue row, not the absence of the marker. **Retry is a real route:** `POST /api/projects/:projectId/optimization/retry` with body `{ objective, inputHash }`, under the same project-write authorization as the settings PATCH. It runs the ordinary admission transaction, so two concurrent Retries produce one child. `202 { state: 'retrying', generation, inputHash }` on admission or enqueue; `409 { code: 'stale-input-hash', currentInputHash }` when the body's hash is not current; `409 { code: 'already-running' }` when a live entry exists for that key; `409 { code: 'not-failed' }` when there is no failure marker to retry. The gate proves a reload through the **real controller payload** in the cold, queued, retrying, failed, partial-success and full-hit states.
- **Failure:** fail-closed and governed by one state machine. A failure writes exactly one `status='failed'` marker row with a `failureReason` (`timeout | invalid-output | no-solution | internal-error | oom | horizon-overflow | objective-overflow`); Fast stays visible; failure is variant-specific. That row never satisfies a read, and it **does** suppress an automatic re-spawn for its exact key — a later read and a same-hash edit both launch nothing, because a read is a timer retry in disguise — while never blocking an explicit Retry (which overwrites it) or the fresh generation a new hash starts. A cancelled run writes no row at all.
- **Events:** a newly stored `ok` row and its durable `event_log` record are written in **one SQLite transaction**, and the broadcaster pushes from the committed record. A newly written `failed` marker row does the same through a second, non-result event **`schedule_optimization_failed`** — without it the read returns Fast while children run, success later emits `schedule_optimized`, and a failure emits nothing, so a client already on screen would sit at `Optimizing…` for ever and the manual Retry control would never appear; when both variants fail no connected client would have any reason to read the marker at all, and when one succeeds its unrelated success event would reveal the other failure by race. This does not disturb the settled rule that a cache **hit** broadcasts nothing: a hit is not a new outcome, and a newly written `failed` row is. The failure event carries no schedule and triggers no variant refetch — it flips that variant to `Optimization unavailable · Retry`. Both event payloads are `(projectId, generation, inputHash, objective, contractVersion, budgetMs)`, the failure one adding `failureReason`; **`budgetMs` is in the identity because it is a cache-key column** — raising the budget changes neither the hash nor the generation, so without it a larger-budget result would announce itself under the smaller-budget result's identity and a client holding that identity would ignore the only notice that should move it. **The delivery guarantee is narrowed to what the stack can keep:** one durable replay record per new outcome, plus one best-effort post-commit push. `event_log` is a replay buffer consulted on resume, not a dispatched-and-acknowledged outbox, and the process can die after commit and before the push, so “delivered at least once” over a live socket was false. The no-outbox constraint stands. The seam is named rather than assumed, because today `EventLogRepo.recordEvent` opens its own transaction and `GatewayBroadcaster.publish` both records and pushes: `recordEventIn(tx, subscription, message, createdAt)` writes inside the caller's transaction, and `pushRecorded(subscription, recorded, event)` buffers and pushes an already-recorded sequence without recording it twice; `publish` becomes those two calls and keeps its behaviour.
- **Resource ceilings and slot fencing (Sol r6 Critical 4):** 4 solver processes per project, 16 global (Dany 2026-09-02), enforced in SQLite rather than coordinator memory — blue and green coexist against one database file and two in-memory coordinators would each admit their own sixteen. `solver_slot` is keyed `(projectId, contractVersion, generation, objective)` and holds `ownerId`, `attemptToken`, `pid`, `startedAt`, `heartbeatAt`, `cancelRequestedAt`. Admission is one transaction that reclaims heartbeat-expired slots, refuses at 4 per project and 16 global counting **every** unreleased row including those already asked to cancel, then inserts with a freshly minted 128-bit `attemptToken`.
  **The token is the fence, and it is checked on every subsequent write.** Heartbeat, release, the cache/failure write and the event write all carry `WHERE attempt_token = :token`; a superseded owner's statement matches zero rows and it aborts rather than refreshing or deleting a replacement slot, and the cache write is a conditional insert asserting its own live slot row rather than a blind upsert — so two nondeterministic results can no longer overwrite each other or emit two outcome records for one key. Reclamation mints a **new** token for the replacement, which is what makes the old owner's late heartbeat, release and write all fail.
  **Reclamation never authorises a replacement while the old child may still be running.** The child carries an independent hard self-deadline — `wbs-solver` arms its own alarm at `budgetMs + 5000` and exits — and slot expiry is defined in terms of it: `SLOT_HEARTBEAT_TTL_MS = solverBudgetMs + 5000 + SLOT_RECLAIM_MARGIN_MS` with a 15 s margin, so an expired row implies the child is past its own deadline rather than merely quiet. `PR_SET_PDEATHSIG` also gets the standard parent-death race check: the entrypoint installs the signal and then re-reads `os.getppid()`, exiting immediately if the parent already died. `solver_queue` is the FIFO, keyed `(projectId, contractVersion, objective)` so a project holds at most one queued entry per objective and a new generation replaces rather than accumulates, ordered by `enqueuedAt`, then `projectId`, then `objective` — the third term is what makes the order **total**, because a project's PRI and Time entries can share a timestamp, and it is the order used in every normative section rather than in some of them. At dequeue an entry is discarded without launching if its generation is no longer current, its cancel epoch moved, **or** the project's toggle is no longer ON. The gate proves rapid generations and expiry under two coordinators, an old owner's late heartbeat, release and write all rejected, that the observed OS process count never exceeds either ceiling, and that only the current token can store.

- **Budget:** one config value `solverBudgetMs`, default 60000 (Dany's >=60s floor), child killed at `solverBudgetMs + 5000`. It **is** a cache-key column, because a larger budget can find a better feasible result and an operator who raises it must not keep being served the smaller-budget answer. The cached promise is exactly "the best result found for this input, this contract, this objective, at this budget".
- **Restart and orphans:** nothing is resumed on startup and no queue is rebuilt. A reparented child cannot be identified by a recycled PID, so cleanup does not depend on finding it: `wbs-solver`'s entrypoint calls `prctl(PR_SET_PDEATHSIG, SIGKILL)` before reading stdin, so it dies when its parent does; slots are reclaimed by heartbeat expiry rather than process probing; and each backend release runs in its own container/cgroup, which is a recorded deployment obligation the ceiling arithmetic depends on.
- **Stored-enum boundary:** every new stored text enum gets both a database `CHECK` and an explicit read-time validator, mirroring `toProject`, which today validates `estimateMethod`, `depReach` and `estimateRounding` rather than casting or defaulting them. That means `isOptimizedStatus`, `isObjective` and `isFailureReason` on the cache read path, `isScheduleEngine` and `isScheduleObjective` on the project read path, `CHECK (optimization_enabled IN (0,1))` on the boolean, and a thrown error naming the column and the stored value on any miss — a malformed trusted row must not cross into a precise internal type and produce an impossible selector branch or a silent default. `failureReason` in particular was previously accepting any non-null text. Negative tests inject an unknown value for each of the five enums and the boolean on the production read path.
- **Project settings:** the toggle, Engine and Objective are project-scoped persisted columns, not view state. An additive migration adds `optimization_enabled` (default false, which is what makes OFF-by-default true for existing rows), `schedule_engine` (default `'fast'`) and `schedule_objective` (default `'pri'`), with repository mapping, a PATCH contract under the existing project-write authorization, the three settings in the read payload, and a new `project_settings_changed` variant on `ProjectEvent` emitted by `ProjectService.update`. The generation counter, the input hash and the cancel epoch deliberately do **not** live here: they are per contract version (see Generations), so they live in the `optimization_generation` table that slice 3 creates rather than on the project row. This is a **second prod-mode path**.
- **“Same order” — the exact comparison relation:** the indicator's four sentences (“Same deadline + same order”, “Same deadline + reordered”, and their earlier/later pairs) require a defined order, and map or array iteration order is not one. `sameOrder(a, b)` holds iff for **every** pair of slices `(s, t)` present in both, `sign(startA(s) − startA(t)) === sign(startB(s) − startB(t))`, compared **in the real fractional-workday domain on the two materialised schedules**, not in quantised units — real Fast's starts need not lie on the unit grid, so quantised comparison could label a pair reordered purely by rounding. That is a strict weak ordering by start: it is blind to a uniform shift of the whole plan, blind to iteration order, and it treats ties as first-class — a tie broken and a tie created are both “reordered”, which is the honest answer, since two slices that used to start together and now do not have visibly changed the plan. Zero-duration slices participate by start like any other. The relation is computed **server-side on the materialised schedules** and shipped as one boolean beside the day-count delta, so client and server cannot label the same pair differently.
- **Determinism:** production runs multi-worker under a wall-clock budget and is explicitly not required to be reproducible; one result is stored and every collaborator refetches that row, so all clients converge. Reproducibility is asserted only under a pinned test configuration (`num_search_workers=1`, fixed `random_seed`, deterministic time limit).

- **Migrations ship with their rollback:** AGENTS.md mandates a `down.sql` beside every `migration.sql`, and both prod-mode slices previously asked only for a “forward migration”. Each of slices 3 and 3b explicitly creates its own `down.sql` and proves rollback-then-re-apply against the applied set; without it migration lint and `readMigrationFolders` refuse at the gate and an aborted blue/green deploy cannot return.
- **Packaging is part of the change, not a consequence of it:** creating the `wbs-solver` package and running its suite standalone can be green while every deployed solve fails on an absent executable. The Dagger/image path installs the pinned Python runtime and the locked OR-Tools environment, copies the package and entrypoint into the be-01 runtime, exposes the installed version to the coordinator as the `solverVersion` half of `contractVersion`, and an ordered slice proves a spawn **from the built image** plus the negative case where the package is absent. The Python suite gets its own Nx target wired into the gate.

## Risks / Trade-offs

- **New language in the stack (Python):** the deploy image must carry a pinned Python runtime plus OR-Tools. Mitigated by isolating the solver behind a one-line stdin/stdout contract and versioning the package into the cache key.
- **Two concurrent solves per edit:** CPU cost. Mitigated by the OFF-by-default toggle, debounce, cancellation, and the 4/16 ceilings.
- **SQLite growth:** the retention rules above bound this exactly at 2 rows per project per live contract version — one per objective — with superseded budget and contract rows deleted when their replacement commits and retired contract versions pruned after 30 days. The earlier “only the latest pair” claim ignored budget and contract changes, which reuse the generation.
- **Best-found semantics:** a host-dependent solve could surface differing "optimal" dates; the exact input hash plus the reported day-count comparison forces like-for-like reads, and storing exactly one result per key means collaborators never disagree even though a re-solve might have found other offsets.
- **Two prod-mode migrations inside a dev-mode item:** the cache/slot/queue tables and the four project-settings columns are the prod-mode paths here. Each is isolated into its own slice (tasks.md slices 3 and 3b) so the rest of the change stays dev-mode and only those slices carry the reviewed-PR obligation.
- **Cross-process coordination in SQLite:** admission and generation allocation become contended write transactions on the same database as the application. Mitigated by keeping each transaction to a few indexed row reads and one insert, and by the 5-second slot heartbeat being an `UPDATE` on a primary-key hit.
