## Context

The scheduler (`libs/domain/src/schedule.ts` — it moved out of be-01 on 2026-09-02) is a deterministic millisecond pass (Fast). It is immediately visible, the sole fallback, and never labelled optimal. WBS has no optimization today. Dany approved adding an optional dual-objective mode using official OR-Tools CP-SAT. Architecture section 1 (toggle, PRI+Time concurrency, exact-hash SQLite cache, one generation per project) and sections 2-4 (behaviour, failure, test design) are all approved; this design records the settled technical shape.

## Goals / Non-Goals

**Goals:**

- Compute Priority-first (PRI) and Finish-first (Time) schedules with a real constraint solver, concurrent, behind a project-wide OFF-by-default toggle.
- Keep Fast unchanged as the preview and fallback.
- Cache validated results in durable SQLite; broadcast newly stored results so collaborators converge.
- Surface a compact comparison indicator without a toast or modal.

**Non-Goals:**

- No proven optimality (best-found only).
- No daemon, port, sidecar, or outbox.
- No fix to the known capacity/floor hand-off audit finding.
- No timer retry; no per-user objective.

## Decisions

- **Runner:** official OR-Tools CP-SAT in its own versioned Python package `wbs-solver`, invoked by Bun as a short-lived stdin/stdout CLI. No import, no daemon, no HTTP port.
- **Concurrency:** optimization ON computes PRI and Time concurrently for one canonical input. Engine Fast/Optimized and Objective Priority-first/Finish-first only select which cached output is displayed.
- **Objective mathematics:** `MAKESPAN = max finish`; `PRIORITY = Σ w(s)·finish(s)` where `w(s) = (P_max + 1) − p(s)` over the leaf priority resolved by `priorityByLeaf`'s nearest-ancestor floor rule, and `w(s) = 0` for a leaf with no priority above it; `MOVEMENT = Σ |start(s) − baselineStart(s)|`. PRI minimizes `(PRIORITY, MAKESPAN, MOVEMENT)` lexicographically, Time minimizes `(MAKESPAN, PRIORITY, MOVEMENT)`. Lexicographic order is implemented as staged optimization — optimize a term, fix it as an equality, optimize the next within the remaining budget — never as a weighted sum. These are **not** total orders: ties exist and production is not required to break them reproducibly.
- **Canonical input:** the exact argument tuple of `schedule(rows, edges, slices, notBefore, poolSizes, reach)`. Hashed: every `PlannedRow`'s `id`, `parentId`, `position`, `frozenNumber` and as-written `priority`, sorted by id; authored `{ predecessorId, successorId }` edges, sorted; the `slices` array **in its given order**, because that order is intra-work-item step precedence, each carrying `workItemId`, `stepId`, `days` (null distinct from 0), `personId`, `width` and the sorted set `poolIds: readonly string[]`; `notBefore` entries as whole days from day zero (so `project.startDate` is normalized away rather than hashed); `poolSizes` entries; and `reach` from `project.dep_reach`. Excluded: Engine, Objective, the toggle, the display variant, clock, acting user, and request sequence — nothing in `schedule()` reads them. Objective, `contractVersion` and `budgetMs` are separate key columns, not hash inputs.
- **Cache identity:** one SQLite table `optimized_schedule_cache` in the existing application database, declared in `apps/be-01/src/repository/schema.ts` with a forward migration under `apps/be-01/drizzle/`. Composite primary key `(projectId, inputHash, objective, contractVersion, budgetMs)` → `generation`, `status` (`'ok' | 'failed'`), `scheduleJson` (NULL iff failed), `failureReason` (NULL iff ok), `createdAt`. A row satisfies a read iff `status='ok'` and every key column plus `generation` matches the project's current state. Integrity is declared in the schema, not assumed: `projectId` FK `ON DELETE CASCADE`, `CHECK (status IN ('ok','failed'))`, a CHECK tying `ok` to non-NULL `scheduleJson` + NULL `failureReason` and the inverse for `failed`, `CHECK (objective IN ('pri','time'))`, and read-time JSON validation that deletes an unparseable row and treats it as a miss. Retention is one rule: a project keeps only its current generation's rows, and allocating a new generation deletes every older row for that project in the same transaction — so an undo back to a previous hash is a miss that re-solves, with Fast visible throughout. **`apps/be-01/drizzle/**` is a prod-mode path, so every slice that lands a migration ships as a reviewed PR and is not self-merged.**
- **Contract version:** `contractVersion = "<SCHEDULER_CONTRACT_VERSION>+<solverVersion>"`. `solverVersion` alone was unsound, because durations, the leaf expansion and `baselineOffsets` are produced by Bun/domain code that the Python package version does not describe. `SCHEDULER_CONTRACT_VERSION` is an exported constant in `libs/domain`, bumped by any change to Fast semantics, `ASSUMED_SLICE_WORKDAYS`, `snapWorkdays`, reach or numbering semantics, resource tie-breaks, the canonicalizer, or the duration rule — and guarded by keying the Fast golden corpus on it, so an unbumped Fast change fails the corpus rather than silently serving stale rows.
- **Generations:** each project carries a monotonic `optimizationGeneration`. Every hash change allocates the next one in the same transaction that deletes the previous generation's rows, every spawn carries it, and every write is conditional on it still being current. This fences the H1→H2→undo-to-H1 ABA sequence, a cancelled child stamping `failed` over a live `ok`, and two writers of the same key. Concurrent cold reads coalesce on an `INSERT … ON CONFLICT DO NOTHING` slot, so one project never starts two solvers for one objective.
- **Solver contract:** request is one JSON line `{ contractVersion, solverVersion, objective, budgetMs, horizonDays, slices, edges, pools, baselineOffsets }`. Bun owns duration and graph derivation; Python owns placement only. Each slice carries `key` (`sliceKey`), integer `durationDays` already computed exactly as Fast computes it (`ASSUMED_SLICE_WORKDAYS` for null `days`, divided by `width`, then `snapWorkdays` — no fraction crosses the boundary), `width`, `personId`, `poolIds`, resolved `priorityWeight`, and resolved `notBeforeDays`. `edges` are already leaf-expanded with `reach` applied and already carry intra-item step-order edges, so Python never sees the tree or `reach`. Response is one JSON line `{ status, offsets, objectiveValues }`; parsing is the named seam `parseSolverResponse(raw)` so framing failures are testable without a process. Bun independently re-validates every offset, edge, floor, pool capacity, assignee non-overlap and the recomputed objective values before storing. The solver reads no clock, database, or other schedule.
- **Failure:** fail-closed and governed by one state machine. A failure writes exactly one `status='failed'` marker row with a `failureReason` (`timeout | invalid-output | no-solution | internal-error | oom`); Fast stays visible; failure is variant-specific. That row never satisfies a read, and it **does** suppress an automatic re-spawn for its exact key — a later read and a same-hash edit both launch nothing, because a read is a timer retry in disguise — while never blocking an explicit Retry (which overwrites it) or the fresh generation a new hash starts. A cancelled run writes no row at all.
- **Events:** the cache row and a durable `event_log` record are written in **one SQLite transaction**, and the broadcaster pushes from the committed record. The guarantee is exactly one durable event record per newly stored result, delivered at least once; the payload `(projectId, generation, inputHash, objective, contractVersion)` makes duplicate delivery idempotent. A cache hit emits nothing.
- **Resource ceilings:** 4 solver processes per project, 16 global (Dany 2026-09-02), enforced in SQLite rather than coordinator memory — blue and green backends coexist against one database file, and two in-memory coordinators would each admit their own sixteen. A `solver_slot` table keyed `(projectId, generation, objective)` holds `ownerId`, `pid`, `startedAt`, `heartbeatAt`; admission is one transaction that reclaims heartbeat-expired slots, refuses at 4 per project and 16 global, then inserts. `solver_queue` is the FIFO, ordered by `enqueuedAt` then `projectId` for a total order; at dequeue an entry is discarded without launching if its generation is no longer current **or** the project's toggle is no longer ON — the toggle is excluded from the hash, so the hash check alone would not catch an opt-out.
- **Budget:** one config value `solverBudgetMs`, default 60000 (Dany's >=60s floor), child killed at `solverBudgetMs + 5000`. It **is** a cache-key column, because a larger budget can find a better feasible result and an operator who raises it must not keep being served the smaller-budget answer. The cached promise is exactly "the best result found for this input, this contract, this objective, at this budget".
- **Restart and orphans:** nothing is resumed on startup and no queue is rebuilt. A reparented child cannot be identified by a recycled PID, so cleanup does not depend on finding it: `wbs-solver`'s entrypoint calls `prctl(PR_SET_PDEATHSIG, SIGKILL)` before reading stdin, so it dies when its parent does; slots are reclaimed by heartbeat expiry rather than process probing; and each backend release runs in its own container/cgroup, which is a recorded deployment obligation the ceiling arithmetic depends on.
- **Project settings:** the toggle, Engine and Objective are project-scoped persisted columns, not view state. An additive migration adds `optimization_enabled` (default false, which is what makes OFF-by-default true for existing rows), `schedule_engine` (default `'fast'`), `schedule_objective` (default `'pri'`) and `optimization_generation` (default 0), with repository mapping, a PATCH contract under the existing project-write authorization, the three settings in the read payload, and a new `project_settings_changed` variant on `ProjectEvent` emitted by `ProjectService.update`. This is a **second prod-mode path**.
- **Determinism:** production runs multi-worker under a wall-clock budget and is explicitly not required to be reproducible; one result is stored and every collaborator refetches that row, so all clients converge. Reproducibility is asserted only under a pinned test configuration (`num_search_workers=1`, fixed `random_seed`, deterministic time limit).

## Risks / Trade-offs

- **New language in the stack (Python):** the deploy image must carry a pinned Python runtime plus OR-Tools. Mitigated by isolating the solver behind a one-line stdin/stdout contract and versioning the package into the cache key.
- **Two concurrent solves per edit:** CPU cost. Mitigated by the OFF-by-default toggle, debounce, cancellation, and the 4/16 ceilings.
- **SQLite growth:** one row per objective per project per valid input, but only the latest pair is retained so the table stays bounded per project.
- **Best-found semantics:** a host-dependent solve could surface differing "optimal" dates; the exact input hash plus the reported day-count comparison forces like-for-like reads, and storing exactly one result per key means collaborators never disagree even though a re-solve might have found other offsets.
- **Two prod-mode migrations inside a dev-mode item:** the cache/slot/queue tables and the four project-settings columns are the prod-mode paths here. Each is isolated into its own slice (tasks.md slices 3 and 3b) so the rest of the change stays dev-mode and only those slices carry the reviewed-PR obligation.
- **Cross-process coordination in SQLite:** admission and generation allocation become contended write transactions on the same database as the application. Mitigated by keeping each transaction to a few indexed row reads and one insert, and by the 5-second slot heartbeat being an `UPDATE` on a primary-key hit.
