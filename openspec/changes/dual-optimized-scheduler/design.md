## Context

The scheduler (`libs/domain/src/schedule.ts` — it moved out of be-01 on 2026-09-02) is a deterministic millisecond pass (Fast). It is immediately visible, the sole fallback, and never labelled optimal. WBS has no optimization today. Dany approved adding an optional dual-objective mode using official OR-Tools CP-SAT. Architecture section 1 (toggle, PRI+Time concurrency, exact-hash SQLite cache, one generation per project) and sections 2-4 (behaviour, failure, test design) are all approved; this design records the settled technical shape.

## Goals / Non-Goals

**Goals:**

- Compute Priority-first (PRI) and Finish-first (Time) schedules with a real constraint solver, concurrent, behind a project-wide OFF-by-default toggle.
- Keep Fast unchanged as the preview and fallback.
- Cache validated results in durable SQLite; broadcast newly stored results so collaborators converge.
- Surface a compact comparison indicator without a toast or modal.

**Non-Goals:**

- No proven optimality (best-found only).
- No daemon, port, sidecar, or outbox.
- No fix to the known capacity/floor hand-off audit finding.
- No timer retry; no per-user objective.

## Decisions

- **Runner:** official OR-Tools CP-SAT in its own versioned Python package `wbs-solver`, invoked by Bun as a short-lived stdin/stdout CLI. No import, no daemon, no HTTP port.
- **Concurrency:** optimization ON computes PRI and Time concurrently for one canonical input. Engine Fast/Optimized and Objective Priority-first/Finish-first only select which cached output is displayed.
- **Objective mathematics:** `MAKESPAN = max finish`; `PRIORITY = Σ w(s)·finish(s)` where `w(s) = (P_max + 1) − p(s)` over the leaf priority resolved by `priorityByLeaf`'s nearest-ancestor floor rule, and `w(s) = 0` for a leaf with no priority above it; `MOVEMENT = Σ |start(s) − baselineStart(s)|`. PRI minimizes `(PRIORITY, MAKESPAN, MOVEMENT)` lexicographically, Time minimizes `(MAKESPAN, PRIORITY, MOVEMENT)`. These are **not** total orders: ties exist and production is not required to break them reproducibly.
- **Anytime staged lexicographic (the exact algorithm):** lexicographic order is implemented as staged optimization, never as a weighted sum, and the wall-clock budget is divided by stage — `STAGE_BUDGET_SPLIT = [0.60, 0.25, 0.15]` of `budgetMs`, an exported constant, with a stage that finishes early donating its remainder to the next. Each stage ends in one of four states and the rule is exact: **OPTIMAL** fixes the term at its proven value as an equality and continues; **FEASIBLE** with incumbent `v` adds the *inequality* `term ≤ v` and continues — not an equality, because fixing an unproven incumbent is not lexicographic minimisation over the feasible set, while `≤ v` excludes no solution at least as good; **UNKNOWN with an incumbent** is treated as FEASIBLE; **UNKNOWN with no incumbent** stops staging and publishes nothing (`no-solution`), Fast staying visible. INFEASIBLE at stage 1 is a contract violation rather than a plan property — Fast found a placement for the same input — and is `invalid-output`. Because every stage only ever adds an inequality, the incumbent of the last stage that produced one is feasible for the original constraints, and that is what is published. A partially staged result **is** cacheable: it is exactly the promise the cache makes. `objectiveValues` therefore carries, per term, `{ value, bound, status }`, so the stored row records how far the run got instead of implying proof it does not have.
- **What Optimized guarantees (the satisfiable replacement):** two independent, multi-worker, time-limited best-found runs cannot guarantee that PRI's priority value beats Time's and Time's makespan beats PRI's — either run may simply find a better incumbent for the other's primary term — so that cross-objective claim is struck. What is guaranteed instead is checkable and is what the product needs: **each variant's own primary term is no worse than the Fast baseline's value for that term.** Fast's placement is supplied to CP-SAT as a solution hint *and* as an upper-bound constraint on stage 1's term, so the search starts feasible and can only improve on it. A run that cannot beat Fast returns Fast's own value, which is a valid, publishable result.
- **Time quantisation (Fast's real duration arithmetic):** the previous “integer whole workdays computed by the caller” rule was false. `durationOf` returns `ASSUMED_SLICE_WORKDAYS` for `days === null` **without** dividing by `width`, and `days / width` otherwise **without** calling `snapWorkdays`; `snapWorkdays` only removes floating drift near an integer and deliberately preserves genuine fractions, and the production adapter carries fractional schedule numbers verbatim. A width-two one-day slice is 0.5 workdays and stays 0.5. The boundary is therefore fixed-point rather than integer-day: `SOLVER_QUANTUM = 48` units per workday, an exported constant chosen so widths 1–4, 6, 8, 12, 16 and 24 divide exactly. Bun computes each duration with Fast's exact rule, multiplies by `SOLVER_QUANTUM`, and sends an integer unit count; a product that is not integral within `DRIFT` (an estimate that does not divide) is rounded **up** to the next unit and the rounding is recorded in the request, so a solver block is never shorter than the work it stands for. `notBeforeDays`, `horizonDays` and every returned offset are in the same units; Bun divides by `SOLVER_QUANTUM` before materialising, so what is stored is in the fractional workday unit Fast already uses. Overflow is bounded before spawn: `horizonUnits × SOLVER_QUANTUM ≤ 2^31 − 1`, and a plan exceeding it fails with `horizon-overflow` rather than being sent. `SOLVER_QUANTUM` is covered by `SCHEDULER_CONTRACT_VERSION`.
- **Canonical input:** the exact argument tuple of `schedule(rows, edges, slices, notBefore, poolSizes, reach)`. Hashed: every `PlannedRow`'s `id`, `parentId`, `position`, `frozenNumber` and as-written `priority`, sorted by id; authored `{ predecessorId, successorId }` edges, sorted; the `slices` array **grouped by work item, groups ordered by work-item id, and each group's own order preserved as given** — the intra-item order is step precedence and carries meaning, the order *between* groups does not and must not be hashed, because production `WorkItemRepo.listByProject` selects work items with no `ORDER BY` and `slicesOf` emits each group in that row order, so SQL is free to hand blue and green different global arrays for one unchanged project. Each slice carries `workItemId`, `stepId`, `days` (null distinct from 0), `personId`, `width` and the sorted set `poolIds: readonly string[]`. Then `notBefore` entries as whole days from day zero (so `project.startDate` is normalised away rather than hashed); `poolSizes` entries; and `reach` from `project.dep_reach`. Excluded: Engine, Objective, the toggle, the display variant, clock, acting user, and request sequence — nothing in `schedule()` reads them. Objective, `contractVersion` and `budgetMs` are separate key columns, not hash inputs. Independently of the hash, `listByProject` acquires `ORDER BY work_item.id`: an argument tuple that varies between reads of an unchanged project is a Fast defect as much as a cache one, and the unchanged-hash proof is built through the real adapter rather than by reordering `rows` in a fixture.
- **Cache identity:** one SQLite table `optimized_schedule_cache` in the existing application database, declared in `apps/be-01/src/repository/schema.ts` with a forward migration under `apps/be-01/drizzle/`. Composite primary key `(projectId, inputHash, objective, contractVersion, budgetMs)` → `generation`, `status` (`'ok' | 'failed'`), `scheduleJson` (NULL iff failed), `failureReason` (NULL iff ok), `createdAt`. A row satisfies a read iff `status='ok'` and every key column plus `generation` matches the project's current state. Integrity is declared in the schema, not assumed: `projectId` FK `ON DELETE CASCADE`, `CHECK (status IN ('ok','failed'))`, a CHECK tying `ok` to non-NULL `scheduleJson` + NULL `failureReason` and the inverse for `failed`, `CHECK (objective IN ('pri','time'))`, `CHECK (failure_reason IS NULL OR failure_reason IN ('timeout','invalid-output','no-solution','internal-error','oom','horizon-overflow'))`, and read-time JSON validation that deletes an unparseable row and treats it as a miss. Retention is one rule: a project keeps only its current generation's rows, and allocating a new generation deletes every older row for that project in the same transaction — so an undo back to a previous hash is a miss that re-solves, with Fast visible throughout. **`apps/be-01/drizzle/**` is a prod-mode path, so every slice that lands a migration ships as a reviewed PR and is not self-merged.**
- **Contract version:** `contractVersion = "<SCHEDULER_CONTRACT_VERSION>+<solverVersion>"`. `solverVersion` alone was unsound, because durations, the leaf expansion and `baselineOffsets` are produced by Bun/domain code that the Python package version does not describe. `SCHEDULER_CONTRACT_VERSION` is an exported constant in `libs/domain`, bumped by any change to Fast semantics, `ASSUMED_SLICE_WORKDAYS`, `snapWorkdays`, reach or numbering semantics, resource tie-breaks, the canonicalizer, or the duration rule — and guarded by keying the Fast golden corpus on it, so an unbumped Fast change fails the corpus rather than silently serving stale rows.
- **Generations:** each project carries a monotonic `optimizationGeneration` **and the `optimizationInputHash` that generation was allocated for** — the counter alone could not record *which* hash it represented, so a second backend process had no atomic way to decide whether its computed H was the hash generation G already stands for or a new hash needing G+1, and a cold or in-flight generation has no cache row to reveal it from. Allocation is one transaction: read `(optimization_generation, optimization_input_hash)`; if the stored hash equals H, reuse the generation unchanged (so a backend restart on an unchanged plan does not thrash); if it differs or is NULL, `UPDATE … SET optimization_input_hash = :H, optimization_generation = :seen + 1 WHERE id = :projectId AND optimization_generation = :seen`, and in the same transaction delete every cache, slot and queue row of the older generation. The `WHERE` on the seen generation makes the pair a compare-and-swap: a losing writer retries and observes the winner's H rather than allocating a second generation for the same input. This is what makes cold-read coalescing and “exactly one child per objective” implementable across blue and green, and it fences the H1→H2→undo-to-H1 ABA sequence, a cancelled child stamping `failed` over a live `ok`, and two writers of the same key. Every spawn carries the generation and every write is conditional on it still being current.
- **Solver contract:** request is one JSON line `{ contractVersion, solverVersion, objective, budgetMs, stageBudgetSplit, quantum, horizonUnits, slices, edges, pools, baselineOffsets, fastHint }`. Bun owns duration and graph derivation; Python owns placement only. Each slice carries `key` (`sliceKey`), `durationUnits` (an integer in `SOLVER_QUANTUM` units, computed exactly as Fast computes duration and rounded up only when the estimate does not divide), `width`, `personId`, `poolIds`, resolved `priorityWeight`, and resolved `notBeforeUnits`. `edges` are already leaf-expanded with `reach` applied and already carry intra-item step-order edges, so Python never sees the tree or `reach`. Response is one JSON line `{ status, offsets, objectiveValues }` with `offsets` in the same units; parsing is the named seam `parseSolverResponse(raw)` so framing failures are testable without a process. Bun independently re-validates every offset — including that each is a non-negative integer multiple of one unit within `horizonUnits` — plus every edge, floor, pool capacity, assignee non-overlap and the recomputed objective values before storing. The solver reads no clock, database, or other schedule.
- **Optimized-result materialiser:** the response's `offsets` are an intermediate and are **never persisted alone**. `scheduleJson` is the serialised full `Schedule` — `slices`, `workItems`, `waitingForPerson`, `waitingForCapacity` — produced by a named domain function `materialiseOptimized(canonicalInput, offsets)`, because every bar and row consumes a whole `ScheduledSlice`: duration and estimate state, earliest/latest, float/critical, `boundBy`, `resourcePredecessorId`, `capacityPredecessorIds`, `capacityTeamId`, binding team, `width`, `effort`, parent projections and both wait counters, and several of those are not mechanically recoverable from an offsets map. The materialiser does not invent a second read contract and does not reuse Fast's annotations against different dates: it runs Fast's own annotation pass with the optimized starts **pinned**, so every field comes out of the one code path that produces it today, with resource edges and late times derived from the optimized placement rather than Fast's. Its invariants, each asserted and each separately tested: (1) every start is ≥ the recomputed floor set for that slice; (2) `boundBy` is the named latest floor when the start equals it; (3) **`ScheduleFloor` gains one additive member, `'optimizer'`**, used exactly when the start is strictly later than every floor — an optimizer may deliberately idle a low-priority slice while a high-priority one is unreleased, and that start has no value in today's union, so the union is extended rather than a floor being misreported; (4) under `'optimizer'`, `resourcePredecessorId` is null, `capacityPredecessorIds` is empty and `capacityTeamId` is null, which preserves the render-path invariant that those three are set exactly when `boundBy === 'capacity'`; (5) `duration`, `estimated`, `width` and `effort` are input-derived and identical to Fast's for the same canonical input; (6) float, critical, earliest and latest are recomputed over the optimized placement; (7) both wait counters are recounted from the materialised slices. `floorWordsOf` gains an `'optimizer'` case, and the whole materialiser is proved through the real plan-read payload rather than against the domain type alone.
- **Failure:** fail-closed and governed by one state machine. A failure writes exactly one `status='failed'` marker row with a `failureReason` (`timeout | invalid-output | no-solution | internal-error | oom | horizon-overflow`); Fast stays visible; failure is variant-specific. That row never satisfies a read, and it **does** suppress an automatic re-spawn for its exact key — a later read and a same-hash edit both launch nothing, because a read is a timer retry in disguise — while never blocking an explicit Retry (which overwrites it) or the fresh generation a new hash starts. A cancelled run writes no row at all.
- **Events:** a newly stored `ok` row and its durable `event_log` record are written in **one SQLite transaction**, and the broadcaster pushes from the committed record. A newly written `failed` marker row does the same through a second, non-result event **`schedule_optimization_failed`** — without it the read returns Fast while children run, success later emits `schedule_optimized`, and a failure emits nothing, so a client already on screen would sit at `Optimizing…` for ever and the manual Retry control would never appear; when both variants fail no connected client would have any reason to read the marker at all, and when one succeeds its unrelated success event would reveal the other failure by race. This does not disturb the settled rule that a cache **hit** broadcasts nothing: a hit is not a new outcome, and a newly written `failed` row is. The failure event carries no schedule and triggers no variant refetch — it flips that variant to `Optimization unavailable · Retry`. Both event payloads are `(projectId, generation, inputHash, objective, contractVersion, budgetMs)`, the failure one adding `failureReason`; **`budgetMs` is in the identity because it is a cache-key column** — raising the budget changes neither the hash nor the generation, so without it a larger-budget result would announce itself under the smaller-budget result's identity and a client holding that identity would ignore the only notice that should move it. **The delivery guarantee is narrowed to what the stack can keep:** one durable replay record per new outcome, plus one best-effort post-commit push. `event_log` is a replay buffer consulted on resume, not a dispatched-and-acknowledged outbox, and the process can die after commit and before the push, so “delivered at least once” over a live socket was false. The no-outbox constraint stands. The seam is named rather than assumed, because today `EventLogRepo.recordEvent` opens its own transaction and `GatewayBroadcaster.publish` both records and pushes: `recordEventIn(tx, subscription, message, createdAt)` writes inside the caller's transaction, and `pushRecorded(subscription, recorded, event)` buffers and pushes an already-recorded sequence without recording it twice; `publish` becomes those two calls and keeps its behaviour.
- **Resource ceilings:** 4 solver processes per project, 16 global (Dany 2026-09-02), enforced in SQLite rather than coordinator memory — blue and green backends coexist against one database file, and two in-memory coordinators would each admit their own sixteen. A `solver_slot` table keyed `(projectId, generation, objective)` holds `ownerId`, `pid`, `startedAt`, `heartbeatAt`; admission is one transaction that reclaims heartbeat-expired slots, refuses at 4 per project and 16 global, then inserts. `solver_queue` is the FIFO, keyed `(projectId, objective)` so a project holds at most one queued entry per objective and a new generation replaces rather than accumulates, ordered by `enqueuedAt` then `projectId` then `objective` — `objective` is what makes the order total when a project's PRI and Time entries share a timestamp; at dequeue an entry is discarded without launching if its generation is no longer current **or** the project's toggle is no longer ON — the toggle is excluded from the hash, so the hash check alone would not catch an opt-out.
- **Budget:** one config value `solverBudgetMs`, default 60000 (Dany's >=60s floor), child killed at `solverBudgetMs + 5000`. It **is** a cache-key column, because a larger budget can find a better feasible result and an operator who raises it must not keep being served the smaller-budget answer. The cached promise is exactly "the best result found for this input, this contract, this objective, at this budget".
- **Restart and orphans:** nothing is resumed on startup and no queue is rebuilt. A reparented child cannot be identified by a recycled PID, so cleanup does not depend on finding it: `wbs-solver`'s entrypoint calls `prctl(PR_SET_PDEATHSIG, SIGKILL)` before reading stdin, so it dies when its parent does; slots are reclaimed by heartbeat expiry rather than process probing; and each backend release runs in its own container/cgroup, which is a recorded deployment obligation the ceiling arithmetic depends on.
- **Stored-enum boundary:** every new stored text enum gets both a database `CHECK` and an explicit read-time validator, mirroring `toProject`, which today validates `estimateMethod`, `depReach` and `estimateRounding` rather than casting or defaulting them. That means `isOptimizedStatus`, `isObjective` and `isFailureReason` on the cache read path, `isScheduleEngine` and `isScheduleObjective` on the project read path, `CHECK (optimization_enabled IN (0,1))` on the boolean, and a thrown error naming the column and the stored value on any miss — a malformed trusted row must not cross into a precise internal type and produce an impossible selector branch or a silent default. `failureReason` in particular was previously accepting any non-null text. Negative tests inject an unknown value for each of the five enums and the boolean on the production read path.
- **Project settings:** the toggle, Engine and Objective are project-scoped persisted columns, not view state. An additive migration adds `optimization_enabled` (default false, which is what makes OFF-by-default true for existing rows), `schedule_engine` (default `'fast'`), `schedule_objective` (default `'pri'`), `optimization_generation` (default 0) and `optimization_input_hash` (nullable, default NULL), with repository mapping, a PATCH contract under the existing project-write authorization, the three settings in the read payload, and a new `project_settings_changed` variant on `ProjectEvent` emitted by `ProjectService.update`. This is a **second prod-mode path**.
- **“Same order” — the exact comparison relation:** the indicator's four sentences (“Same deadline + same order”, “Same deadline + reordered”, and their earlier/later pairs) require a defined order, and map or array iteration order is not one. `sameOrder(a, b)` holds iff for **every** pair of slices `(s, t)` present in both, `sign(startA(s) − startA(t)) === sign(startB(s) − startB(t))`, compared in quantised units on the materialised schedules. That is a strict weak ordering by start: it is blind to a uniform shift of the whole plan, blind to iteration order, and it treats ties as first-class — a tie broken and a tie created are both “reordered”, which is the honest answer, since two slices that used to start together and now do not have visibly changed the plan. Zero-duration slices participate by start like any other. The relation is computed **server-side on the materialised schedules** and shipped as one boolean beside the day-count delta, so client and server cannot label the same pair differently.
- **Determinism:** production runs multi-worker under a wall-clock budget and is explicitly not required to be reproducible; one result is stored and every collaborator refetches that row, so all clients converge. Reproducibility is asserted only under a pinned test configuration (`num_search_workers=1`, fixed `random_seed`, deterministic time limit).

- **Migrations ship with their rollback:** AGENTS.md mandates a `down.sql` beside every `migration.sql`, and both prod-mode slices previously asked only for a “forward migration”. Each of slices 3 and 3b explicitly creates its own `down.sql` and proves rollback-then-re-apply against the applied set; without it migration lint and `readMigrationFolders` refuse at the gate and an aborted blue/green deploy cannot return.
- **Packaging is part of the change, not a consequence of it:** creating the `wbs-solver` package and running its suite standalone can be green while every deployed solve fails on an absent executable. The Dagger/image path installs the pinned Python runtime and the locked OR-Tools environment, copies the package and entrypoint into the be-01 runtime, exposes the installed version to the coordinator as the `solverVersion` half of `contractVersion`, and an ordered slice proves a spawn **from the built image** plus the negative case where the package is absent. The Python suite gets its own Nx target wired into the gate.

## Risks / Trade-offs

- **New language in the stack (Python):** the deploy image must carry a pinned Python runtime plus OR-Tools. Mitigated by isolating the solver behind a one-line stdin/stdout contract and versioning the package into the cache key.
- **Two concurrent solves per edit:** CPU cost. Mitigated by the OFF-by-default toggle, debounce, cancellation, and the 4/16 ceilings.
- **SQLite growth:** one row per objective per project per valid input, but only the latest pair is retained so the table stays bounded per project.
- **Best-found semantics:** a host-dependent solve could surface differing "optimal" dates; the exact input hash plus the reported day-count comparison forces like-for-like reads, and storing exactly one result per key means collaborators never disagree even though a re-solve might have found other offsets.
- **Two prod-mode migrations inside a dev-mode item:** the cache/slot/queue tables and the four project-settings columns are the prod-mode paths here. Each is isolated into its own slice (tasks.md slices 3 and 3b) so the rest of the change stays dev-mode and only those slices carry the reviewed-PR obligation.
- **Cross-process coordination in SQLite:** admission and generation allocation become contended write transactions on the same database as the application. Mitigated by keeping each transaction to a few indexed row reads and one insert, and by the 5-second slot heartbeat being an `UPDATE` on a primary-key hit.
