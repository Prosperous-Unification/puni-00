# PostgreSQL exact-identity index feasibility: observed results

2026-11-04, PostgreSQL **18.6**, Bun **1.4.4** orchestrating container-local **psql**. Immutable image: `postgres@sha256:edb0c08dc33befd0262ab3b5cf1c4f3f8cfd8b09e88c05b45adee29d6761ddb6`.

The candidate SQL primitive is feasible in these observed cases. This is not an engine/schema decision or a provider implementation. Production source stayed at reviewed PR787 head `9917286d18ae327182558f9eec17463fe01339ac`.

| Observation                                                                 | Actual evidence                                                                                                                                                                                                                                                        |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Direct full-key B-tree indexing is insufficient for the admitted key domain | A 65,550-byte JSON identity failed insertion into a bytea primary key with native psql exit 3 / SQLSTATE 54000.                                                                                                                                                        |
| A nonunique fixed-size bucket can locate retained full keys                 | Nine exact byte roundtrips, including two long identities with a common prefix, JSON-escaped NUL, literal escape spellings, distinct lone high/low surrogates, U+FFFD and astral text.                                                                                 |
| A digest need not become the identity                                       | Two deliberately colliding keys stayed distinct; both identical replies retained their original UUID slot, changed content conflicted, and final reads retained the original full key/payload bytes.                                                                   |
| Separate lock then lookup at READ COMMITTED supports this primitive         | Independent A/B backend PIDs; observer confirmed B waited on A's advisory lock. A commit yielded an identical reply and one row; conflicting content yielded conflict and one row; A rollback allowed B to insert and left one row.                                    |
| Omitting the lock is caught                                                 | Controlled competing writes produced two distinct slots and two rows; the one-row assertion failed.                                                                                                                                                                    |
| Combining lock/lookup into one statement is caught                          | B was observed waiting, then used its old statement snapshot and inserted a second row after A committed; the one-row assertion failed.                                                                                                                                |
| REPEATABLE READ is not the equivalent protocol                              | B established its snapshot before waiting; separate lock/lookup still produced a second row after A committed, failing the same assertion.                                                                                                                             |
| Normal owned-resource lifecycle completed                                   | All 72 native command/client receipts have observed exits and matching stream hashes. All clients exited; separate server census showed zero experiment backends. Exact owned container stopped with exit 0/no OOM, was removed, and daemon listing confirmed absence. |

Limitations: this uses psql, not the Bun SQL adapter. It proves neither all-writer participation nor multi-operation RunStore atomicity, revisions/counters/capacity, coherent multi-query reads, migrations/integrity scans, cancellation, timeout cleanup under injected faults, lost COMMIT replies, full provider conformance or paused-writer transfer. The three SQL counterfactuals are laboratory negatives; they are not production-path R5 credit. The earlier P10 immediate client-close/backend-absence failures remain unresolved. JSON bytes are exact for these finite fixtures; PostgreSQL finite value limits remain outside an unbounded mathematical-domain guarantee. No public hash-ID rule, engine/private schema/index format, output/ACP profile, operator migration or production action is adopted.
