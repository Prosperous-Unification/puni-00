## Strengths

- The proposed schema-derived key exists before metadata and remains the same throughout bootstrap and subsequent writes. Database scoping and the single-bigint lock representation match PostgreSQL's documented mechanisms. The proposed `pg_locks` assertion can distinguish that representation from the two-integer overload. [PostgreSQL 18 advisory functions](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS), [pg_locks](https://www.postgresql.org/docs/18/view-pg-locks.html).
- The existing private session exposes the required integration points: `postgres/session.ts:75` supplies keyed writes and snapshots; `:179` and `:182` establish the required isolation modes; `:186` acquires the lock before invoking the callback; `:194` validates native commit acknowledgement. Bootstrap DDL and adapter admission can live in those callbacks without changing public ports. This is feasibility from source inspection, not a new runtime proof.
- The proposed opener preserves the relevant SQLite semantics. `sqlite/open-stores.ts:123` audits format/history/configuration before returning retained ownership, while `sqlite/schema.ts:204` and `sqlite/read-history.ts:25` explain why a metadata-only adapter is insufficient. The design retains full semantic validation alongside physical checks.
- The plan correctly preserves exact bytes, nonunique digest buckets, original acknowledgements and operation-specific guard order. For example, `sqlite/run-store.ts:874` rejects a retained write-local command identity before execution replay; the design expressly carries that adapter responsibility forward.
- Durability checks, catalog/ledger admission, two-process bootstrap, half-write rollback, uncertain COMMIT and unchanged shared-suite execution are explicit future obligations. Engine/serialization approval is clearly separated from the proposed physical mechanism. The unresolved transfer envelope and external pause/drain protocol are honestly identified as separate acceptance work.

## Important findings

### I1 — Bind bootstrap's second admission transaction to the incarnation it just committed

**Location:** `openspec/changes/workflow-postgres-provider/physical-store-design.md:65`, together with `:69`; coverage in `physical-store-tasks.md:31`.

Bootstrap commits the newly generated incarnation, then requires ordinary open/admission before returning a bundle. Ordinary open pins whichever valid incarnation it observes only after its own validation. The text never carries the bootstrap-created incarnation into that second transaction as an expected identity.

Consequently, a replacement between the acknowledged creation commit and ordinary admission can pass all schema/key/configuration checks and be adopted by the bootstrap caller. The existing replacement negative concerns an already opened bundle; it does not cover this interval before the first pin. The advisory transaction lock ends at commit, so it cannot bridge the interval by itself. This is a detection gap, not a request to prevent administrators from replacing schemas or to invent the deferred maintenance pause protocol.

**Minimal fix:** Add to line 65: “Retain the incarnation generated by this bootstrap invocation. Its subsequent locked admission must require that exact incarnation before returning a bundle; replacement throws without adopting or deleting the replacement.” Add a task/scenario that pauses after the successful bootstrap COMMIT, replaces/rebootstraps the namespace with identical options but a different incarnation, and proves the original call rejects while the replacement remains unchanged. Remove only this expected-incarnation comparison for the R5 negative.

## Minor findings

### M1 — Make the per-operation catalog/ledger obligation explicit in the implementation checklist

**Location:** `openspec/changes/workflow-postgres-provider/physical-store-design.md:71`; `physical-store-tasks.md:39`; normative requirement at `specs/workflow-postgres-store/spec.md:99`.

The spec already requires complete ledger/catalog/configuration validation within the admitted transaction. The design's write sequence abbreviates this to “incarnation/key/format/configuration,” and its read sequence says “pinned physical identity and needed integrity.” The task's ledger/catalog corruption cases are described as opening cases. A reader implementing those narrower sentences could mistake a matching metadata format hash for current catalog/ledger validation, particularly for artifact operations that do not run the complete RunStore history reader.

This is a checklist ambiguity rather than a claim that the normative spec authorizes caching: line 99 and the design's prohibition on mixing cached validation with later snapshots already state the stronger contract.

**Minimal fix:** Say explicitly that each write and read validates the complete compiled catalog/ledger/configuration inside that operation's transaction, in addition to pinned incarnation/key. Extend the task with an already-open-bundle case: alter a ledger row or an empty relation's required constraint while leaving metadata/incarnation unchanged; the next read and mutation must reject. Include an artifact path so the proof cannot accidentally depend on the RunStore history scan. Restore the fault and demonstrate successful operations; remove the corresponding operation-time check for the R5 negative.
