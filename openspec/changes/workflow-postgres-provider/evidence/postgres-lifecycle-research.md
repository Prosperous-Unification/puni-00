# PostgreSQL/Bun awaited-close prerequisite

Research date: 2026-11-04. This is new lifecycle design research following the user's PostgreSQL/serialized-write choice, not another P01–P11 campaign. Read-only source/documentation work only; no database, process, container, credential, role, network-service or gate mutation. This report does not adopt a schema/store format, establish adapter conformance or resolve prior P10 failures.

## Actionable conclusion

Use **one continuously pinned observer connection**, separate from every write connection but using the **same owner-supplied database role/DSN**, and a unique startup `application_name` cookie on **every physical writer connection** belonging to this provider bundle. Before allowing a physical connection to write, record its server/backend identity and have the observer verify it. After fencing and draining admitted operations, close every writer client and poll fresh observer statements until no registered writer identity or cookie-bearing writer remains. A failed observation or expired deadline rejects close permanently; it is never an empty observation.

Successful close can distinguish **bundle write quiescence** from **final observer transport disposal**. Require server-observed disappearance of all bundle writers, then stop the observer's fixed read-only SQL and await its local disposal. Do not recursively require another observer to prove the first observer's OS process has exited. This is a proposed interpretation consistent with the existing lifecycle contract, provided its precise limits below are documented and proved. It does not claim all PostgreSQL processes are absent, zero physical disk activity, business settlement or that an unanswered COMMIT rolled back.

## Primary-source facts

1. `pg_stat_activity` reports server processes; PID, backend start, role, database, application name, state, transaction start and parallel leader identifiers describe the observed backend. Current activity is separate from delayed cumulative counters. Its backend-activity snapshot is reused within a transaction, so poll using separate completed autocommit commands, not one long READ COMMITTED transaction. [PostgreSQL 18 monitoring](https://www.postgresql.org/docs/18/monitoring-stats.html).
2. **Same role is sufficient; no blanket monitoring grant is required.** Exact 18.6 `HAS_PGSTAT_PERMISSIONS` permits role privileges of either the backend's session role or `pg_read_all_stats`. The latter is an alternative for different-role observers, not a prerequisite here. Exact `pg_stat_get_activity` exposes application name before its permission branch, but restricts backend-start/state details within that branch. Validate required details instead of assuming public cookie visibility proves complete visibility. [18.6 pgstatfuncs.c](https://raw.githubusercontent.com/postgres/postgres/REL_18_6/src/backend/utils/adt/pgstatfuncs.c).
3. Role memberships can confer privileges and permit role changes. Keep writer and observer `session_user`/`current_user` fixed to the configured role; no `SET ROLE`, changed session authorization or security-definer observer routine. This avoids changing which backend details the observer may see and requires no new credential architecture. [Role membership](https://www.postgresql.org/docs/18/role-membership.html), [session/current user functions](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-INFO-SESSION-TABLE).
4. PostgreSQL's application name is short and printable ASCII; use a complete cookie under the server's `NAMEDATALEN` limit (63 printable ASCII bytes for the standard build), verify exact server echo and never tolerate truncation/escaping. It is an attribution cookie, **not authentication or a secret**. [Application name](https://www.postgresql.org/docs/18/runtime-config-logging.html#GUC-APPLICATION-NAME).
5. Bun 1.4.4 `options.ts` collects `options.connection` entries into the startup-parameter string passed to its PostgreSQL connection. Set the cookie there explicitly rather than through a later pooled `SET` or process-global `PGAPPNAME`. A later `SET` risks missing earlier activity and affects only whichever connection executed it. [Bun 1.4.4 options.ts](https://raw.githubusercontent.com/oven-sh/bun/bun-v1.4.4/src/js/internal/sql/options.ts).
6. Exact Bun 1.4.4 `pool.ts` teardown calls `destroy()` for each local connection then resolves its closing promise; `destroy()` invokes native close and can settle local bookkeeping. This is **not a server acknowledgment of transaction cleanup or backend exit**. The pool can also create replacement connections when existing ones close and callers wait. The provider must own its admission/creation fence. [Bun 1.4.4 pool.ts](https://raw.githubusercontent.com/oven-sh/bun/bun-v1.4.4/src/js/internal/sql/pool.ts).
7. Bun documents `reserve()` as an isolated connection; releasing it returns that connection to its pool, whereas `reserved.close()` closes it. `max: 1` alone does not establish an unchanging session. Use a retained reserved observer, close its owning pool too, and never fall back to the general pool after loss. Exact source binds scoped operations to their stored connection and rejects a missing connection. [Bun SQL reservations](https://bun.sh/docs/runtime/sql#reserved-connections), [Bun 1.4.4 sql.ts](https://raw.githubusercontent.com/oven-sh/bun/bun-v1.4.4/src/js/bun/sql.ts).

## Proposed identity and coverage invariants

These are design requirements inferred from the facts above, not observed adapter behavior:

- Generate a unique nonsecret bundle cookie; use distinct writer/observer purpose values. Every writer client, including artifact, open/inspection or reconnect paths capable of persistent writes, receives the writer cookie at startup. Do not share a writer pool between provider bundles or use the default global SQL client. Keep clients private and prohibit changing/resetting the application name.
- Register **each physical writer session before any persistent mutation**. Read its `pid`, exact `backend_start`, database OID/name, session role OID/name, cookie and server-start identity on that same reserved/transaction connection. Have the pinned observer see that exact tuple before permitting writes. Replacement writer connections must repeat this handshake; a completed SQL operation on a different backend is not evidence about the first.
- Preserve timestamp precision on the server side, for example a stable textual/microsecond representation, instead of reducing `backend_start` to a millisecond JavaScript Date. PID alone is unsafe because it can be reused. Keep registrations for the whole bundle lifetime even after apparent disconnect, so a renamed or recycled-cookie backend cannot silently disappear from the accounting.
- A fresh sample reads the complete relevant role-visible backend set **before cookie/state filtering**. Validate fixed observer role, database, observer session identity and required non-null identity fields, then match both the cookie and recorded full backend identities. Examine registered PIDs even if the role/cookie changed. SQL must not hide rows using `state = 'active'`, `xact_start IS NOT NULL` or a cookie-only `COUNT(*)`; idle connections can receive buffered future work and aborted transactions can still retain resources.
- Expected nulls, such as `xact_start` for an idle session or `leader_pid` for a nonparallel backend, are valid modeled states. Missing required `backend_start`/role/state visibility for a potentially owned backend is a failure, not evidence of absence. A same-role control writer observed during open provides a positive visibility proof; remove that visibility in a negative test.
- Include every matching writer-cookie process and any owned parallel descendants; do not silently exclude rows by `backend_type = 'client backend'`. Independent other bundles using the same role remain out of this bundle's close boundary. The protocol cannot cover arbitrary server extensions/functions that launch autonomous writes on unregistered sessions; fixed provider SQL must exclude that behavior.

## Same server, without blind reconnection

Use direct, pinned connections to one PostgreSQL server instance for this prerequisite. Transaction/statement multiplexing proxies, transparent session migration and independently routed failover endpoints are unsupported until separately modeled. Observing absence on another server proves nothing about the original.

Capture observer `pg_backend_pid`, exact `backend_start`, role, database, `pg_postmaster_start_time`, server address/port and recovery state at initialization; validate continuity in each sample. Address/port may be intentionally null for a Unix socket. These descriptive values are not globally unique attestation: observation of each writer's full identity on the continuously connected observer is the stronger same-server evidence. Server information functions define the relevant identifiers. [PostgreSQL session functions](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-INFO-SESSION-TABLE).

If the observer drops, the server restarts, its PID/start identity changes, a query fails, or a driver unexpectedly reconnects, reject close with the original cause. Do not reconnect to a new server and accept zero rows, even if a hostname, cluster system identifier or postmaster timestamp appears compatible. A surviving observer connection plus validated identity is a required proof assumption, not a convenience retry policy.

## Why the final observer does not require another observer

The observer uses the same role, so it is **not privilege-isolated from writes**. Its read-only property must be an audited code invariant: a private connection accepting only fixed, schema-qualified `pg_catalog` inspection SELECTs, no arbitrary SQL, stored user functions, temporary-table writes, advisory-lock acquisition, role switching, COPY or prepared transactions. Set/verify `default_transaction_read_only = on`; verify each sample's read-only setting. READ ONLY is a defense, not a claim of no disk writes: PostgreSQL explicitly defines it at the SQL level and permits some temporary-table writes. [READ ONLY semantics](https://www.postgresql.org/docs/18/sql-set-transaction.html).

After the final successful writer-absence sample has completed, send no more observer work. Await bounded observer/reservation/pool disposal and retain disposal errors. The observer's final in-flight work can only be the fixed inspection SELECT or rollback/termination of such work; it cannot later publish provider records. Consequently a lingering read-only server transport is outside **writer transaction** quiescence, while its owned local resources remain inside awaited disposal. If the desired contract instead literally requires every remote OS process gone, `pg_stat_activity` plus another ordinary observer cannot prove that without regress; an independently owned external supervisor would be a separate requirement, not introduced here.

Exact 18.6 supplies a useful narrower boundary: `ShutdownPostgres` aborts any active transaction and releases user advisory locks in a `before_shmem_exit` callback. `ipc.c` runs those callbacks before `on_shmem_exit`; `pgstat_beshutdown_hook` clears the activity PID during the latter phase. Thus disappearance supports completed transaction shutdown on the ordinary core-server exit path, **not proof of OS process reaping or every final cleanup callback**. The activity snapshot is copied one backend at a time, not a globally atomic photograph; closure/no-new-writer invariants must make the target set converge. [18.6 postinit.c](https://raw.githubusercontent.com/postgres/postgres/REL_18_6/src/backend/utils/init/postinit.c), [18.6 ipc.c](https://raw.githubusercontent.com/postgres/postgres/REL_18_6/src/backend/storage/ipc/ipc.c), [18.6 backend_status.c](https://raw.githubusercontent.com/postgres/postgres/REL_18_6/src/backend/utils/activity/backend_status.c).

## Prepared transactions and pooling boundaries

`PREPARE TRANSACTION` detaches transaction state from its session and permits a later commit by another session; `pg_stat_activity` absence cannot prove that state gone. `pg_prepared_xacts` provides separate transaction identities and ownership but no automatic mapping to an application-name cookie. Prohibit Bun distributed transactions and SQL PREPARE TRANSACTION in this provider. For the simplest strong deployment prerequisite, verify `max_prepared_transactions = 0`; PostgreSQL documents that zero disables the feature. If the selected environment enables it, do not default the setting to zero or infer safe close: explicitly prove provider SQL cannot prepare transactions, or design separate complete attribution/accounting before claiming that stronger boundary. SQL prepared **statements** are different and are not evidence of prepared two-phase transactions. [PREPARE TRANSACTION](https://www.postgresql.org/docs/18/sql-prepare-transaction.html), [pg_prepared_xacts](https://www.postgresql.org/docs/18/view-pg-prepared-xacts.html), [max_prepared_transactions](https://www.postgresql.org/docs/18/runtime-config-resource.html#GUC-MAX-PREPARED-TRANSACTIONS).

## Bounded close sequence and sticky outcome

Proposed order:

1. Synchronously fence both ports and future resource creation, cache one close promise/outcome, capture the current queue boundary. Queued operations reject at admission. Existing admitted work retains its ordinary operation outcome.
2. Drain admitted operations under their finite operation bounds and the overall close deadline. Await their transaction completion; never convert an unanswered COMMIT into rollback or retry it blindly.
3. Initiate bounded disposal of every writer reservation/client/pool and prevent late callbacks from reopening them. Local close success only allows the server observation phase; it does not complete it.
4. Poll fresh completed autocommit observer queries until the registered/cookie-covered writer set is absent. No absence scan before writer creation is fenced, and no accepting a stale cached result. Query errors, missing visibility, identity discontinuity and unexpected nulls fail immediately; remaining writers may converge only until the finite deadline.
5. Stop observer SQL, await bounded final local observer disposal, then resolve. Any disposal/observation failure remains sticky on repeated close; ports stay fenced. Preserve additional cleanup failures alongside the first cause, without replacing it or reporting cleanup success.

Use one monotonic close deadline covering drain, local writer disposal, observation and observer disposal; per-stage finite bounds must fit within it. Bound observer SQL server-side with `statement_timeout`, but also bound client waiting because a network partition can prevent any response. A JavaScript `Promise.race` timeout does not cancel underlying work: fence/close resources and own eventual rejections. Deadline expiry means **quiescence unproved**, not success. Server statement/transaction timeouts help interrupt work but do not prove immediate backend absence. [PostgreSQL timeout semantics](https://www.postgresql.org/docs/18/runtime-config-client.html#GUC-STATEMENT-TIMEOUT).

Backend disappearance never identifies a commit outcome: PostgreSQL explains that a backend may finish work before it notices disconnect. An unacknowledged COMMIT remains unknown to that operation even after close establishes no future writes. Recovery reads may resolve domain-specific state later under a separate protocol. [Protocol termination](https://www.postgresql.org/docs/18/protocol-flow.html#PROTOCOL-FLOW-TERMINATION).

## Required new proofs, not the old campaign

- Keep a tagged real writer running after client-side close resolves; close must still wait or reject. Removing the server-observation check must make this assertion fail.
- Show one same-role writer's full identity from the observer, then inject missing/restricted identity fields or a wrong-role observer; close must reject, not count zero. No pg_read_all_stats grant is needed for the baseline.
- Demonstrate fresh polls versus a deliberately reused activity snapshot; changed observer PID/start or a redirected/reconnected observer must fail closed.
- Exercise a new physical writer/reconnect and close-during-connect: no write before registration and no late resource creation after the fence. Remove tagging/registration in a negative control and observe failure.
- Distinguish reused PID with a different exact backend start, cookie collisions/renaming, unrelated same-role bundles, and an idle-in-transaction writer. Never test only active queries.
- Test observer final disposal failure and deadline expiry separately; repeated close preserves the first cause, while both ports reject and every independent cleanup is attempted within bounds.
- Prove the observer's allowed SQL cannot mutate provider state or prepare a transaction, and that worker absence plus observer disposal does not imply an unknown COMMIT result.

These need production-path assertions and observed negative failures with adjacent R5 Proof comments when implemented. No such test was run by this researcher. Prior P10 stays unresolved until the new bounded observation protocol is implemented and independently exercised; its old evidence is neither erased nor generalized into a permanent impossibility.
