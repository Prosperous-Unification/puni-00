# Design — sortable step references

`formatStepReference` takes the effective work-item number, immutable step code, one-based ordinal and project step count. Its ordinal field is padded to `String(stepCount).length`. The callers in `readStepAddresses` and plan-document export already use `orderSteps`; each passes the same index and list length. The resolver finds the code in that ordered list, preserves its ordinal/code consistency refusal, and returns the same formatter's spelling. The FE cell detail and Copy reference action render the work-item read's `stepNodes[].reference`, so no separate frontend formatter is needed.

The project's address revision already describes step IDs, codes and positions, including uncoded steps. Adding, removing or reordering steps therefore changes the revision before a stale readable reference can resolve to another node. `sn1.<workItemId>.<stepId>` remains the stable node identity and copied link target. Code-only and unpadded aliases stay valid input at the current revision; only output becomes ordinal-first.

Release order is enforced outside code: merge `accept-padded-step-reference-aliases` first, then verify its SHA is synced to dev and be-01 responds before merging this PR. Dev uses a source checkout and watchers, so a brief mismatch during a sync is possible; the prior parser must accept padded references before this change emits them. Production currently runs pre-product `0afc7775`, which has no WBS app or step-reference routes. Recheck that state before a product release; a future product blue/green swap shares the public API. This follow-up has no database migration and does not alter step codes or permissions.
